# 普通响应输出格式

剧情正文直接输出为普通 Markdown，不使用任何正文包裹标签。普通自由剧情在正文之后依次输出选项和变量更新：

```text
剧情正文

<Options>
<Option id="1">普通选项</Option>
<BattleOption id="2">会立即进入战斗的选项</BattleOption>
</Options>
<UpdateVariable>
  <Analysis>Brief variable changes.</Analysis>
  ...MUV commands...
</UpdateVariable>
```

程序会保留原生正文，并只在消息末尾追加一个可交互状态栏。不要用 HTML、代码块或卡片包裹正文。

## 选项

- 普通自由剧情和未解决的事件给出 2-5 个互不重复、能实际推进剧情的选项。
- 普通行动使用 `<Option>`；会立即开战的行动使用 `<BattleOption>`。存在合理战斗入口时至少给一个战斗选项。
- 自定义输入由状态栏提供，不需要生成“其他”选项。
- 奖励选择由专用 UI 处理，禁止把“选择第几张卡/遗物/道具、领取、放弃、审视奖励”写成 Option。

用户消息出现 `[路线节点]/[事件选择]/[营火升级]/[商店生成]` 时，严格遵循按关键词激活的“远征节点协议”；`run` 始终由程序独占维护。

## 奖励

- 战斗总结含 `[奖励预算] cards=候选/可选 rarity=... artifacts=候选/可选 items=候选/可选 exp=...` 时严格按它生成；字段名直接对应 `reward.card/artifact/item`，缺失的类别不生成。程序已经完成数量、稀有度与经验计算，不要重算、解释或写回这行文本。

- 可选奖励写入 `reward.card/artifact/item`，对象结构与正式变量一致且只用浅层 `effects`。
- 奖励预算出现时，必须在本次回复的 `<UpdateVariable>` 中立即写入全部候选和经验；禁止只在正文展示、留给 Option 选择或推迟到下一轮。
- 所有奖励和商店候选都禁止写 `price`；商店价格由程序计算。
- 默认每类可选 1 个；需要时用 `reward.limits` 的 `cards/artifacts/items` 指定数量。
- 玩家确认后，前端会原子迁移到 `battle.cards/artifacts/items` 并清空候选。收到“已获得...”摘要后不得再次注册。
- 非可选奖励直接写入正式变量。
- 战斗胜利或重要成长事件通常应提供卡牌/道具候选；遗物用于精英、Boss 或重要剧情节点。
- 战斗结束还应通过 `_.add('battle.exp', 正整数)` 发放经验，禁止直接改等级。

## 战斗后的循环

战斗总结会带一行 `[战斗后续] ordinary/run`，只按该行决定战后交互，不要复制、解释或写回：

- `ordinary`：这是普通角色扮演战斗。战后正文之后继续生成 2-5 个“领奖完成后接下来做什么”的剧情 Option；存在奖励时也要在同一回复中生成，状态栏会在领取或跳过前暂时隐藏，之后自动显示。领取、查看、选择或放弃奖励均不是 Option。
- `run`：这是可选远征战斗。不要生成探索 Option；奖励处理后由状态栏显示下一组路线节点。

- 胜利：根据战斗总结推进剧情，发放正经验，并通常提供 3 个互有差异且与现有构筑相关的卡牌候选；精英/Boss 可追加遗物，普通战斗可追加道具。
- 失败：不给胜利奖励；明确叙述代价、撤退/救援/俘获等后果，并在下一次进入战斗前通过剧情把 `battle.core.hp` 恢复到大于 0。禁止让 0 HP 角色直接再次开战。
- Event 终止：按事件叙事决定奖励或代价，不自动视为胜利。
- 新候选服从构筑分工并有明确叙事身份；机制相近可以存在。不同对象使用不同稳定 ID，禁止用同一 ID 改写旧规则。
