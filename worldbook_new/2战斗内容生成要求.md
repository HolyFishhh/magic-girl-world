# AI 战斗内容生成契约

开局关键引擎、形态变化和支援牌可主动使用 `innate:true`（固有），不能只在说明中写开场抽到。固有牌开战时进入手牌，可超过常规起手抽牌数但不超过手牌上限；超出上限的固有牌留在抽牌堆顶部。按构筑需要使用，不设数量配额；战斗中新生成的临时模板不写 innate。

协作敌人应设计同伴死亡后的反应：同一行动使用互补 `when` 分支，有同伴时支援，`self.ally_count == 0` 时反击玩家；或者使用 `escape_when:"self.ally_count == 0"` 预告逃跑。满足条件后至少预警一回合，头顶显示逃跑倒计时；为0时在本回合结束播放逃跑动画后离场，期间仍可击杀或阻止其存活到离场，不按击杀发放掉落。依赖指定队友时，用可执行选择器条件检查目标存活，避免持续给死者增益。敌人 `description` 应介绍其特点，并暗示失去队友后的反应、逃跑或携宝特性。适合携宝的精英、运输者、稀有怪可主动设计 `defeat_reward` 专属卡牌、遗物、道具或金币；只在击杀该原始敌人后发放，逃跑会失去其专属掉落及对应的基础金币份额。不要为所有敌人机械套用同一种行为。

回合末顺序：先结算玩家卡牌、遗物、能力、姿态、状态等回合末被动与到期效果，再让己方存活召唤物按入场先后行动，随后敌人按战场从左到右的稳定队列行动。每个单位的效果、死亡处理与动作反馈完成后才轮到下一个；自动回合队列不因 speed/action_priority 反转左右或入场顺序。中途达到战斗终态立即停止后续行动，敌方召唤及双方回合开始/结束的其他已声明触发仍按所属方阶段结算。

召唤策略补充：卡牌根部可写 `requires_summon:"模板ID"`，仅在我方有该模板的存活召唤物时才能打出，检查发生在扣费前；不能用效果的 `when` 冒充出牌门槛。`activate_summon:{selector,action:{id,name,emoji?,description?,fixed?,effects}}` 可命令选中的召唤物发动一次原行动表中没有的新行动；来源与普通 `self` 均是选中的召唤实例，作用于主人仍须 `summoner_effects`。不提供 action 时执行该召唤预定行动。临时 action 不替换预告的常规行动，也不能与死亡触发同时指定。召唤在入场及正常行动结算后预定下一次行动并保存，玩家看到的意图与正常行动执行一致；预览不重新抽取随机行为。召唤自己的 abilities 可监听回合或伤害等事件，卡牌可用 apply_summon_status 赋予回合回复等能力，行动公式 self.hp/self.max_hp 读取召唤自己的生命。

本游戏是单玩家卡牌战斗：玩家抽牌、支付能量并打牌，可面对一个或多个敌人；各敌人按稳定行动顺序执行自己的行动。本条是所有 AI 可生成战斗对象、效果字段、触发器、目标视角和公式边界的唯一权威。机制以普通文本交付，推荐单个 JSON 对象；这不要求模型接口支持 JSON 模式。可执行数据使用下述浅层字段语法；禁止旧 `effect` 字符串、内部 `spec/op/steps` AST、XML 效果树和字符串化对象。

创作依照已成立剧情和玩家要求；格式依照本契约。AI 负责机制、数值与表现，程序只补技术结构。未知语法只能等价改写；无法保留原机制时报告具体缺口，不得删掉要求、改写描述或用空效果换取通过。流派组合方法见“流派体系与设计方法”，本条只定义数据与执行语义。

## 总则

<!-- shared:semantic-preservation -->
语义保留：结构或载体改写须保留事件、条件、发生者、持有者、目标、数值、时机、次数及寿命；不能靠删条件或收益、改说明、换机制获得合法结果。修复仅在指定可修改字段内进行；载体迁移无法在该范围内保持上述维度时保留失败。自由设计可组合公开能力；玩家明确要求无法等价表达时保留缺口，不省略或用相近机制冒充。不新增检查报告字段，不重写已成立剧情。
<!-- /shared:semantic-preservation -->

- ID 稳定且唯一，只用字母、数字、下划线，并以字母或下划线开头。数值写 JSON number；对象和数组保持原类型。
- effects 对象、数组与合并的作用域见“基础效果”；不按数组长度限制玩法。
- 玩家可见的 `name/description/narrate/source` 必须是自然中文，不暴露 ID、公式路径或字段名。`description` 可省略；填写时必须准确说明何时触发、满足什么条件、实际发生什么，不复述无条件的简单数值标签。含 `when/on/trigger/discard_effects` 或多阶段逻辑时尤其不能把条件收益写成无条件收益。实际结算以结构为准，界面从可执行字段生成权威规则。
- 默认目标、`stacks:1`、`from:"hand"` 和 false 布尔字段可省略。目标会改变含义时显式写 `to:"self"` 或 `to:"opponent"`。数量字段只按下文各操作的契约处理，不存在通用的 `count:1` 省略规则。
- 公式变量与触发时机是闭合白名单。不得自造变量或触发器；不能用零值、空 `effects/trigger` 或只有名称的标记假装实现机制。无法等价表达的明确需求应报告缺口，不擅自换成另一机制。
- AI 直接填写的效果数值与公式常量最多两位小数，便于准确表达 `0.75` 等倍率；运行时保留两位、界面显示最多一位。生命、欲望等 MVU 存档字段仍服从各自的数据精度与范围约束；能量、费用、抽牌、命中和卡牌数量必须为整数。增量语义中的 `energy/lust/resource` 可使用负数表达消耗或降低，`set_hp/set_lust/set_energy/set_block/set_resource` 的公式可越过边界但运行时会夹取到该属性合法范围；伤害量、治疗量、获得格挡量、状态层数、抽弃牌数、命中数、生成数量、容量、槽位和其他计数语义不得为负。MVU 中直接登记的当前值仍必须位于各自合法范围。

## 内容对象

<!-- shared:effect-timing-route -->
| 结算意图 | 结构入口 | 生效范围 |
| --- | --- | --- |
| 当前结算 | 当前内容的 effects | 本次执行；when 只判断条件，不等待事件 |
| 响应事件 | 内容根 trigger、状态 triggers 事件键或姿态 events；弃牌牌面用 discard_effects | 载体实际生效期间；事件筛选不改变载体寿命 |
| 持续改变规则 | 根 trigger.on:passive、状态 triggers.hold 或姿态 passive | 仅 modify/card_rule；不是反复执行即时收益 |
| 预约未来阶段 | 独立 schedule 项，内部 effects | 到期阶段执行；有限重复用 repeat_every 与 repeats |
先按时机选择入口，再按来源、目标和寿命选载体。状态层数不代表等待回合；schedule:0 也须等对应阶段，不表示立刻执行。各载体允许的事件和操作见下文。
<!-- /shared:effect-timing-route -->

卡牌必填 `id/name/type/rarity/quantity`；`type` 只用 `Attack/Skill/Power/Event/Curse`，`rarity` 只用 `Common/Uncommon/Rare/Epic/Legendary/Corrupt`。可选 `emoji/description/dialogue/unique/retain/exhaust/ethereal/innate/sly/lifecycle/discard_effects/creates/trigger`。普通单能量 `cost` 是非负整数，单能量 X 费为 `"energy"`；复合费用见“自定义资源”，只能引用已注册资源。Power 默认打出后消耗；Event 的唯一效果为 `{narrate:"自然中文叙事"}`，不写 `when/on`，其他入口不用 narrate。

### 卡牌生命周期

普通卡打出后弃置；`exhaust:true` 为打出后消耗（本场消耗区，战后恢复持有卡），不是永久删牌。`retain:true` 为回合末保留手牌；`ethereal:true` 为虚无（回合末仍在手中则消耗，优先于保留）；`innate:true` 为固有（优先起手）。`sly:true` 为灵巧：回合结束清理前从手牌被主动或效果弃置时免费打出并完整结算，回合末自动弃牌不触发。Curse 默认保留，Power 默认打出消耗。

需要组合或覆盖默认行为时，可选 `lifecycle`：`on_play` 选 `discard/exhaust/purge`，`on_discard` 选 `discard/exhaust/remove/purge`，`turn_end` 选 `discard/retain/exhaust`。只写需要覆盖的时机；显式值优先于同一时机的旧字段与类型默认。`on_discard:"remove"` 的公开词条名为“遗弃”：任意弃牌（包括回合末自动弃牌）后移出本场战斗，不进入可回收的消耗区，战后原持有卡恢复。`on_discard:"purge"` 的公开词条名为“遗忘”：任意弃牌后永久移除被弃掉的精确持有卡实例，临时副本不影响原卡。`on_discard:"exhaust"` 只是可回收的“弃置消耗”。这些规则不作用于正常打出或预见；主动/效果弃牌先执行 `discard_effects`，卡仍在弃牌堆才执行精确去向。

保留且被弃置后遗弃：`lifecycle:{turn_end:"retain",on_discard:"remove"}`。普通打出不因此移除；回合末仍保留。需要回合末弃牌并触发遗弃则把 `turn_end` 设为 `discard`。模板 `creates` 使用同一规则。

<!-- shared:card-execution -->
需要开场铺设的引擎、形态变化、关键支援牌可主动使用 innate:true（固有），不要只在描述里写起手效果。固有牌战斗开始时优先全部进入手牌，可超过常规起手抽牌数但不能超过手牌上限；超出上限的固有牌留在抽牌堆顶部。是否使用由构筑需要决定，不要求固定数量。战斗中才生成的临时模板不能写 innate。
卡牌可重复持有：名称、类型、费用与可执行规则完全相同的卡（例如同为“斩击”，造成 6 点伤害）优先复用同一稳定 ID、名称和完整定义，以 unique:false 与 quantity 表达份数；每份会成为独立持有实例。构思与已有卡相近、只差小幅数值或换名且不形成有意义玩法差异时，也优先直接选用已有卡的完整规则和名称作为副本，不为微差强造新卡。此条只指导生成选择：程序不会模糊合并已经合法但不同的内容。unique:true 才是单张持有限制，必须 quantity:1，不得改 ID 伪造额外副本；规则、费用或效果确有玩法差异时才必须使用新 ID。召唤物用稳定 slot 限同一召唤者一只，并设计 on_existing_effects 实现重复打出后的加强；群体召唤不设 slot。缺省唯一字段的旧牌保持原语义。
强化须说明实际改变量，例如“使指定卡牌（王剑）造成的伤害增加 3（永久）”，不写“升级一级”。精确定位模板用选择器 id:"稳定卡牌ID"（等同 template_id）；精确定位某张持有卡用已有 run_instance_id，单场副本用 combat_instance_id，不凭空编造实例 ID。from:"combat" 扫描手牌、抽牌、弃牌和消耗区；pick:"all" 自动选中，无需弹窗；pick:"choose" 才手选。
单卡成长示例 {patch_card:"damage",id:"royal_sword",from:"combat",pick:"all",add:3,scope:"permanent",match:"run_instance"}。同名牌包括今后生成的副本用 {patch_card:"damage",name:"小刀",from:"combat",pick:"all",add:2,scope:"combat",match:"filter",future_copies:true}；只限同模板则用 id 和 match:"template"。无需已存在副本也能登记未来强化；run/permanent 范围跨战斗保留。增加打击次数用 patch_card:"hits",add:1；使卡牌对敌方的伤害及欲望攻击变为群体用 patch_card:"area"，不配 add/set/targets。三种可组合，保留非攻击效果的原目标，不修改该卡召唤出的单位或生成牌模板。对召唤物另用 modify_summon_effect 或 persistent_growth,summon_template。
生命周期写在卡牌/模板根部，不是 effects 操作：lifecycle.on_play 选 discard/exhaust/purge，on_discard 选 discard/exhaust/remove/purge，turn_end 选 discard/retain/exhaust；仅写覆盖项。on_discard:"remove" 是“遗弃”，任意弃牌（包括回合清理）后移出本场且不可回收；on_discard:"purge" 是“遗忘”，任意弃牌后永久移除精确持有卡实例，临时副本不影响原卡；on_discard:"exhaust" 只是可回收的弃置消耗。正常打出不算弃牌。sly:true 是“灵巧”：回合清理前被主动或效果弃置时免费完整打出，回合末自动弃牌不触发。旧 exhaust/retain/ethereal/innate 仍可用，显式 lifecycle 按时机覆盖；Curse 默认保留，Power 默认打出消耗。临时牌由 add_card/复制生成，不给持有卡伪造 temporary 字段。
指定召唤在场才可打出的卡，在卡牌根部写 requires_summon:"召唤模板ID"。该字段在扣除能量或资源之前检查；缺失时不能打出，不能把这个门槛写成 effects.when。
卡牌按实际执行方式选类型：Attack/Skill 使用非空根 effects，不写 trigger；已有 discard_effects 也不能代替可打出的根 effects。Event 专用于纯叙事卡，根 effects 必须且只能是一条 {narrate:"自然中文叙事"}，不写 when/on/trigger，也不能混入数值或强化。打出时执行 patch_card、persistent_growth、召唤强化等操作的功能牌通常是 Skill；scope:"permanent" 只表示效果跨战斗保留，不会把卡牌变成 Event 或 Power。Curse 必须省略整个 cost（null 不是省略）；纯不可打出占位牌可同时省略 effects，有实际后果则保留非空 effects/discard_effects，不用 narrate、空对象或虚假零值占位。只靠弃牌等被动后果的不可打出牌属于 Curse，保留真实 discard_effects。
Power 的结构按实际时机三选一：①打出后持续修改规则：根 trigger:{on:"passive",effects:modify/card_rule}；②打出后监听事件：根 trigger:{on:公开事件,effects:即时效果,...事件筛选}；③打出时施加持续状态：根 effects 写 apply_status，已注册状态的 triggers.hold 承担持续规则。同时有根 effects 与 trigger 时，即时部分在打出当下结算，监听器登记后按时机触发。只有 trigger 时省略根 effects，不写空数组；不用 trigger 的 Power 仍需非空根 effects。只有即时伤害、格挡、抽牌、能量或召唤强化的牌应为 Attack/Skill，不能仅凭名称“强化”标成 Power。Power 不支持 battle_start。
passive 只接受持续 modify/card_rule，不接受 apply_status/damage/block/energy/draw 等一次性操作，也不接受 scope/ordinal/n/event/phase/reason/source_kind 等事件筛选。每回合首次或指定事件收益使用对应非 passive trigger。trigger 位于内容根部，不嵌进 effects；modify 的值为属性字符串，不是对象。

`battle.player_lust_effect` 与 `battle.enemy.lust_effect` 只在存在真实欲望施压、积累、读取或转化入口时生成；若生成，都必须有非空中文 `name` 与浅层 `effects`。闭合字段集合固定为必填 `name/effects`，可选 `emoji/description/creates/when`，不得使用任何相似拼写或自造字段。所有操作放在 `effects` 中，不能把伤害、状态或抽牌直接写在顶层；可选的同级 `when` 会作为整个欲望效果的触发条件。满溢通常积累数回合，无论主副轴，兑现须明显超过普通单卡：以同等回合与费用用于直接输出能取得的累计收益为参照，并计入触发后的持续收益，不能只多一点；这是相对衡量，不用固定数值、倍率上限或硬编码终结替代。描述若宣称捕获、失控或其他终局，`effects` 必须使用运行时支持的处决、击杀或等价可执行机制落实结果，不能只有叙事文字。敌人的机制首先服从本轮剧情中的身份、形态、行为与场景，不因含有欲望、诱惑或精神影响主题就强制采用纯欲望流，也不规定欲望压力必须占主要比例。生命伤害、欲望、格挡、控制、自定义状态、能力与牌库干扰可按剧情自由组合；遭遇整体仍应保留至少一条可执行的终局路径，使反复行动能够通过生命伤害、已完整注册的持续伤害，或运行时支持的明确失败推进结束战斗。

欲望上限的强弱方向：谁的欲望满，谁让对手发动欲望效果。因此提高一个角色自己的欲望上限通常是加强其抗性，降低其上限通常是削弱。对我方欲望路线而言，敌方上限越低，越容易满溢兑现、越有利；提高敌方上限通常是敌方强化或我方代价，不能标作我方增益。敌人欲望槽是需要填满的资源，上限不是欲望攻击力。只有明确按欲望上限缩放伤害、消耗或收益的机制可有例外，必须计算净收益并解释方向。只有存在真实欲望体系才生成欲望效果；仅有 lust 数值栏不算体系。只要玩家内容能以可执行结构增加欲望（包括其实际引用的状态、召唤行动或触发器），就必须同时生成完整 `player_lust_effect`；只要某敌人内容能增加欲望，就必须在该敌人对象生成完整 `lust_effect`。未被内容引用的共享状态库条目不据此强制生成。欲望效果在对方满溢时自动触发：`player_lust_effect` 在敌人欲望满时发动，self=玩家、opponent=满条敌人；敌人 `lust_effect` 在玩家欲望满时发动，self=来源敌人、opponent=玩家。绝不把自己满溢写成自己触发自己的效果；不再附加 `lust>=max_lust`、`self.lust>=self.max_lust` 或 `opponent.lust>=opponent.max_lust` 的重复 `when`。欲望是与 HP 并行的完整战斗路线，敌人欲望槽是需要投入费用、卡位和回合才能积累的兑现资源。必须审查整套牌组的积累→满溢→击败敌人闭环；欲望主轴必须能够依靠自己的满溢效果及其后续机制完成输出或终结，不能要求另补普通攻击才算可玩。只给资源、抽牌、治疗或更多欲望而没有可执行输出用途，不构成有效兑现；奖励资源须连接开局已有且可支付的消费入口。可以设计强爆发、持续侵蚀、控制转化、递进终结或资源驱动的原创机制，必须在协议内完整执行；不把成人玩法的欲望体系降格为保守的辅助奖励。估算首次满溢所需回合、每次兑现及最终击败敌人的总投入，纳入敌人欲望上限、重置、抗性、多目标和存活成本；不能用收益名称或循环产出冒充胜利进度。满溢通常耗数回合，兑现须明显超过普通单卡：以同等回合与费用用于直接输出能取得的累计收益为参照，并计入触发后的持续收益；不能只比普通卡多一点。主副轴同样适用，不以固定数值、倍率上限或硬编码终结替代这份投入衡量。仅有额外条件时填写根 `when`，值必须是合法布尔公式；自然语言条件属于说明文字，不是可执行公式。

## 目标与来源

<!-- shared:effect-target -->
普通卡牌、遗物、能力与召唤行动的实体目标默认值：未写 to/targets 时，damage/lust/execute/kill/apply_status/remove_status 默认 opponent，其余支持实体 to 的操作默认 self。self 是当前效果执行者，不固定指玩家；敌人行动的 self 是敌人，召唤行动的 self 是召唤物。牌区操作的 to:hand/deck/discard、召唤 selector.owner 等使用各自契约，不套用这条实体目标规则。
`targets` 省略 team 或写 team:"enemies" 保持旧的正式敌人集合；team:"self"/"opponent" 按实际来源阵营选取存活实体池，角色本体和每个召唤实例都独立参与随机。它只用于能落到实体的基础操作（damage/heal/block、数值池、status 等）；来源身份不会因此变成目标。
| 状态的实际接收者 | 操作入口 |
| --- | --- |
| 当前执行者本体 | apply_status/remove_status，显式 to:self |
| 当前执行者的对方本体 | apply_status/remove_status，显式 to:opponent |
| 由外部效果选中的召唤物 | apply_summon_status/remove_summon_status 的 selector；owner 是阵营，不是角色本体 |
| 召唤行动/能力的具体主人 | summoner_effects 内的效果；不把普通 to:self 当作主人 |
状态施加/移除按实际意图明确写同级 to；buff/debuff、名称和 description 不会纠正目标。Power 也不会因此默认对自己施加状态。
状态定义内部的 triggers 则以精确持有者为 self，省略 to 时作用于持有者；有 targets 时按敌人实体集合契约解析。来源、持有者、目标与说明须一致，注册状态 ID 不等于施加状态。
<!-- /shared:effect-target -->

- 允许反噬、生命代价、援助和控制；这些效果显式写正确的 `to`。如填写中文说明，必须指出实际受影响的一方，不能把伤害一律写成“对敌方造成”。

多敌环境中，在效果对象同级写 `targets` 访问敌人实体集合：`mode` 只用 `active/by_id/all/random/random_n/lowest_hp/highest_hp`。指定实体必须完整写成 `targets:{mode:"by_id",id:"敌人ID"}`，随机多个必须写成 `targets:{mode:"random_n",count:正整数}`；`id/count` 位于 `targets` 对象内部，实体 ID 永远不能写入 `to`。`targets` 存在且省略 `to` 时自动指向当前来源可访问的敌人集合：玩家来源是对方敌人，敌人来源是己方敌群；若显式写 `to`，必须与该集合一致。敌人来源攻击玩家仍以 `opponent` 且不写 `targets`；敌人治疗指定队友可写 `{heal:4,to:"self",targets:{mode:"by_id",id:"队友ID"}}`。随机多段可用 `allow_repeat` 决定同一实体能否重复命中，并用 `retarget:"each_hit"` 表示每段命中前从仍存活实体中重新选靶；省略时在结算开始锁定目标。死亡敌人立即退出后续选靶；全体或随机多段效果只在最后一个敌人死亡时结束战斗。

## 基础效果

基础键：`damage/heal/block/energy/lust/set_hp/set_lust/set_energy/set_block/draw`。字段名必须逐字使用公开键：格挡 `block`、能量 `energy`、欲望 `lust`；不用内部动作名 `gain_block/gain_energy/gain_lust`。

基础抽牌修饰：passive/hold 使用 {modify:"draw_per_turn",add|subtract|multiply|divide|set:数值或合法stacks公式}，只调整玩家开局及每回合自动抽牌，结算时向下取整且至少0；主动draw不受影响，固有牌仍按原规则进入开局手牌。按状态当前层数计算，移除状态即失效；即时draw的负数不是少抽牌，limit_draw是每次抽牌上限，不是基础抽牌增减。

<!-- shared:effect-composition -->
effects 组合：单项写浅层对象，多项写按顺序执行的数组；有先后依赖、不同条件或不同目标时拆项，不依赖 JSON 键顺序。
条件组写 {guard:布尔公式,effects:[子效果]}：进入组时判断一次，成立后依序执行；子项自己的 when 仍在执行该项时判断。用于先判断、再支付与结算收益等依赖链；组不写 to/targets/when/on，目标各归子项。不自动回滚，不改变载体限制；最多嵌套8层，每组1至256项。
合并仅限 damage/heal/block/energy/lust/apply_status/remove_status/draw。合并对象的 when 在组前判断一次，控制整组；显式 to/targets 传给其中每个支持该字段的操作，省略时各操作仍用自身默认目标。合并不建立独立条件或目标。
修饰字段归属：damage_type/bypass_block/lifesteal 仅修饰同项 damage；stacks 仅修饰同项 apply_status。hits 只用正整数，只用于独立 damage 项，不能用于合并对象。bypass_block 仅 true，表示完全无视格挡，不支持指定点数。lifesteal 是按实际生命损失恢复生命的数值倍率或 CEL 数值公式，不是布尔开关；0.5 表示50%，1 表示100%，禁止 true/false。例如 {damage:10,lifesteal:0.5}；伤害完全被格挡时不产生吸血。其余操作各自独占数组项。
<!-- /shared:effect-composition -->

普通效果默认方向：伤害与欲望作用于对方，治疗、格挡、能量作用于自身。状态操作写 `{apply_status:"状态ID",stacks?:层数,to?:目标}` 或 `{remove_status:"状态ID|all|buffs|debuffs",to?:目标}`；ID 是操作值，`stacks/to` 与操作同级，不嵌套进操作值。

### 自定义资源

自定义战斗资源必须先在对应实体的 `resources` 数组注册，再由卡牌或效果引用。资源定义只含稳定英文 `id`、中文 `name`、单个 `emoji`、整数 `start/current/max`、`refresh` 与可选 `end_of_battle`；初次生成可写 `start`，存档运行中以 `current` 为权威，二者同时存在时 `current` 优先。ID 不能是 `energy`，`0<=start/current<=max`，`refresh` 只用 `reset/retain`。不存在的资源不会被隐式创建。

<!-- shared:combat-resource-execution -->
资源 end_of_battle 独立控制战后结余：retain 保留当前值到下一场，reset 在战后恢复 start（省略 start 则为 0）。新资源按设计明确选择；旧存档省略此字段仍保留。此规则不修改每回合 refresh。
资源 refresh 的执行含义：reset 是每回合开始补满到 max，不是归零或恢复 start，第一回合也补满；retain 保留当前量、不自动补充。从 0 逐渐积累并跨回合消费的资源应选择 retain，不应仅凭名称“重置”选择 reset。
资源效果只写 {resource:{id:"资源ID",amount:数值或公式},to?:目标,targets?,when?} 或 {set_resource:{id:"资源ID",value:数值或公式},to?:目标,targets?,when?}。默认目标是自身；amount 为正数是增加，为负数是减少，结果限制在 0 到 max；set_resource 是直接设值，不是增减。amount 只属于 resource 内部以及明确声明 amount 的召唤专用对象。
负数 resource 效果不是出牌费用：资源不足仍可打出，只会扣到 0。若必须支付 N 点资源才能打出，写复合 cost:{energy:能量费,资源ID:N}，不足时整张牌不能打出；费用已经自动扣除，effects 不得重复扣费。若只是可选条件收益，不能擅自改成必付费用；when 在每个效果执行时重新判断当前状态，不会冻结为整张牌的共同条件，描述应准确对应各步。
资源用途：产出须连接真实的支付、公式读取、条件或其他可执行联动，不强制消费。只有产出而无用途不能兑现当前收益承诺；尚未领取奖励或未来剧情的用途须明确为未来依赖。按剧情补齐所需机制，不删除资源或改说明掩盖缺失。
<!-- /shared:combat-resource-execution -->

## 公式与费用

<!-- shared:formula-authoring -->
条件位置：具体操作同级 when，只接受比较或 &&/||/! 布尔条件；不接受 true、数字、自然语言、三元式或 {when,effects} 包装。数值二选一写在操作值中，如 {damage:"self.hp < self.max_hp ? 8 : 5"}；数值效果的三元式可嵌入算式及数值函数，只执行选中的结果一次。
运算：+ - * / %、括号、比较、&& || !、数值三元式。% 为取余，除数不可为0；cards_played_this_turn % 3 == 0 表示本回合每第3张牌。数值函数仅 floor/ceil/abs（各1个数值参数）和 min/max（1..32个数值参数），不用 Math.*、对象方法或其他 JavaScript；公式最多64语法节点、16层，条件展开最多64分支。
弃牌计数：discard_count 表示同一效果序列最近一次 discard 实际移出的卡牌数量；取消或无匹配为0，嵌套触发不覆盖外层结果，新卡/新触发从0开始。例如 [{discard:"all",from:"hand",pick:"all",name_contains:"小刀"},{damage:"discard_count"},{draw:"discard_count"}]。name 是精确同名匹配，name_contains 是名称包含匹配（打击可匹配完美打击）；过滤可结合 id/tag。
全局数值：spent_energy、x_value、turn_number、cards_played_this_turn、attacks_played_this_turn、skills_played_this_turn；spent_resource.资源ID、x_resource.资源ID。出牌事件触发器另可读取 event_paid_energy、event_paid_total、event_paid_resource.资源ID。支付变量的适用位置见“资源与支付”。
实体数值：以下每个路径都须加 self. 或 opponent. 前缀：hp、max_hp、lust、max_lust、energy、max_energy、block；hand_size、draw_pile_size、discard_pile_size、exhaust_pile_size；summon_count、ally_count；buff_count、debuff_count、neutral_count、status_count；status.状态ID.stacks；resource.资源ID.current/max。self 与 opponent 是并列根，不存在 self.opponent 或 opponent.self。HP阈值直接比较 hp/max_hp，不存在 hp_percent 变量。能力本身没有层数；可累积条件使用状态层数。
实体条件：self./opponent. 下的 has_buff、has_debuff、has_neutral、has_status、has_summon、has_ally、alive 是无参数布尔字段，仅用于条件，可直接取值或加 !，不作函数调用。has_buff/has_debuff/has_neutral/has_status 分别检查对应有效状态数量是否大于0；指定状态用 self.status.状态ID.stacks > 0 或 opponent.status.状态ID.stacks > 0。
数量范围：has_summon/summon_count 指所属阵营存活召唤；has_ally/ally_count 指所属阵营其他存活非召唤战斗实体；alive 指该实体 hp>0。“每个召唤物提供N”须按 summon_count 计量；has_summon 只表达有无，不得代替数量缩放，即使当前只有一个召唤物。敌人来源的 opponent 牌区数量就是玩家牌区；无牌区实体的牌区数值为0。
局部上下文：状态触发器额外可用裸 stacks，姿态槽内的姿态额外可用 orb_value；离开该上下文不可读取。伤害事件条件额外可用 event.damage_type，仅与 attack/effect/hp_loss/retaliation/damage_over_time/execute 作 == 或 !=，不用于数值公式。
变量边界：除上方全局数值与适用的局部变量外不使用裸变量；不存在裸 summon_count、ally_count、hp/lust/energy，也不存在 enemy_summon_count、slot_count。效果使用公开操作，不输出通用 if/then、内部 op/steps AST 或自然语言效果。
<!-- /shared:formula-authoring -->

<!-- shared:status-event-condition -->
指定状态的获得、叠层或移除：在对应状态事件的效果 when 中写 event_status_is("状态ID")，只匹配当前 status_applied/status_removed 事件影响的状态。参数必须是一个已注册的稳定状态ID字符串；source_id 表示事件来源，不是被改变的状态。该函数只用于布尔条件，不用于 hold 数值修饰；没有当前状态事件时为 false，后续卡牌和延迟效果不继承旧事件。判断状态当前是否存在则用 self.status.<id>.stacks > 0，不能把“当前存在”当成“本次获得”，也不自造裸 event/source_id/status_id 变量。
<!-- /shared:status-event-condition -->

### 资源与支付

`spent_energy` 表示当前卡牌本次实际支付的能量，固定能量费用与单能量 X 费都可读取。单能量 X 费仍将 `cost` 写成 `"energy"`，只有这种费用可额外读取 `x_value`。复合费用把 `cost` 写成非空资源对象：键为 `energy` 或已经注册的资源 ID，值为非负整数或 `"all"`；含 `"all"` 的组件分别用 `x_resource.<id>` 读取其实际 X 值，任意组件的实际支付量可用 `spent_resource.<id>` 读取。公式读取 `spent_resource.<id>` 时，同一张卡的 `cost` 必须包含同名资源键；读取 `x_resource.<id>` 时，该键还必须写成 `"all"`。`cost:"energy"` 只支付能量，绝不会支付自定义资源；复合费用的能量 X 组件写 `energy:"all"` 并读取 `x_resource.energy`，不能再读取 `x_value`。若效果只按当前资源池数值计算而不消费资源，应读取 `self.resource.<id>.current`，不能假装它是已支付资源。延迟效果、注册后的触发能力、当前姿态和姿态槽内的姿态等脱离当前出牌结算的程序没有支付上下文，不得读取这些值。所有组件一次检查并原子支付，任一资源不足都不得发生部分扣除；Replay 只支付一次。

计数变量包含当前正在结算的牌，并在下一玩家回合归零。

`battle_won/victory/battle_end` 等战后阶段不是 `when` 变量，也不是公开 `trigger.on`。卡牌、状态、遗物或能力不能承诺“战斗胜利后”再执行战斗内效果；胜利后的卡牌、遗物、道具、经验和其他持久变化由战斗结算或节点 `reward` 事务处理。无法用当前战斗公开变量表达的条件不要生成，不能发明裸标识符或空状态标记替代。

状态公式只读取已经注册且由真实效果维护的状态，不用空标记状态代替未公开传感器。召唤的群体强化、激活、伤害、治疗与控制使用召唤 selector；需要其他跨效果数据时，显式注册资源并由真实效果维护。

## 触发与历史

<!-- shared:event-filter-vocabulary -->
事件筛选枚举：trigger.event 与 history.event 使用 turn_started/turn_ended/card_drawn/draw_pile_shuffled/card_moved/card_played/damage_resolved/heal_resolved/lust_increased/lust_decreased/block_gained/block_lost/resource_spent/resource_changed/status_applied/status_triggered/status_removed/stance_changed/orb_channeled/orb_evoked/orb_value_changed/turn_control_changed/summon_spawned/summon_acted/summon_intercepted/summon_defeated/summon_status_applied/summon_status_triggered/summon_status_removed/entity_defeated，不是 trigger.on 的触发名。
phase：before/resolve/after；source_kind：card/relic/status/ability/enemy_action/system/summon/enchantment/affliction；damage_type：attack/effect/hp_loss/retaliation/damage_over_time/execute。
这些是可筛选的记录值，不代表每个记录都有同名公开触发器；trigger 的 event/phase 必须与 on 对应，history 按实际记录筛选。
<!-- /shared:event-filter-vocabulary -->

持续能力统一写结构化 `trigger:{"on":触发时机,"effects":效果}`；若还有即时效果，才另写同级 `effects`。独立玩家/敌人能力填写简短中文 `source`；Power 转化能力由程序自动标注来源。可用触发时机：

`battle_start/passive/ability_gain/turn_start/turn_end/card_played/attack_played/skill_played/power_played/on_discard/on_exhaust/on_draw/on_shuffle/take_damage/take_heal/deal_damage/deal_heal/lust_increase/lust_decrease/deal_lust_increase/deal_lust_decrease/gain_buff/gain_debuff/lose_buff/lose_debuff/enemy_gain_buff/enemy_gain_debuff/enemy_lose_buff/enemy_lose_debuff/gain_block/lose_block/defeated/kill`。

`card_played/attack_played/skill_played/power_played` 触发效果可读取当前这次出牌的实际支付：`spent_energy`（也可写 `event_paid_energy`）为实际支付能量，`event_paid_resource.资源ID` 为指定资源实际支付量，`event_paid_total` 为所有费用组件实际支付量之和；0费、减费、免费组件均按实际值读取，X能量费读取实际消耗，重放不会再次支付。敌人能力也使用同一组变量，例如“玩家每实际支付1能量便赋予1力量”写 `{apply_status:"sts_strength",stacks:"spent_energy",to:"self"}`。它们只读取当前出牌事件，不是卡面基础费用，也不继承到延迟效果。

<!-- shared:trigger-ownership -->
先确定监听内容的持有者，再选择 on 和收益目标；召唤的 take_damage 监听召唤自己受伤，不是主人受伤，scope:"team" 不会扩大事件分发范围。召唤自己的行动、能力及所持状态中，普通 apply_status/remove_status 的 to:"self" 绑定该召唤本身，不是主人或同类召唤群。其他来源要选择召唤时使用 apply_summon_status/remove_summon_status 与 selector；召唤给具体主人效果使用 summoner_effects。
<!-- /shared:trigger-ownership -->

持续、事件和即时效果的放置遵循“内容对象”的共享规则。`on_draw/on_shuffle` 可以抽牌；同一来源的同类触发在自身结算期间不递归重入，只产生本次明确写出的额外抽牌。遗物和能力必填根 `trigger`；道具、敌人行动及双方欲望效果使用根 `effects`，不写 `trigger`。遗物稀有度为 `Common/Uncommon/Rare/Epic/Legendary`；`Boss/ENS` 兼容旧内容；道具 `count` 为正整数；敌人行动 `weight` 为正数。

需要按事件来源或发生次数触发时，使用结构化 `trigger`，其中 `on` 与 `effects` 必填。可筛选的时机是回合开始/结束、出牌与牌区事件、生命/欲望/格挡变化、获得或失去增益/减益，以及 `kill`；`battle_start/ability_gain/defeated/passive` 不写事件筛选。可选筛选字段为 `scope/ordinal/n/event/phase/reason/source_kind/source_id/damage_type/card_type/template_id/card_instance_id/actor_id/target_id`；筛选条件同时满足才触发。`scope` 只用 `turn/combat/run/card_instance/team`；`ordinal` 只用 `first/first_n/nth/every_n`。`first` 禁止写 `n`，`nth/every_n` 必须写正整数 `n`，没有序数规则时不得单独写 `n`。需要限制为每回合首次发生时，应使用回合作用域、首次序数以及与真实事件一致的类型和实体筛选，而不是创建专用触发器或依赖描述文本。回合开始/结束分别对应 `turn_started/turn_ended`，获得状态对应 `status_applied`，失去状态对应 `status_removed`；`kill` 固定 `event:"entity_defeated"`、`phase:"after"`，只在持有者实际击败敌人后分发：玩家持有者只计玩家本体击败，召唤持有者只计该召唤击败；可用 `source_kind/source_id` 等现有字段筛选击杀来源，不能拿死亡者的 `defeated` 冒充击杀。其他事件必须与实际触发时机匹配。事件、阶段、来源种类与伤害种类只能使用程序公开枚举，稳定 ID 筛选必须与事件中真实来源或实体 ID 一致。

精简触发器可省略 `event/phase` 和由 `on` 唯一确定的 `card_type`，它们是程序派生的技术字段。例如每回合首次技能牌可写 `trigger:{on:"skill_played",scope:"turn",ordinal:"first",effects:{energy:1}}`。显式写出时必须一致：出牌、抽牌、主动弃牌、消耗和 `kill` 在 `after` 分发，其余可筛选时机在 `resolve` 分发，没有可用的 `before` 公开触发。序数按真正可触发的事件计数，区分牌型、来源/持有者、状态极性与主动弃牌；`team` 按触发器对应的来源或接收阵营计数。同一张牌的前后两条日志不当作两次出牌。

需要把历史记录作为效果数值时，数值位置可写唯一的 `history` 对象。`metric` 只用 `count/last_damage/last_hp_loss/last_heal/last_resource_spent/last_turn/last_sequence`，并可复用 `scope/event/phase/reason/source_kind/source_id/damage_type/card_type/template_id/card_instance_id/actor_id/target_id` 进行交集筛选。它读取已经提交的权威事件记录，不读取叙事文本，也不把当前尚未记录的结果重复计数。统计出牌数量时明确 `event:"card_played",phase:"after"`，因为底层日志分别保存结算前与结算后；这一历史查询不同于已按真实触发去重的序数监听。`run` 作用域只在宿主明确提供跨战斗历史时生效；普通剧情的独立战斗不得伪造、补写或猜测整局历史。

## 持续规则

持续修饰符和出牌规则只用于 `passive` 能力/遗物或状态 `hold`。`modify` 的值直接是目标属性字符串；目标属性只用 `damage/damage_taken/lust/lust_taken/heal/block/summon_capacity/draw_per_turn`，同一对象再且仅再写 `add/subtract/multiply/divide/set` 中一个。`summon_capacity` 修改所属阵营的当前召唤容量。禁止把 `attribute/operation/value` 对象嵌套进 `modify`；它也不接受 `scope/selector/targets/stat/event` 等额外字段，不存在 `scope:"summon"` 或 `modify:"summon_damage"`。运算量通常直接写有限数值；只有状态 `hold` 可使用只含 `stacks` 与四则运算的公式。持续修饰符绝不能使用 `history`、资源、牌数或其他动态对象；持续规则也不写 `when/on`。

`card_rule` 用于持续替换回合规则。`replay/free` 必须写 `limit`，可为非负整数、合法公式或 `"all"`；`replay` 还必须写正数 `extra`，表示原本结算之外的额外完整结算次数，费用只支付一次且不改变 `hits`；`free` 不写 `extra`，省略 `resources` 或写 `"all"` 时免除全部费用组件，写唯一资源 ID 数组时只免除这些组件，其他组件仍须原子支付。免费组件对应的 X 值为零。`retain_hand/retain_block` 不写 `limit`，分别保留回合末手牌或回合切换时格挡，虚无仍优先结算。`limit_draw/limit_block_gain/limit_energy_gain` 必须写非负 `limit`，用于收紧单次或本回合对应获取上限。`deny_card_play/allow_card_play` 必须用卡牌过滤字段声明范围；允许规则可以解除卡牌类型或其他规则造成的不可打出状态，但不跳过费用与回合终态检查。`limit_card_play` 同时写过滤范围和非负 `limit`，只统计符合过滤器的主动出牌。`card_destination` 写过滤范围、合法 `destination` 与可选整数 `priority`，高优先级覆盖低优先级。持续规则可复用 `name/card_type/rarity/cost/min_cost/max_cost/tag/template_id/run_instance_id/combat_instance_id/origin/upgraded`，不得把一次性卡牌操作伪装成持续规则。`card_rule` 自身不接受 `when/on`；需要按条件存在的持续规则应放进对应状态的 `triggers.hold`，并通过状态的施加、移除与 `stacks_change` 控制生效时间，不能删除条件后改成永久无条件规则。
`card_rule:"ethereal"` 赋予符合筛选的卡牌“虚无”：回合结束仍在手中则本场移入消耗区，优先于保留。敌方存活光环写在敌人 `trigger.on:"passive"` 中并以 `to:"opponent"` 指向玩家；每次结算动态读取所有存活来源，所以赋予者死亡后立即解除，不给卡实例写永久补丁。作用全部玩家卡牌时省略筛选字段。

常见状态可直接引用程序内置 `sts_strength/sts_dexterity/sts_weak/sts_vulnerable/sts_frail/sts_poison/sts_regeneration/sts_metallicize/sts_ritual/sts_thorns/sts_barricade/sts_vigor/sts_artifact/sts_intangible/sts_buffer`，保存时程序会自动展开完整定义。它们主要用于通用小兵与常见数值模板；核心剧情增益、减益和独特机制仍应独立创作并登记完整定义。

`card_rule` 也不接受 trigger 专用的 `ordinal/n/scope/event/phase/reason/source_kind/source_id/damage_type`。`limit` 已经表示每回合匹配的前 N 张，所以“每回合第一张”只写 `limit:1`，不再写 `ordinal:"first"`。

`persistent_growth` 是玩家的永久核心成长独占项：`{persistent_growth:"max_hp"|"max_lust",add|subtract|set:数值或合法公式}`，三个运算字段恰好写一个，不写 `to/targets`。它在本场先立即改变运行时玩家上限，战斗结束后才写回角色核心；普通 `heal/set_hp` 或临时上限效果绝不会因此永久化。召唤的行动、能力和状态中的 `self` 是召唤实例，不能直接使用该操作给主人；确有主人成长时必须显式写入 `summoner_effects`。当前不支持能量上限或其他字段的永久成长。

## 牌区选择与移动

牌区键：`scry/seek/discard/exhaust/recover/reduce_cost/modify_card/patch_card/copy/double`。`from` 可用 `hand/draw/discard/exhaust/all/combat`；`all` 保持为手牌、抽牌堆和弃牌堆的合集，`combat` 才表示含消耗堆在内的四个当前战斗牌区，两者都必须配 `pick:"all"`。`pick` 可用 `random/choose/left/right/top/bottom/all`，数量按字段语义写本体或 `count`。选择器可按 `name/card_type/rarity/cost/min_cost/max_cost/tag/template_id/run_instance_id/combat_instance_id/origin/upgraded/keyword/exclude_keyword/root_only` 过滤；`keyword/exclude_keyword` 只用 `retain/exhaust/ethereal/innate/sly`，可写单值或非空数组，分别表示必须含有全部列出关键词、或不能含有任一列出关键词。例如筛选带“消耗”的牌写 `keyword:"exhaust"`，不能在 `recover/discard` 等另一个操作旁写 `exhaust:true`。`name` 精确匹配可见名称，`template_id` 匹配同模板，`run_instance_id` 匹配整局实例，`combat_instance_id` 匹配当前战斗实例；`root_only:true` 只排除运行时临时复制实例，牌库原实例、生成的根实例和变形后的根实例仍可入选。同名、同模板、整局实例和当前战斗实例必须按实际语义明确区分。约束如下：

- 每个牌区操作必须独占一个 `effects` 数组项，不得与 `damage/heal/block/energy/lust/draw` 或另一项牌区操作写在同一对象；需要组合时按结算顺序拆成多个浅层数组项。
- `discard/exhaust` 的值只能是数量、`"all"` 或合法公式，绝不能写成对象；选择来源与方式使用同一个效果对象中的同级 `from/pick`。主动弃牌即使数量为 1 也必须显式写在 `discard`，不能改写成或省略为 `count`。
- `seek` 只写数量：从抽牌堆选择原卡加入手牌，不触发 `on_draw`。
- `scry` 只写查看数量：可把其中任意张置入弃牌堆，不触发 `on_draw/on_discard`。
- `recover` 只从 `discard/exhaust` 取回，`pick` 只用 `random/choose/all`。
- `left/right` 只用于手牌，`top/bottom` 只用于有顺序的牌堆；`from:"all"` 与 `from:"combat"` 都必须配 `pick:"all"`。跨牌区保持手牌、抽牌堆、弃牌堆、消耗堆的稳定顺序；没有合法目标时效果安全完成，手动选择可取消且不得产生部分修改。

跨牌区移动、移出战斗和变形分别使用独占数组项 `move_card/remove_card/transform_card`。`move_card` 的值是数量或 `"all"`，同层必填 `destination:"hand"|"draw"|"discard"|"exhaust"`，可写 `position:"top"|"bottom"` 与选择字段；`remove_card` 的值是数量或 `"all"`，表示只从当前战斗移除选中的实例；`transform_card` 的值必须引用同一内容对象 `creates` 中已经定义的模板 ID，并用同层选择字段确定原卡。三者都保留稳定实例与来源记录，不得用直接改写长期 `battle.cards` 模拟战斗中的牌区操作。

`choose/options` 只用于让玩家从 2..8 个预先写好的不同效果分支中选择一项，固定写成 `{choose:"稳定英文ID",options:[{id,label,effects},...]}`；每个选项必须有互不重复的稳定英文 `id`、非空 `label` 和非空浅层 `effects`。它不用于选择牌区中的卡牌。从手牌、抽牌堆、弃牌堆或消耗堆选择一张牌去弃掉、取回、复制、强化或自动打出时，应在对应牌区操作同级写 `pick:"choose"`、`from`、数量与筛选字段，不能另写 `options`。

## 卡牌修改与附着

`modify_card` 用于修改所选卡牌的可执行数值。其值只用 `damage/block/lust/stacks`，并且恰好搭配 `add/subtract/multiply/divide` 中一个；同对象使用 `from/pick/count` 选择卡牌，默认从手牌选择一张。修改只作用于伤害、格挡、欲望或施加状态的层数，不得改变 `hits`、费用、目标、触发时机或卡牌类型。一次修改会作用于该卡牌中对应数值通道的全部步骤；若需区分不同步骤，应把规则设计为不同卡牌或不同结算入口。

`patch_card` 用于带明确生命周期的通用卡牌补丁。它的值必须直接是 `damage/block/lust/stacks/cost/dynamic_cost/x_value/replay/hits/area/retain/exhaust/ethereal/innate/sly` 之一的字符串；运算字段、布尔字段、`scope/from/pick` 与全部筛选字段必须和 `patch_card` 处在同一层。`cost` 用固定数值配 `add/subtract/multiply/divide/set/min/max`；`x_value` 用同样的数值运算调整卡牌结算时使用的 X 值；`dynamic_cost` 还必须同层提供 `timing:"on_draw"|"while_in_hand"|"on_play"` 与一个运算字段，可选 `minimum/maximum`。严禁把补丁类型、运算或选择器包进 `patch_card:{...}`，也严禁使用 `patch_card:{字段:{运算:数值}}` 的嵌套形状。数值、费用、关键词和额外结算分别使用各自合法的运算或布尔字段。`scope` 只用 `resolution/turn/until_played/combat/run/permanent`，`match` 只用 `instance/run_instance/template/filter`，省略 `match` 时固定为当前 `instance`。只有模板或过滤器范围可以启用 `future_copies`。补丁必须记录来源，并在对应结算、回合、出牌、战斗或整局边界自动移除；禁止通过直接覆写卡牌字段模拟持续时间。复制与变形只按补丁作用域和正负修饰类别继承，不得把临时费用或本次结算修正意外写回长期牌组。
敌方行动令玩家所有攻击牌本场费用 +1 可直接写 `{patch_card:"cost",add:1,scope:"combat",match:"filter",future_copies:true,card_type:"Attack",from:"combat",pick:"all"}`；`from:"combat"` 包含消耗区，`future_copies:true` 也覆盖之后生成的匹配牌。

卡牌永久或整局成长使用独占数组项 `upgrade_card`，其值是要升级的数量或 `"all"`，不能写成对象；同层必填非空 `changes`，可选 `levels/max_level/scope` 与牌区选择字段。`scope` 只用 `combat/run/permanent`。每项变化固定使用 `kind` 区分 `numeric/cost/keyword/replay/hits/area/x_value/dynamic_cost`，再填写该种变化要求的 `stat/operator/value`、`keyword/enabled`、`extra` 或 `timing`；升级等级和实际变化必须同时存在，不能只增加等级标签却不改变可执行卡牌。

卡牌本体的攻击次数成长只用 `upgrade_card.changes:[{kind:"hits",add:正整数}]`，建议配 `scope:"run"|"permanent"` 与明确 `max_level`；它只给该卡每个原有 damage 命中组增加攻击次数，抽牌、格挡、状态、生成等同卡副作用仍只结算一次，绝不能改用 `replay`。没有本卡 damage 的目标不会获得此成长；召唤行动、召唤能力和模板 damage 不属于卡牌本体，不能借此强化。次数始终受程序每组上限约束，不承诺任意属性无界增长。

需要把一组卡牌变化作为一个有名称、来源和统一生命周期的整体时，使用独占数组项 `attach_card`。其对象必填稳定 `id`、`kind`、中文 `name`、`scope` 与非空 `changes`；`kind` 只用 `enchantment/affliction`。可选 `description/emoji/remove_on/remaining/discard_reasons/priority`。同一张卡至多拥有一个 enchantment，但可拥有多个不同 affliction；整个附着包必须原子添加、统一倒计时和统一移除，不能把包内变化拆成互不关联的补丁。`changes.kind` 可用 `numeric/cost/keyword/replay/hits/area/x_value/dynamic_cost/play_access/discard_auto_play`，前六项沿用对应卡牌补丁字段；`play_access.mode` 只用 `deny/allow`；`discard_auto_play` 必填 `reasons`、`failure_destination` 与 `only_player_turn`。`remove_on` 只用 `resolution_end/played/discarded/turn_end/combat_end/run_end/manual`；`scope:"resolution"` 省略时固定在当前最外层效果程序结束时原子移除，仅在 `remove_on:"discarded"` 时可写 `discard_reasons`。run/permanent 附着会随长期卡牌写回，临时复制、持久复制和变形只按既定继承策略保留附着，不得把战斗期 affliction 意外永久化。

所有牌区移动都带内部原因日志，但只有 `player_choice/random_effect/effect` 三种表示真实手牌弃牌，可用于 `discard_auto_play.reasons` 和 `remove_on:"discarded"` 的 `discard_reasons`。`discard_auto_play` 只有在卡牌确实从手牌进入弃牌流程、当前原因列入 `reasons` 且满足玩家回合限制时才免费自动打出；从抽牌堆移动、预见、回合清理、消耗、生成、复制、变形、自动出牌或敌方阶段都不会被笼统视为弃牌。自动打出失败时按 `failure_destination` 原子落入 `discard/exhaust/draw_top/draw_bottom/hand/remove`，并保留完整原因日志；不得用 description 模拟弃牌触发。

## 模板与生成牌

动态插牌在内容对象同级写 `creates` 模板数组；效果用 `add_card` 引用模板 ID，`to` 只用 `hand/deck/discard`，默认 hand，`count` 为正整数。`discard` 表示新实例直接进入弃牌堆，不算从手牌弃掉，也不会触发 `discard_effects`。模板只使用 `id/name`，以及可选 `emoji/type/rarity/cost/description/dialogue/effects/discard_effects/retain/exhaust/ethereal`；只有 `type:"Power"` 的模板可额外写根 `trigger`，Attack/Skill/Event/Curse 模板一律不写 `trigger`。模板绝不写 `quantity/tags/innate` 或嵌套 `creates`，实际数量只由 `add_card.count` 或 `ensure_card.minimum` 决定，也不得循环生成；模板内部不能用 `add_card/ensure_card` 引用自身，因为模板没有第二层 `creates` 容器。敌人行动和能力同样可用 `creates + add_card` 向玩家手牌、抽牌堆或弃牌堆加入主题临时牌、妨碍牌或诅咒牌；这些牌只属于本场战斗。

临时牌模板沿用“内容对象”的类型、稀有度与执行规则，不另设 `Special/Token` 稀有度；Curse 模板省略整个 `cost`，`cost:null` 也不是省略。模板的字段范围、引用位置和生成数量遵循本节，不按正式卡牌补 `quantity`。

`ensure_card` 用于保证某个 `creates` 模板在当前战斗中的根实例至少达到 `minimum`，`minimum` 为 1..100 的整数；`to` 只用 `hand/deck` 并默认 hand。计数固定扫描手牌、抽牌堆、弃牌堆和消耗堆，已经消耗的根实例仍满足数量，不会因离开手牌而重复生成。默认省略或写 `include_copies:false`，使临时复制实例不计入根实例数量；只有规则明确要求复制品也计数时才写 true。数量不足时只补足差额并生成新的当前战斗实例，不增加长期牌组；目标为手牌但手牌已满时，新增实例按统一溢出规则进入弃牌堆。新实例从 `creates` 的基础模板生成，不继承此前登记给未来模板或未来副本的补丁。

需要在确保实例后立刻强化本场现有根实例时，把 `ensure_card` 与后续 `patch_card` 写成按顺序结算的两个独立效果项。后者使用 `from:"combat"`、`pick:"all"`、同一 `template_id` 与 `root_only:true`，并省略 `match` 以采用默认 `instance` 匹配；每个当前根实例分别获得实例补丁，刚补出的实例也会在同一轮被选中。该组合不写 `future_copies`，不会修改 `creates` 模板、长期牌组、临时复制品或之后才生成的副本。

## 自动出牌与重放

从非手牌区自动打出使用独占数组项 `auto_play`，值为正整数或 `"all"`；同级复用 `from/pick` 与卡牌过滤器，默认从抽牌堆顶部选择并免费打出，只有确实要支付原费用时才写 `free:false`。自动打出仍完整执行卡牌、单卡 Replay、事件、触发器和最终牌区移动，但不消耗“每回合前若干张主动出牌”的规则窗口。卡牌需要改变自身结算后的去向时使用独占数组项 `card_destination`，值只用 `discard/exhaust/draw_top/draw_bottom/hand/remove`；该操作只在正在结算的卡牌中有效。不要以复制效果、先移动再伪装出牌或直接改写牌堆代替这两个原语。

当前这张非 Power、非 Event 卡要在本次打出中再次完整结算，使用独占数组项 `{replay_current:正整数或合法数值公式,when?:条件}`。条件只写在 `when`，`replay_current` 不写三元式；例如“本回合打出过技能牌则重放一次”固定写 `{replay_current:1,when:"skills_played_this_turn > 0"}`，不能再把同一条件写成 `replay_current:"skills_played_this_turn > 0 ? 1 : 0"`。它先让当前牌的整段原效果正常执行完毕，再额外完整结算指定次数；费用只支付一次，重放沿用第一次实际支付的资源和 X 值，每次重放都会产生正常的出牌事件并触发对应的卡牌、状态、遗物与能力联动，最终牌区移动只发生一次。由 `replay_current` 产生的重放再次执行到 `replay_current` 时不会继续追加次数，并受统一安全上限约束。该操作只允许出现在当前卡牌的直接主效果中，不能放进 Power、Event、`trigger`、`discard_effects`、状态、遗物、能力、敌人行动、召唤行动或预约效果；这些脱离当前牌的入口没有可重放对象。不要写 `{replay:true}`，也不要用重复伤害、`double`、`patch_card:"replay"` 或 `card_rule:"replay"` 替代：`double/patch_card` 改的是选中卡牌之后的结算次数，`card_rule` 改的是持续规则，只有 `replay_current` 表示“这张牌现在完整再结算”。

## 特殊战斗容器与回合控制

需要预约未来效果时使用独占数组项 `schedule`，其值是等待的非负整数回合数；同级 `phase` 只用 `turn_start/before_draw/after_draw/turn_end`，`effects` 写届时执行的浅层效果。持续预约必须同时写正整数 `repeat_every` 与 `repeats`，分别表示间隔和总执行次数；可选整数 `priority` 决定同一时点的稳定顺序。预约效果保存来源并随战斗存档，错过到期回合时在下一个相同阶段补执行一次；失败会整体回滚并保留待重试项。不要用立即生效的状态、虚假回合数字或叙事描述冒充预约执行。

`stance` 用于进入一个互斥姿态，值为 `null` 时退出当前姿态；非空对象必填稳定 `id/name`，可写中文 `description`、单个 `emoji` 与 `enter/exit/passive`。进入和退出效果各只在真实切换时执行一次；重复应用同一 ID 不刷新也不重复触发。`passive` 只能包含 `modify/card_rule` 持续规则，不能放即时伤害、治疗、抽牌或资源获取。玩家来源默认修改玩家姿态，敌人来源默认修改该敌人；多敌玩家效果可用 `targets` 选择具体敌人。

`channel_orb` 用于向目标的有序姿态槽右端充能姿态，必填稳定 `id/name` 与非负 `value`，可写中文 `description`、单个 `emoji`、`passive/evoke`。姿态槽已满时先移除并激发最左侧姿态，再加入新姿态；`passive` 在持有者对应回合结束阶段按从左到右结算，`evoke` 在主动激发、满槽挤出或缩减姿态槽溢出时结算。两者公式额外可读取 `orb_value`，每个姿态维护独立数值和来源。它与 `stance` 的当前互斥姿态是两套独立机制。

`evoke_orb` 的值本身就是激发数量，只写正整数或 `"all"`；正整数可配 `pick:first/last`，`"all"` 只能省略 `pick` 或配 `pick:all`，不要再写重复的 `count`。可用稳定 `orb_id` 先过滤姿态。`orb_slots` 把目标姿态槽设置为 0..20 的整数或合法公式，缩小时溢出的姿态按原槽位顺序激发。`modify_orb:"value"` 必须且只能配 `add/subtract/multiply/divide` 之一，并用 `pick/count/orb_id` 选择目标姿态；除数不能为 0，结果不小于 0。

`extra_turn` 写正整数或合法公式，为 `to` 所指一方排入额外完整回合；玩家额外回合会跳过本次敌方阶段，敌方额外回合会重复完整敌方阶段，并保持多敌稳定行动顺序。`end_turn:true` 请求强制结束 `to` 所指一方当前回合；结束敌方回合会中止尚未行动的敌人队列。终态优先于额外回合，所有队列和请求都必须随战斗快照保存并在失败时整体回滚。

入战时已经存在的容器可写在 `battle.core` 或每个敌人对象中：`stance` 是上述当前互斥姿态；`orb_slots` 为 0..20 整数；`orbs` 是不超过姿态槽数量的有序姿态数组。初始姿态的 `value` 必须是具体非负数值，公式只写在其 `passive/evoke` 内。不要把战斗运行中的当前容器状态持续写回 MVU。

## 召唤单位

时效：`modify_summon_effect` 改写现有行动与能力，攻击后或回合结束不会自动恢复；固定效果除外。一次执行不等于只生效一次。仅下次或本回合强化须另有可执行的次数消耗或到期恢复，不能只写该操作，也不能删改时效承诺掩盖缺失。它只成长本场召唤实例，不修改长期卡牌模板或后续生成的模板；永久卡牌成长必须走卡牌自身的持久成长规则。

召唤单位只由效果中的独占数组项 `spawn_summon` 产生并保存在本场战斗快照；变量模型不得创建或回写 `battle.summons`。外层 `to` 决定召唤归属并默认 `self`。定义必填稳定英文 `id`、中文 `name` 与单个 `emoji`。省略 `has_hp` 时视为有生命单位并必须填写正数 `max_hp`；写 `has_hp:false` 时省略 `max_hp`，该单位不显示生命、不会受伤或治疗，也不参与援护。可按需写中文 `description`、非负 `block`、稳定英文 `tags`、`resources/modifiers/actions/abilities`、`actions_per_activation/action_priority/speed`、`intercept/slot/on_existing/on_defeated/retain_corpse/capabilities`，以及生成控制 `count/capacity/overflow`。公开生成只使用 `actions` 数组，即使只有一个行为也必须写数组；旧存档中的单数 `action` 仅由运行时兼容读取，AI 不得生成。每项行动必填稳定英文 `id`、中文 `name` 与非空 `effects`，可写单个 `emoji`、中文 `description`、正数相对 `weight`、同层 `when`，以及仅供该行动引用的 `creates` 卡牌模板；单位入场及正常行动结算后按权重预定下一次行为并保存，执行使用已预告行为；`when` 作为该次效果整体的执行条件。`abilities` 与普通能力使用相同的结构化 `trigger` 和效果契约，但不使用 `passive`，持续修饰改写在召唤自己的 `modifiers` 或持有状态中；其中 `self` 始终是该召唤实例，一个召唤可以有多个互不覆盖的触发能力，能力也可用自己的 `creates`。`deal_damage/deal_heal` 等来源本地事件由真正造成效果的实体接收：玩家能力只响应玩家本体，召唤能力只响应该召唤。需要“召唤造成伤害后让召唤者获益”时，应把对应 trigger 写在召唤 ability 上，再用 `summoner_effects` 把收益交给召唤者；不能在玩家 Power 或遗物上用 `source_kind:"summon"` 冒充跨实体监听，也不能创建空状态标记模拟这一事件。行动或能力写 `fixed:true` 时，其数值不受召唤效果强化，应用于每回合固定资源等不应随构筑膨胀的效果；其他行动与能力可以被统一强化。`actions_per_activation` 为 0..20 的整数，顺序先按整数 `action_priority` 从高到低，再按整数 `speed` 从高到低，最后按创建顺序与同一单位的行动序号。单位在轮到行动前死亡时跳过其剩余队列。

普通多召唤不写 `slot`，同一模板可以产生独立实例。我方基础召唤容量为 3，敌方默认无容量上限，可由能力、遗物或状态的 `summon_capacity` 持续修饰符提高，不设固定总上限；舞台会按创建顺序使用多层环绕布局。`capacity` 是可选的本次效果基础容量；省略时使用所属方默认值，敌方只有显式设置时才受这个容量限制；`overflow` 只用 `reject/replace_oldest/replace_lowest_hp`。超过当前容量时默认由新单位挤掉创建最早的存活单位，被挤掉者按被击杀处理并正常触发 `defeated`。需要所属阵营内唯一槽位时才写稳定英文 `slot`：槽内已有存活单位时，`on_existing` 只用 `reinforce/replace`；槽内只有已保留的倒下实例时，`on_defeated` 只用 `new_instance/revive_reset/revive_reinforce`。两种策略都必须与 `slot` 同时出现；`retain_corpse` 决定倒下后是否保留可寻址记录。不要把普通多实例与唯一槽位策略混写。

召唤选择器固定为 `selector` 对象，并由所有召唤专用操作复用。`owner` 相对于当前效果来源，只用 `self/opponent/any`；`pick` 优先使用 `left/right/random/random_n/choose/all/lowest_hp/highest_hp/by_id/source`，旧内容的 `first/last` 仅作为 `left/right` 兼容别名。`left/right` 按稳定创建顺序选择最早或最晚入场者，不依赖屏幕瞬时坐标；`choose` 由玩家手动选择且不允许程序偷选第一项；`random_n` 配正整数 `count` 随机选择多个不重复目标。`source` 只选当前召唤行动、能力或状态触发的那一个召唤实例；没有该召唤来源上下文时不选任何单位。例如召唤自己的 `on_shuffle` 触发用 `{modify_summon_effect:{selector:{pick:"source"},stat:"damage",add:1}}` 才只强化本只，不能因同模板而强化全部。还可用 `id/template_id/tags/slot` 过滤；`by_id` 的 `id` 是运行时实例 ID，模板筛选必须用 `template_id`。最低或最高生命只在有生命单位中按当前生命比例判断；默认只选存活且可选择的单位。只有明确控制不可选槽位单位时才写 `include_untargetable:true`，不得用它扩大普通群体效果。

召唤专用操作各自独占一个效果数组项：`damage_summon/heal_summon` 使用 `selector/amount`，无生命目标会安全跳过；`modify_summon` 使用 `selector/stat` 并且恰好一个 `add/subtract/multiply/divide/set`，`stat` 只用 `max_hp/block/actions_per_activation/speed/action_priority`；`modify_summon_effect` 使用 `selector/stat` 与恰好一个 `add/subtract/multiply/divide`，`stat` 只用 `damage/block/lust/stacks`，同时修改所选召唤的非固定行动和全部非固定触发能力；两类除数都不能为 0。两种修改操作都在执行当下修改已经被 `selector` 选中的现有召唤，不会自动影响未来召唤，也绝不能放进 `passive` 或状态 `triggers.hold`；需要在状态获得或叠层时强化现有召唤，可放入该状态的 `triggers.apply/stack`。`summon_resource/set_summon_resource` 使用已在该召唤定义中注册的资源 ID；`apply_summon_status/remove_summon_status` 只能引用 `battle.statuses` 中已注册的状态 ID。普通 `apply_status` 固定以状态 ID 字符串为值，不能在值内嵌 `id/stacks/targets`，也不能用 `targets` 选召唤；从其他来源选择召唤施加状态使用独占项 `{apply_summon_status:{selector,id,stacks?}}`，召唤自身的普通状态操作按上文持有者规则执行。`activate_summon` 立即按稳定队列行动；`dismiss_summon` 可用 `retain_corpse` 决定是否保留倒下记录并正常触发离场能力；`copy_summon` 使用同一 `selector`，可用 `to:same/self/opponent` 决定复制体阵营，并可写 `capacity/overflow`。复制保留目标当前生命、状态、资源、行动、能力、固定标记和已获得强化，但分配新的实例身份与入场顺序。没有合法目标时安全完成，不隐式改为战斗实体或其他召唤。

召唤的 `resources` 是以资源 ID 为键的对象，键本身就是资源 ID；每个值只写中文 `name`、单个 `emoji`、正整数 `max`、`refresh:"reset"|"retain"`，以及 `start/current` 至少一个，不要在值内重复写 `id`。初次生成优先写 `start`，载入后统一转为 `current`。`modifiers` 只用 `damage_modifier/damage_taken_modifier/lust_damage_modifier/lust_damage_taken_modifier/heal_modifier/block_modifier` 的有限数值。召唤行动和能力中的普通 `self` 精确表示当前召唤实例，`opponent` 表示其所属阵营的对方；改变其他召唤实例的生命、格挡、状态、资源、行动参数或效果数值时必须使用上述召唤专用操作。只有明确要让召唤者本体获得效果时，才用独占效果项 `summoner_effects:[...]` 包裹非空的普通效果数组；该数组内的 `self` 改为召唤者本体，`opponent` 仍为对方阵营。不得用普通 `self` 猜测或替代召唤者，也不得嵌套 `summoner_effects`。召唤行动可按多敌规则使用 `targets` 选择敌人。

无生命常驻单位可以用普通行动或触发能力表达有序容器式玩法：其持有期间效果、主动行动、离场能力与召唤物数值强化都沿用上述通用结构；需要为召唤者增加能量、格挡、状态或自定义资源时使用 `summoner_effects`。每回合固定增加资源、固定姿态槽经济或其他不应随召唤强化增长的数值必须在对应行动或能力上写 `fixed:true`；可成长的伤害、格挡、欲望和状态层数才省略 fixed。不要因为存在独立姿态槽容器就拒绝生成这种召唤玩法，也不要把召唤运行时状态写回长期 MVU。

有生命召唤默认参与援护，不必显式写 `intercept`；普通攻击以召唤者本体为原始目标，先计入本体易伤等承伤增益，再按最早创建顺序由召唤单位承接；减伤与格挡按实际承伤者结算，不提前消耗本体格挡或套用本体减伤。召唤单位减伤、格挡与生命结算后的过量伤害继续援护或回到本体，回到本体时才结算本体减伤和格挡。例如攻击10、本体易伤50%、召唤物减伤2，召唤物承伤13。常规状态的原始目标仍为本体，不随攻击援护转移。敌人的普通单体攻击不会因为援护自动变成群体攻击。需要改变援护顺序或限制次数时才写 `intercept`，其中只支持 `mode:"unblocked_attack"`，可写整数 `priority` 与正整数 `max_per_turn`；显式优先级高者先于默认顺序。无生命召唤、生命流失、直接设值与非攻击效果不参与援护。`capabilities` 的 `selectable/accepts_status/acts/intercepts` 都是布尔策略，分别控制普通选择、接收状态、自动或立即行动和援护；关闭一项不会暗中关闭其他能力。

## 敌方被动、增援与形态分裂

- 单敌遭遇写 `battle.enemy` 并清空 `battle.enemies`；多敌遭遇写 `battle.enemies` 并清空 `battle.enemy`。每个敌人必须有唯一稳定 `id`，完整携带自己的生命、欲望、行动、能力与活动状态。只有剧情明确存在多个同时参战实体时才使用多敌，不为展示机制强行拆分敌人，也不提前登记旁观者或尚未入场的增援。
- 剧情已经明确同族、上下位、进化体或同一组织制式时，可填写稳定 `family_id`、中文 `family_name` 与中文 `evolution_stage`；没有明确关系时全部省略，禁止只凭名字猜谱系。已知谱系优先复用 `battle.design_context.lineage` 中至少一个招牌行动或核心状态，再增加符合当前位阶的新机制；复用是连续性，不要求复制全部旧数值。
- 多敌的行动顺序先按整数 `action_priority` 从高到低，再按整数 `speed` 从高到低，最后按 `battle.enemies` 中的稳定站位顺序；两项省略时都按 0。已死亡敌人在行动前退出队列；玩家死亡后其余敌人停止行动。活动目标死亡后切到仍存活的最前实体，默认 `targets.mode:"active"` 始终只处理当前活动目标。不要依赖随机数组顺序表达先后。

敌人的 `abilities` 是与玩家遗物等价的独立被动区，同一敌人可以拥有多个被动。每项必须使用不同稳定英文 `id`、中文 `name/source`（`description` 可省略）、合法结构化 `trigger` 与非空效果；界面会逐项显示和展开。被动数量与联动只服从剧情和可玩性，不要求每个敌人复杂，也不能把多个不相关规则塞进一个能力或用一个描述冒充多个效果。

`defeated` 在该实体生命归零后、从敌人集合移除前触发，可用于退场结算、复活、增援或形态变化。若效果恢复了该实体生命，实体继续留场；否则触发完成后才移除。退场效果不得直接宣告胜负，战斗只在所有独立敌人都离场后结束。

`kill` 属于实际击杀者的触发：目标死亡后的 `entity_defeated/after` 才分发，可按 `source_kind/source_id` 精确限制来源；不要把击杀奖励写进死者自己的 `defeated`，也不要用名称或叙事文字冒充击杀归属。

需要在战斗运行中加入新的独立敌人时，使用独占效果 `spawn_enemy`，固定形状为 `{spawn_enemy:{完整敌人字段...,count?:数量,capacity?:场上容量}}`。`count/capacity` 属于 `spawn_enemy` 的值对象内部，禁止写成 `{spawn_enemy:{...},count:1,capacity:3}` 的外层同级字段。生成对象必须完整包含稳定 `id`、中文显示字段、当前与最大生命/欲望、非空 `actions` 数组、行动模式，以及闭合且非空的 `lust_effect:{name,effects}`；`abilities/status_effects` 仅在实际需要时填写。每个生成实例自动获得不冲突的运行时 ID，独立拥有生命、状态、意图、行动顺序和被动，可被单体、随机或群体目标正常选中。前排最多五个，超出的敌人进入候补；候补不可选中，不受战斗伤害和状态影响，也不预选意图，上场后才参与战斗。省略 capacity 时没有隐含的12人容量；显式容量计入存活前排与候补。内容设计应避免巨量或无界递归增援。

`spawn_enemy` 与 `spawn_summon` 语义不同：前者进入正式敌人集合并参与胜负判定、目标选择和敌方行动队列；后者属于阵营附属召唤容器。正文尚未实际入场的增援或分裂形态不得预先写进 `battle.enemies`，应由已经在场实体的行动、状态或被动在真实触发时生成。世界书和变量输出只写通用结构，不为某个具体敌人预设名称、数值或固定机制。

## 自定义状态

程序没有内置状态。引用任何状态 ID 前，先读取当前 `battle.statuses`：已有定义只复用，不存在则在首次引用前用 `_.assign('battle.statuses', 完整定义)` 注册一次。容器固定为数组，禁止按 ID 写对象。输出前核对所有 `apply_status/remove_status`、状态公式、双方 `status_effects` 和活动状态引用；除 `all/buffs/debuffs` 外，每个 ID 必须已存在或在本轮注册。

定义必填 `id/name/emoji/type/triggers`，`type` 只用 `buff/debuff/neutral`。生命周期键为 `apply/stack/tick/remove/hold/threshold_execute`；状态持有期间还可直接监听这些战斗事件：`battle_start/ability_gain/turn_start/turn_end/card_played/attack_played/skill_played/power_played/on_discard/on_exhaust/on_draw/on_shuffle/take_damage/take_heal/deal_damage/deal_heal/lust_increase/lust_decrease/deal_lust_increase/deal_lust_decrease/gain_buff/gain_debuff/lose_buff/lose_debuff/enemy_gain_buff/enemy_gain_debuff/enemy_lose_buff/enemy_lose_debuff/gain_block/lose_block/defeated/kill`。每个触发值直接是非空浅层效果对象或数组，不再包 `effects`、`{on,effects}` 或 `{when, effects}`；其中仍只能使用上述公开浅层键，不得改写为内部动作名或嵌套修饰符对象。数组各项的 when 在执行到该项时重新判断，不是事件开始时的快照。共享条件仅在前序效果及其触发联动不会改变条件真假时才能逐项复制；有支付、状态移除或其他依赖时，必须保留判断时机和先后关系，不能机械展开。一次判断后顺序执行使用 guard 条件组，见组合契约；必须保留原组边界及子条件，不删除条件或收益。事件值不能只剩 `when`，也不能为通过校验而删除原操作。仅有衰减或眩晕时可让根 `triggers` 为空对象；绝不能注册值为空对象或空数组的子触发器。可选：

- `stacks_change`：数字、`"x0.5"`、`"reset"` 或 `"keep"`
- `maxStacks`：正数
- `stun:true`：令持有者无法行动，寿命按下方眩晕规则设计
- `creates`：至多 32 项临时牌模板；非 `hold/threshold_execute` 触发器可通过 `add_card/ensure_card/transform_card` 引用该状态自身模板，不能借用施加状态的卡牌或遗物的模板。若使用 registry 草稿，只在 `registry.templates` 定义一次，程序按真实引用编译到状态自身。生成牌不立即执行其效果，模板不能循环生成，也不能读取创建状态的 `stacks` 上下文。
- `description`：可选中文表现；填写时准确说明触发时机、条件与结果，不代替实际机制

<!-- shared:status-execution -->
人物外观：状态可选 character_emoji（1..32字符），仅在持有正层数期间替换持有者人物emoji；AI生成的变身状态优先用character_emoji明确外观，而不是把状态自身emoji误当人物外观；多个外观状态以最后获得且仍持有的为准，再次叠层不改变优先级，移除/到期/战斗清理后恢复其他仍有效外观或原人物emoji。状态自己的emoji仍是状态图标，不能推断为人物外观。Power、遗物、独立能力可通过apply_status赋予这种外观状态，寿命仍由状态的可执行移除/衰减控制，不得只在描述中声称变身。
状态载体：hold只承载持续modify/card_rule；apply/stack/tick/remove及事件键只承载一次性effects。监听事件直接用triggers的对应事件键，不能嵌入hold；不存在card_rule:"energy_gain"或modify:"energy"。
获得与叠加：首次获得正层数只触发apply；已持有且层数实际增加只触发stack，两者互不代替。零增长或达到上限不触发stack。若要求首次获得和再次叠加都有收益，必须分别实现对应入口；不能只写stack却说明为每次获得。
状态筛选：事件键不接受scope/ordinal/n/event等结构化筛选。首次、第N次或来源筛选优先使用Power、遗物、独立能力或召唤ability的根trigger；scope:"turn"仅重置计数，不改变内容寿命。全牌、攻击、技能计数分别为cards_played_this_turn、attacks_played_this_turn、skills_played_this_turn，不可混用；计数条件不代替事件监听。
状态上下文：省略to作用于精确持有者，opponent为其对方；玩家、具体敌人、具体召唤不能互相冒充。公式可读取裸stacks及通用变量；伤害事件when可用event.damage_type与attack/effect/hp_loss/retaliation/damage_over_time/execute作==或!=比较，不用于数值公式，不读取未公开的amount/damage。
状态监听：仅在实际持有期间响应。事件开始冻结已有状态，本事件中新获得的状态不追溯响应；其apply/stack造成的新事件可正常响应。移除后立即停止。同一持有者的同一状态不会递归重入自己正在结算的同名事件；不同状态和不同事件仍按顺序结算。
状态 tick：triggers.tick只在持有者自身行动边界执行；根tick_timing可为before_action或after_action，省略默认before_action。每个敌人/召唤按自己的行动前后结算，玩家在自己的行动期前后结算；这不是turn_start/turn_end，不能重复触发那两个事件键。状态衰减：持有者回合末只执行根stacks_change、零层移除及triggers.remove，与tick_timing无关。数字为当前层数加该值后向下取整且不低于0；"x倍率"为乘后向下取整；"reset"归零；"keep"或省略不自动变化。减1层写根stacks_change:-1。remove_status立即移除整个状态，不接受部分扣层；stacks只修饰apply_status。
状态期限：层数不是剩余回合或触发次数。行动期施加且设置回合末衰减的状态，从施加当回合末就开始衰减；须按施加→tick→衰减→移除→后续触发计算真实次数。当回合turn_end不是下一回合。有限未来收益要同时落实触发时点与结束机制，不能只按目标回合数填写stacks。
眩晕：stun:true使持有者无法行动。除玩家要求或题材明确需要永久控制外，用stacks_change:-1、"reset"或可执行移除机制结束；永久眩晕本身不是结构错误。

奖励卡、遗物或道具引用尚未注册的一个或多个新状态时，在该候选同级写 `statuses:[完整状态定义...]`。从候选自身效果的直接引用开始，沿状态定义中的引用继续展开，数组必须闭合全部依赖，且每个定义都沿该链真实可达；程序会在领取时原子注册全部定义并从最终持有内容移除外壳。已有同 ID 同机制状态只复用。旧单个 `status` 仅兼容读取，新输出统一使用 `statuses`；没有新状态时必须完全省略，不能写空数组或 `null`。

`threshold_execute` 是回合末恢复、姿态槽内姿态与常规状态 tick、衰减都完成后的独立阶段，只允许 `execute` 或 `kill:true`，必须作用于状态持有者 `to:"self"`，不得写 `targets`，也不得混入伤害、治疗、状态或牌区操作。`execute` 的值是非负生命阈值或可读取 `stacks` 的合法公式，`threshold_mode` 只用 `hp/hp_percent`；满足阈值时直接处决，不经过格挡和普通伤害修饰。该阶段先按阵营内稳定实体和状态顺序建立快照再结算；已死亡实体跳过，最后一个战斗实体死亡后立即停止余下处决队列。不要用普通 `tick` 伤害或硬编码状态名称模拟阶段处决。

## 设计参考

`battle.design_context` 是程序提供的设计参考，不写回。剧情模型读取 brief，变量模型读取完整对象；优先使用 `balance.deckProfile/targetEnvelope`，缺省时使用 `balance.deck/target`。评分、流派缺口、谱系和实战反馈都是软参考，不覆盖剧情伤势、人物身份与自定义构筑，不强制传统攻防比例。敌人数值优先采用预算区间；伤害、欲望、控制、成长、格挡共享预算，增加一项时平衡其他项，并给主要压力提供可观察的应对窗口。

稀有度同时决定卡牌的预期强度、规则潜力与界面外观，不能只换一个标签。以费用和使用条件为基准：`Common` 是直接、可靠的基础构件；`Uncommon` 可以有更高效率、双用途或明确联动；`Rare` 应提供显著收益、条件回报、持续能力或足以支撑构筑核心的机制；`Epic` 应当明显改变一场战斗的决策方式或形成高影响力优势；`Legendary` 可以成为整套构筑的规则核心并改变原有出牌思路，但不能无条件直接宣告胜利；`Corrupt` 用于诅咒或带有与收益相称代价的危险力量。高稀有度的提升可以来自效率、灵活性、成长性、持续触发、牌区操作或机制协同，不要靠堆叠互不相关的效果伪装强度；低稀有度也可以是长期构筑中的关键组件。

## 完整性

- 初始牌组必须非空并包含可执行卡牌。总 quantity、基础能量下的可打出率、是否具备传统输出、攻守恢复比例与核心联动都属于设计建议，不得据此判定生成失败或强行重建牌组；字段形状、费用、效果可执行性、状态注册与重复 ID 仍必须通过契约校验。
- 稀有度表达预期强度与规则潜力，不规定效果数组条数；复杂度服务于玩法，不堆无关字段。
- 敌人至少有一个可执行行动，强度结合玩家等级、当前生命、卡组防御与恢复能力；入战生命、欲望、格挡和活动状态必须承接剧情已经发生的命中、伤害和变化，不能机械填满。机制由剧情决定：简单遭遇可以简洁，剧情确有需要时应使用少量彼此联动的自定义减益、多个独立被动、临时牌、牌库干扰、增援或形态变化塑造特色，避免只堆生命、伤害和格挡数值，也不要为了显得复杂而无关堆砌。
- 简洁表示规则易懂，不表示无变化的伤害木桩。单敌也应有逐回合/命中后成长、蓄力与周期爆发、状态施压或阶段转换之一；多敌应形成支援、标记与兑现、错位攻守等能被击杀顺序拆解的关系，总预算共享。易伤、虚弱、脆弱等通过已登记状态真实修改承受伤害、造成伤害、格挡获取；在动作或真实事件施加，持续规则仅放 hold/passive。前4至6回合的推演是内部设计检查，不输出分析，也不据此新增程序质量门槛。
- 只要玩家或某敌人的实际可达内容能增加欲望，就必须在同一侧补齐对应的完整满溢效果：玩家用 `battle.player_lust_effect`，该敌人用自己的 `lust_effect`。检查卡牌/行动、已引用状态、召唤行动和触发器的结构化效果，不用名称或说明文字猜测；共享状态库中未被引用的条目不算欲望机制。没有可执行欲望增量时，两种满溢效果都可省略。缺失时保留原欲望机制并补完整效果，不得删掉欲望操作、改说明或用固定弱效果兜底。
- `[构筑建议]` 由程序提供缺口、联动与候选方向；奖励和商店内容按其方向生成，但不要复制、解释或写回该行。不同时间出现同机制换皮是允许的，但同一组待选奖励不能只换名称与表现而保持机械结构相同；不同对象始终使用不同稳定 ID。
- 输出前逐个检查所有 `effects`、`trigger.effects` 与状态触发器：只使用对应层级的公开字段。效果根层禁止内部动作 `gain_block/gain_energy/gain_lust` 和通用 `attribute/operation/value` 包装；明确声明的嵌套字段仍合法，例如 `set_resource.value` 和 `changes.operator/value`，不得误删。绝不输出空 `effects`、空 `trigger.effects` 或值为空对象/数组的状态触发器；没有作用的字段直接省略。递归预检会拒绝未知字段、未知状态、重复 ID、非法选择器、空效果和错误类型；不要用 `<Analysis>` 声明代替实际校验。

### 召唤物唯一性与通用操作

spawn_summon:{id,name,emoji,description?,has_hp?,max_hp?,block?,tags?,resources?,modifiers?,actions?,abilities?,actions_per_activation?,action_priority?,speed?,intercept?,slot?,on_existing?,on_defeated?,retain_corpse?,capabilities?,count?,capacity?,overflow?,on_existing_effects?}；actions:[{id,name,emoji?,description?,weight?,fixed?,effects,creates?,when?}]；abilities:[{id,name,emoji?,description?,trigger,fixed?,creates?}]。唯一性由 slot 明确：有 slot 为同一召唤者同槽唯一，无 slot 为非唯一且每次创建独立实例。模板 id 不是场上实例 id，不能写入 selector.id；按类型手选使用 {pick:"choose",template_id:"模板ID"}，唯一目标使用 slot 筛选。唯一召唤可写 on_existing:"reinforce" 与 on_existing_effects：已有单位时不新增，执行这些效果而不再默认增加基础生命；self 指该召唤物，pick:"source" 指该实例，作用于召唤者须用 summoner_effects。首次召唤不执行 on_existing_effects。通用 activate_summon 立即行动；trigger_summon_death 仅触发所选单位的 defeated 能力，不使其退场；dismiss_summon 实际退场并触发死亡能力。三者均使用 {selector:{...}}，不要仅在说明中承诺。

# 抽牌与高频触发的收益

抽牌与返还能量会扩大后续行动；伤害触发抽牌时，必须考虑多段伤害、群攻、零费牌和造牌的组合收益。按整体平衡选择收益数值、费用、消耗、有限资源或次数约束；确需每回合上限时可用 `scope:"turn", ordinal:"first_n", n:正整数`，不能把限次作为所有遗物的默认模板。允许无次数限制的强力组合，能自我维持抽牌/能量循环的内容倾向最高稀有度 `Legendary`，结合获得阶段设计；这不是运行时质量硬门槛，不得擅自改写已经合法的玩家卡牌。卡牌描述避免重复计数范围、事件枚举和结算阶段等技术词，实际次数由可执行结构生成。


### 敌人队列、响应行为与行动台词
- 敌人定义可以写 `quantity`（省略为1；整数1..100），每份展开为独立稳定身份、生命、状态和行动。内容设计优先同种不超过两只，例如四人队设计成两个变种各两只；这是 Prompt 设计指导，不以数量/数值质量为由重写合法内容。
- 战斗固定五个前排槽位。enemies 按第1名、第2名依次编写，quantity 展开后，舞台从玩家视角左到右按第5、4、3、2、1名反向呈现（不足五人保留空位）。后写的初始成员更靠左、更接近左侧玩家；先写远端后排，再写近端肉盾。站位本身不会自动赋予承伤保护。内部 stageSlot 是零基稳定存档槽，不作为生成字段；现有存档不重写。死亡不压缩其他位置。超额进入候补，不生成意图、不接受伤害/状态/选择、不触发生命周期与回合事件；补空位上场时才初始化意图并参与战斗。设计时控制候补和增援规模，避免巨量敌人使群攻收益与处理成本失衡。
- 敌人可写 `victory_on_defeat:true`：此实体最终被击倒即胜利，即使仍有其他前排/候补；成功复活或逃跑不算击倒。界面提示胜利目标；战斗恢复保留目标与候补。
- 敌方召唤物默认无容量上限，我方默认3；`spawn_summon`/`copy_summon` 可显式设置正整数 `capacity`，按原有 overflow 策略处理。敌人增援 `spawn_enemy.capacity` 可选，计算存活前排加候补，不再隐含上限12。
- 通用效果 `{"wait":true}` 表示空过（仍消耗这次行动）；`{"say":"台词"}` 只记录行动台词，不产生数值效果；`{"enemy_intent":"guard"}` 将当前结算敌人的下一次行动改为本敌人 actions 中已有的稳定 ID（例 guard），不影响其他敌人。可以放在现有结构化事件触发器、条件分支中，响应玩家出牌，不需要另建专用反应系统；禁止引用不存在或其他敌人的行动 ID。
- 卡牌、敌人 actions 条目与召唤物 actions 条目可选 `dialogue` 非空文本。执行对应行动时展示台词；台词仅用于叙事，规则仍由 effects 决定。

### 战斗呈现约定
- 主动为有特色的卡牌、敌人行动和召唤行动写一句简短中文 `dialogue`，普通重复动作可省略。台词实际执行时显示在对应角色头顶5秒，点击可关闭；不只写进 `description`，也不为说话额外制造伤害或空过。`description` 用作卡牌底部风味文字，数值规则仍由 `effects` 决定。
- 敌人只按 `enemies` 数组生成先后排列，不输出序号、位置或 `stageSlot`。首项显示最右，后续依次向左；靠玩家的左侧是前排侧、最右是后排侧，因此需要前后排时先写后排、后写前排。最多5名在场，其余为后备；死亡留空位、增援补位由程序处理。视觉排位本身不提供保护或限制点选，保护须有真实机制；行动遵循程序队列，不因选中目标而改序。

### 敌方同队保护
敌人能力或本场新增状态定义需要保护时，写可执行 `protection:{mode,scope,target_id?,priority?}`。指定保护只能引用同场敌方稳定 `id`；目标死亡、离场或不存在即失效，不回退到名称/站位/active enemy。`intercept` 先于均摊，保护者按 `priority` 承接，死亡后的余伤才交下一名或原目标。`share_damage` 的 `specific` 在原目标和匹配存活保护者间分摊；`all_allies` 在所有存活敌人间分摊。二者都只处理攻击伤害，不把现有生命值强制设为平均。纯保护能力可写 `trigger:{on:"passive",effects:{}}`，不要伪造无关格挡或伤害效果。


### 状态通用防御
状态可写结构化 defense：{negate_debuff:true} 每层在负面状态赋予或叠加前抵消一次，抵消时不得执行被拦状态的 apply/stack；{damage_cap:1} 使每个伤害或生命流失包在格挡前最多造成1点；{prevent_hp_loss:true} 每层抵消一次格挡后仍会失去生命的伤害或生命流失包，格挡完全挡住不消耗。处决、击杀和直接设定生命值不属于伤害包，不能被此字段阻止。另可写 {retaliate_attack:数值或"stacks"}，受到攻击伤害包时对精确攻击者反伤，完全格挡仍触发，反伤不会引发反伤。这些是持有者本地规则，玩家、敌人与召唤物均按精确实例独立结算。
