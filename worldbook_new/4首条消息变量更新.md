# 首条消息初始化

本条是玩家初始状态、初始牌组、初始遗物与道具、玩家欲望满溢效果以及首次等级经验的唯一详细生成入口。其他条目只能判断是否需要进入本事务，不重复定义初始化清单。

## 防重复硬门禁

本条常驻可见，但只允许在当前对话的第一条助手回复执行。先检查聊天记录：若当前回复之前已经存在任何助手剧情楼层，本条立即停止，即使卡组为空也禁止再次初始化；之后的空牌组只能由玩家明确提出的修复操作处理。第一条助手回复必须读取当前 `battle.cards/artifacts/items/player_lust_effect`：只要 `battle.cards` 为空，就必须在本次第二阶段响应中一次性完成全部初始化，不能先只写职业和时间、再交给另一轮模型补牌。只要 `battle.cards` 已是非空数组，就代表初始化已经完成：即使最新回复错误地再次含有 `<CHARACTER_INIT_PENDING>`，也必须忽略该标记并跳过本条目下方全部初始化规则。

初始化不依赖 `<CHARACTER_INIT_PENDING>`：第一条助手回复中只要 `battle.cards` 没有任何真实卡牌对象，即使剧情漏掉标记也必须执行。标记只是提示，不能让后续楼层重新触发初始化。用户可能通过开始页提交 `[角色创建]` 浅层 JSON，也可能绕过表单直接自由输入；两种方式都必须在第一条助手回复对应的同一次第二阶段响应里初始化，缺少表单字段不是错误。以主模型刚生成的开场剧情为事实来源，补全职业、地点和卡牌主题。只输出一个 `<UpdateVariable>`，不续写或改写开场正文，不输出选项或战斗启动标记。变量路径均相对于 `stat_data`，遵循“MVU 变量更新协议”。

开始页的 `[角色创建]` JSON 使用 `mode/name/appearance/world/identity/opening/card` 这些通用浅层字段；爬塔模式还可能携带 `tower_requirements`，它只是本局自动节点内容的额外偏好，不授权 AI 修改地图、模式锁或程序状态。`appearance` 是角色形象描述，`identity` 是玩家希望尝试的身份，`opening` 是开场时机，`world` 与 `card` 只是玩家偏好的方向；字段可以缺省。不要寻找旧版的阵营、地点、偏好、剧情模板或机制字段，阵营和具体地点由剧情自然决定。卡牌方向也不构成硬绑定：它只表达节奏或构筑兴趣，具体元素、状态名、伤害类型和公式必须根据当前剧情由模型现场设计并注册。

这是由“当前卡组为空”触发、也可由当前回复专用标记明确提示的一次性完整初始化事务，不受“只更新本轮发生变化”限制。若 `battle.cards` 为空，只更新 `status.time/location/core` 属于失败；必须在同一个 `<UpdateVariable>` 中完成下列所有必需项。`battle.artifacts` 或 `battle.items` 留空、设为 `[]`、或完全不输出，也属于初始化失败。若卡牌已存在但遗物、道具、玩家欲望效果或其他门禁项缺失，说明上次输出被截断；只补齐缺失项，不得重复卡牌或状态。门禁已经全部满足时禁止重新输出 `battle.cards/artifacts/items/statuses/player_lust_effect`，只按普通增量规则处理本轮真正变化。

## 必须初始化

1. `status`：时间、地点、职业 `name/ability`，以及剧情中明确出现的服装、状态或物品。初始化文件已经提供空结构，不要为未变化的空字段输出命令。
2. `battle.core`：代表当前角色形象的单个 `emoji`、当前/最大生命、当前/最大欲望、删卡次数。`emoji` 不得留空；数值尺度根据角色设定与当前构筑决定，当前值不得超过对应上限。AI 直接填写的生命和欲望最多一位小数，删卡次数必须是整数。只有初始牌组确实使用自定义战斗资源时，才同时完整设置 `resources`；定义与费用必须服从“战斗内容生成要求”，未使用时保持空数组。
3. `battle.cards`：与角色职业和背景一致的主题卡组。卡牌只能写入此路径，绝不能写入 `battle.player_abilities`。
4. `battle.artifacts/items`：至少 1 个初始遗物和 1 个初始战斗道具，两者都不可省略。必须根据角色、世界、开场内容与构筑现场设计，不套用固定题材、固定功能或固定数值模板。
5. `battle.player_lust_effect`：玩家使敌人欲望满溢时触发的具名终极效果；因触发困难，必须足以逆转或决定胜负，不能只相当于普通卡牌的小额收益。必须有非空中文 `name`，所有操作都放在浅层 `effects` 中，不得把操作字段直接写在对象顶层。用一条 `_.set('battle.player_lust_effect', 完整对象)` 原子写入，禁止先写空壳再对 `.effects` 使用 `_.assign`。默认只用数值或牌区效果，禁止自行引用状态。
6. `battle.statuses`：默认保持空数组。只要用户没有在开局设定中明确要求状态构筑，卡牌、遗物、道具、欲望效果和敌人都不得出现任何 `apply_status/remove_status` 或状态公式。若用户明确要求状态构筑时，整套初始内容只使用 1 个新状态；先收集全部状态引用，先完整注册该 ID，再输出所有引用它的对象。程序没有内置状态。
7. `battle.level/exp`：无明确强者设定时为 1/0；经验是当前等级内进度。
8. `factions.player_alignment/invasion/relations`：入侵强度是 0-7 整数，无相关剧情时为 0。
9. `npcs`：仅登记开场已出现并会持续登场的重要人物；普通敌人和路人不登记。它是对象映射，新增人物只用三参数 `_.assign('npcs', id, 完整对象)`；没有符合条件的 NPC 时不输出命令。

`run/run_node/run_node_reward/run_event/run_shop/run_treasure/run_rest/run_result/run_upgrade/run_transform` 由程序按需处理，首轮禁止输出相关命令。`game_mode/game_mode_lock` 由开始页程序写入，AI 不要创建、修改或切换；剧情模式的 `run` 保持 null，爬塔模式由程序在初始化内容通过门禁后创建运行状态。

## 输出预算与顺序

- 整个初始化最多输出 20 条 MVU 命令，固定写 `<Analysis>Update.</Analysis>`，不输出分析过程。即将超出时减少卡牌种类和附加机制，绝不能截断 JSON、命令或 `</UpdateVariable>`。
- 先输出新状态定义，再输出 `battle.core`、遗物、道具、玩家欲望效果和卡牌；最后才写职业、时间、地点、服装、势力与 NPC。这样即使宿主意外截断，最关键的可玩内容也优先完整。
- 首轮也使用短命令逐项登记：每张卡各用一条 `_.assign('battle.cards', 完整对象)`，每个遗物和道具分别各用一条 `_.assign`。不要把整副卡组或多个对象塞进一条超长数组命令；这能减少括号配对和截断错误。没有状态定义时不要重复写空的 `battle.statuses`。初始化完成后的成长仍逐项使用 `_.assign/_.remove`，不得覆盖已有数组。
- `status.profession`、`status.clothing` 和 `battle.core` 可各用一条 `_.set` 写完整对象，不要把每个子字段拆成独立命令。

## 初始牌组

- 初次生成通常使用 3-4 个不同卡牌定义，总 `quantity` 至少为 10，不设总量上限。围绕玩家选择与剧情建立可执行核心机制，避免只为换皮增加定义数量；牌组规模与攻守恢复配比不作硬性限制。
- 首轮每个卡牌对象分别用一条 `_.assign('battle.cards', 完整对象)` 登记。含 `type/rarity/cost/quantity` 的对象就是卡牌；禁止写入 `battle.player_abilities`。`player_abilities` 只放带 `trigger` 的本场被动能力，首轮没有必要时保持空数组。
- 基础牌简单可靠，核心牌体现一个清晰构筑方向；卡组必须有可执行的胜利手段，但不强制包含格挡、治疗或任何固定攻防比例。
- 每个对象完整输出，ID 唯一且只用字母、数字、下划线；不得用中文名充当 ID。
- 新内容只使用 `effects`，不得同时生成旧 `effect`、内部 AST 或字符串化 JSON。
- `Curse` 牌必须省略 `cost`；其他可支付费用的牌才写非负整数或合法资源费用。`hits` 只能与同一浅层项里的 `damage` 共同出现，不能拆成独立效果项。
- `copy/double` 的值直接是数量或 `"all"`，来源、选择方式和过滤条件与操作同级；不能把选择器包装进操作值。`add_card/ensure_card` 的值直接是当前内容对象 `creates` 中已登记的模板 ID 字符串，目标与数量放在同一效果项的同级字段，不能把永久牌组中的卡牌 ID 当作临时模板直接引用。
- 卡牌、遗物、道具、能力、欲望效果和状态的 `description` 可省略，但通常应填写一句简短自然中文，用于表现动作、来源、质感或非数值特征；不要复述无条件的简单数值。只要存在 `when/on/trigger/discard_effects`、分支或多阶段规则，描述必须准确说明触发时机、条件和结果，不能只写氛围，也不能把“触发后”写成“打出时”等错误时机。所有玩家可见文本禁止出现英文 ID、公式路径或内部字段名，实际结算仍只由 `effects` 决定，界面会据此生成权威规则说明。
- 初始构筑默认不引用状态，也不生成状态定义。用户在开局设定中明确要求状态构筑时，整套初始内容必须共享恰好 1 个新状态，并至少由一项卡牌、遗物、道具或欲望效果实际引用；不得仅因职业、元素或叙事主题自行推断用户需要状态机制。
- 输出前汇总卡牌、遗物、道具、能力、欲望效果、状态公式和敌人引用的全部状态 ID。首轮当前没有可复用状态，因此每个引用 ID 都必须在同一更新中先完整注册且只注册一次；不得把任何常见英文 ID 当成内置状态。禁止生成未被任何内容引用的备用状态。
- 欲望构筑要能可靠累积欲望，并在敌人 1-3 次满溢内产生足以推进胜利的收益。

不要输出教学示例或占位对象；根据本轮正文直接生成精简、完整且闭合的初始化更新。

关闭 `</UpdateVariable>` 前做形状终检：每张初始卡、每个遗物和每个道具都必须分别通过其数组根路径的 `_.assign` 登记；禁止对这些数组根路径用 `_.set` 写单个对象。弃牌构筑中的每次主动弃牌都必须把数量直接写在 `discard`，其值不得是对象，`from/pick` 只能作为同级字段；弃牌、抽牌或伤害同时出现时必须拆成依次结算的独立数组项。多段伤害的 `hits` 必须和 `damage` 保持在同一项；复制数量、临时牌模板引用、诅咒费用和状态持续修饰必须再次按本条语法复核。并确认核心数值、总量至少 10 的卡组、至少一个遗物、至少一个道具、玩家欲望满溢效果、等级与经验都已经在本次事务中完成；缺少任一项都不得提前结束输出。卡组总量超过 13 不属于错误，不得因此重建或删减合法卡牌。
