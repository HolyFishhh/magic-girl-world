# 首条消息初始化

玩家初始状态、初始牌组、初始遗物与道具、玩家欲望效果以及首次等级经验的唯一详细生成入口。命令格式使用“额外模型变量更新格式”；卡牌字段和执行语义使用“战斗内容生成要求”，本条不另设效果语法。

## 何时执行

- 只在当前对话第一条助手回复对应的第二阶段执行。之前已有助手剧情楼层时立即停止，即使卡组为空也禁止再次初始化；之后的空牌组只能由玩家明确提出的修复操作处理。
- 初始化不依赖 `<CHARACTER_INIT_PENDING>`。第一条助手回复中只要 `battle.cards` 没有任何真实卡牌对象，就必须在本次响应完成初始化；已有非空但损坏的数组走修复，不覆盖已有内容。
- `battle.cards` 已是非空数组时跳过初始化，即使最新回复错误地再次含有 `<CHARACTER_INIT_PENDING>`。卡牌已存在时不得因为辅助内容缺失、卡组数量、攻守比例或程序评分再次初始化。
- 普通自由输入与开始页表单地位相同：允许绕过表单直接自由输入，缺少表单字段不是错误。事实以刚完成的 preset 正文为准，不续写或改写正文，不输出选项或战斗启动标记。

## 输入与模式

`[角色创建]` 可含 `mode/name/appearance/world/identity/opening/card`，爬塔还可含 `tower_requirements`。形象、身份、开场、题材均可自由指定；字段缺省时依剧情创作，不寻找旧版表单字段。`card` 中明确机制按“流派体系与设计方法”落实启动、运转与收益，只有名称、emoji 或说明不算实现；节奏与体验是软偏好。

爬塔只生成 `status.time/location/profession` 与所需战斗内容，不填 NPC、势力、关系、服装或普通剧情背包。剧情模式才登记正文明确出现的服装、物品和重要人物。未变化的空字段不输出命令。

`game_mode/game_mode_lock` 和全部 `run*` 路径由程序维护，首轮禁止输出修改命令。剧情模式的 `run` 保持 null；爬塔模式由程序在初始化内容通过门禁后创建运行状态。`tower_requirements` 不授权改地图、模式或程序状态。

## 生成清单

| 路径 | 内容与约束 |
| --- | --- |
| `status` | 时间、地点、职业 `name/ability`；仅剧情模式补已发生的服装、状态或物品事实。 |
| `battle.core` | 角色形象的单个 `emoji`、当前/最大生命与欲望、整数删卡次数。`emoji` 不得留空；数值根据人物设定，当前值在对应正上限内，生命与欲望最多一位小数。确实使用自定义资源才登记完整 `resources`。 |
| `battle.cards` | 初次生成至少包含一个真实卡牌定义；卡牌只能写入此路径，禁止写入 `battle.player_abilities`。完全相同的非唯一卡共用一个完整对象、稳定英文 ID 与名称，并以 `unique:false`、整数 `quantity:1..100` 表达独立副本；规则不同才新增 ID。 |
| `battle.artifacts/items` | 按角色与构筑需要自由生成，也可以保持空数组；爬塔后续最多3个道具槽，剧情模式不受此上限影响。 |
| `battle.statuses` | 按真实引用注册状态，程序没有内置状态。初始构筑是否使用状态以及状态数量由玩法需要决定；每个状态都必须有实际引用或可观察用途。 |
| `battle.player_abilities/player_status_effects` | 本场能力与活动状态，首轮没有必要时保持空数组；不能代替长期职业能力。 |
| `battle.player_lust_effect` | 初始玩家内容只要能以结构化效果增加欲望（含已引用状态、召唤行动和触发器）就必须生成；无可执行欲望增量才可省略。若生成必须含非空中文 name 与真实浅层 effects，满溢通常积累数回合，兑现须明显超过普通单卡：以同等回合与费用用于直接输出能取得的累计收益为参照，并计入触发后的持续收益，不能只多一点；以一条 `_.set('battle.player_lust_effect', 完整对象)` 原子写入。 |
| `battle.level/exp` | 首次等级与等级内经验；无明确强者设定时为1/0。 |
| `factions`、`npcs` | 仅剧情模式：阵营与关系按剧情，入侵为0..7整数，无相关剧情为0。NPC只登记会持续登场的重要人物；用 `_.assign('npcs', id, 完整对象)`，没有人物则不输出。 |

遗物、道具、状态、独立能力与玩家欲望效果是可选构筑内容，不为凑数生成；一旦生成必须完整可执行。只更新时间、地点、职业或核心而未建立初始牌组，属于初始化失败。

## 内容与引用

<!-- shared:initial-deck-design -->
[召唤构筑方法：选择有因果联系的模块，不要求全部塞进同一套牌]
召唤不是只有放单位与增加攻击。先明确单位承担输出、防护、资源生产、回合成长或牺牲兑现中的哪些职责，再设计建立核心、维持核心和兑现核心的不同卡牌。单核心可围绕同槽强化、治疗、生命上限成长、被动和指令展开；多单位可围绕轮换、保护、死亡触发、复制和退场回收展开。单位名和故事外观不能代替可执行配合。
召唤物的 actions 表达主动出招；abilities 使用真实 trigger 与 effects 表达被动，例如回合触发恢复生命。卡牌可用 apply_summon_status 赋予带触发器的状态，形成每回合恢复或成长；用 modify_summon、modify_summon_effect 改变单位属性和行动。生命转伤害的公式必须在召唤物行动中读取 self.hp 或 self.max_hp，不能误读召唤者生命；作用于召唤者时使用 summoner_effects。
限定某种召唤物在场才能打出的牌，在卡牌根部写 requires_summon:"模板ID"，精确匹配我方存活召唤模板，不能仅在效果的 when 中写存在检查后仍收取费用。需要一张指令牌让指定单位发动新招时，使用 activate_summon 的 action，并明确 selector；新招不必来自原 actions，伤害和触发来源属于召唤物。临时指令不会替换预告中的常规行动。按公开字段协议表达，不发明字段。
检查每条配合的对象身份、触发时点、次数和来源：启动牌是否真的能产生收益牌指定的模板/槽位/状态，核心尚未到场或已死亡时有哪些可用行动，随机目标是同一次选取还是分别抽取，持续成长是否来得及兑现。奖励优先补齐现有链条的缺口，也可以连接新的模块；不要因为玩家选了召唤就把所有牌做成重复召唤或纯加数值。
构筑主轴来自玩家职业、能力、指定流派和真实机制；成人世界题材不会自动要求欲望卡牌或 player_lust_effect。纯物理、小刀、格挡、召唤等方案可独立成套；只有主动采用欲望积累和兑现链时才加入欲望效果。没有指定流派时可从符合角色的多种玩法中原创选择，不套固定欲望模板。
开局牌组默认按总 quantity 合计 10–15 张设计；用户明确指定数量、极简牌组或其他特殊规模时优先遵从。未指定时交付完整可玩的起始牌组，不能只交付两三张展示核心机制的示例牌。
重复卡是合法构筑：当已有卡的名称、类型、费用和可执行规则完全相同（例如同为“斩击”，造成 6 点伤害）时，优先复用该卡的同一稳定 ID、名称和完整定义，并以 quantity 表达份数；不要为凑变化而另起近义名称或新 ID。构思只差小幅数值或换名、却没有有意义玩法差异时，也直接复用已有完整规则和名称，不为微差强造新卡。非唯一卡写 unique:false；每份会在运行时成为独立持有实例。唯一是单张卡牌的持有限制，unique:true 必须 quantity:1，不能用换 ID 的方式复制唯一牌。已合法且不同的内容不会被程序模糊合并；规则、费用或效果确有玩法差异时才是新卡，必须使用新 ID。
按通常每回合抽 5 张、3 点基础能量审查开局与后续洗牌循环；实际构筑改变这些规则时按真实规则。围绕用户主轴提供启动、运转、兑现和维持战斗的配合，费用支持同回合组合；不固定攻防比例，不用无关散卡填数量。检查核心牌未抽到、消耗或永久销毁后的续航；奖励候选、召唤物、遗物和未生成的临时模板不计入已持有牌数，也不能冒充开局已有配合。
以上规模是首次生成的设计默认值，不是运行时硬门槛；合法的特殊小牌组仍可使用，后续不得因牌数不足重建或自动补改已有卡组。

- 牌组规模与攻守恢复配比不作硬性限制。可打出率、输出、生存与循环评分只作建议，不授权删减极端或实验性构筑。
- 收集卡牌、遗物、道具、能力、欲望效果及状态公式的全部引用：每个引用 ID 都必须在同一更新中先完整注册且只注册一次；不得把任何常见英文 ID 当成内置状态。禁止生成未被任何内容引用的备用状态。
- 效果、触发、临时牌模板和费用只按通用契约输出，不重复旧 `effect` 或内部 AST，不字符串化 JSON。生成牌引用模板，复制现有牌使用对应操作；不得因格式报错改掉原机制。
- `description` 可省略；写机制说明时必须与真实时机、条件、目标和结果一致，实际结算仍只由 `effects` 决定。界面由结构生成权威规则，不要求再手写一份同样的数值说明。

## 提交顺序与终检

只输出一个 `<UpdateVariable>`，分析行固定为 `<Analysis>Update.</Analysis>`，不输出推理。

1. 先登记状态定义，再写核心、遗物、道具、欲望效果与卡牌，最后写人物及剧情模式资料。
2. 每张卡各用一条 `_.assign('battle.cards', 完整对象)`；遗物、道具、状态同样逐项完整登记。不要把整副卡组或多个对象塞进一条超长数组命令，也不要对 `.effects/.trigger` 追加碎片。
3. `battle.core/status.profession/status.clothing` 可按对象整体 `_.set`，不必逐个子字段输出；不重写未变化的空数组。
4. 关闭 `</UpdateVariable>` 前做形状终检：对象完整、数组保持数组、所有引用闭合、人物数值合法、必需卡组已建立；禁止对这些数组根路径用 `_.set` 写单个对象。完整响应通过校验才可使用，不能把输出顺序当成允许部分提交。
5. 通过 quantity、省略无变化字段和删除重复说明节省输出；不得为了命令条数删掉玩家要求的机制，不截断命令或闭合标签。不要输出教学示例或占位对象。
