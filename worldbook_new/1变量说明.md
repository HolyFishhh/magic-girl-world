# 剧情可见状态与构筑

当前 MVU 状态是剧情连续性的事实来源。本条目在每一轮剧情生成中常驻，下面展示的都是当前真实值；你只需要理解它们的意义，不负责修改，也不需要解释内部公式。不要因为某项本轮没有在正文出现就遗忘它，更不要把“没有提到”当成变量为空。

`battle.enemy`、`battle.player_abilities`、`battle.player_status_effects` 与 `reward` 不在普通剧情轮常驻注入，一次性战斗或奖励对象由对应事务消息按需提供。游戏流程专用状态同样不进入普通剧情上下文，剧情模型不读取、不判断也不修改。不要因为常驻区没有展示这些对象就推断其被清空。

把这些数据当成剧情事实。卡牌、遗物和道具中的 `name/description` 与浅层 `effects` 只用于理解它们在剧情中的实际作用；不要复述字段、计算公式、ID 或 JSON，也不要据此输出任何变量命令。

## 剧情中应关注

- `status`：当前时间、地点、职业、服装、剧情物品和长期/临时状态。正文与这些事实保持连续。
- `battle.core`：玩家当前生命、生命上限、欲望与上限。受伤、疲惫、恢复和欲望变化应在剧情中有合理表现。
- `battle.cards`：玩家实际拥有的卡牌。通过卡名、类型和效果理解玩家能做什么、构筑偏向什么；不要向玩家展示内部公式。
- `battle.artifacts/items`：遗物与战斗道具。让它们在剧情和选择机会中有存在感，避免遗忘已经获得的资源。
- `battle.statuses/player_lust_effect`：理解当前构筑的自定义机制与欲望满溢能力；它们没有程序内置含义，只能按变量中实际注册的中文名称、描述和效果理解。
- `battle.level/exp`：玩家成长阶段。只决定表现尺度，不要直接宣布程序尚未结算的升级。
- `battle.design_context.brief`：程序对当前构筑与最近实战的紧凑判断，只用于帮助剧情提供更相关的机会与挑战；它不是世界事实、不是硬配比，也不授权剧情模型修改变量。
- `factions/npcs`：势力关系、入侵强度和持续登场人物。保持立场、关系和行动连续。
- `reward`：只在奖励事务消息明确提供时理解为尚待玩家确认的候选；普通轮不常驻读取，也不要替玩家选择。

## 构筑友好叙事

判断卡组当前的主要胜利手段、防御方式、资源循环与已经形成的联动。剧情应优先提供以下帮助：

1. 补足明显的生存、恢复或资源循环缺口。
2. 强化已有主题，让玩家能逐渐形成明确而非随机拼凑的构筑。
3. 用敌人和环境检验构筑，但保留可观察、可应对的窗口。
4. 允许机制相近但叙事身份不同的内容存在，不因“效果类似”否定合理换皮。

你可以描述适合出现的奖励方向，但不要决定具体 JSON、数值、ID 或公式；这些由 MVU 额外模型根据同一段剧情生成。剧情模型每轮读取这些 MVU 值，但永远不输出变量命令；“持续读取”和“禁止写入”必须同时成立。
