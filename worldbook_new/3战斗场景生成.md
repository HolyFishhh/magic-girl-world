# 战斗数据注册

本条是普通剧情遇敌时注册敌人、本场新状态和临时战斗内容的唯一详细入口。只有主模型已经描写完整敌人并以 `<BATTLE_PENDING>` 交接时，才在额外模型解析阶段使用本格式。以主模型的敌人描述为唯一叙事依据，只输出变量更新：

`<BATTLE_PENDING>` 是必须注册实际参战敌人的明确指令，不是战斗结算提示。每次激活本条目，都必须按剧情完整替换唯一一个敌人入口：单敌写 `battle.enemy` 并清空 `battle.enemies`，多敌写 `battle.enemies` 并清空 `battle.enemy`；只更新 `status`、`battle.core` 或玩家内容而没有敌人对象属于失败。若当前 `battle.cards` 为空，先在同一个更新中按“首条消息初始化”完成玩家初始化，再注册敌人，不能拆到下一轮；不得为补齐门禁套用固定遗物、道具、状态或数值模板。

固定分析行仍为 `<Analysis>Update.</Analysis>`。不要续写剧情，不要输出 `<BATTLE_PENDING>`、`<BATTLE_START>` 或选项，也不要输出教学模板。更新成功后，卡内运行时会把主模型的待注册标记转换为战斗启动标记；如果数据无效则保持原文并等待修复。

## 敌人对象

单敌对象或 `battle.enemies` 中的每个对象每场都要完整设置，不依赖上一场残留。每个对象必须有唯一稳定英文 `id`，并包含中文 `name/description`、`emoji`、成对的当前与最大生命/欲望、非空 `actions`、`lust_effect`、`action_mode/action_config`；没有能力或活动状态时分别写空的 `abilities/status_effects` 数组。多敌只登记正文中已经同时参战的实体，不拆分一个敌人，不登记旁观者或未来增援。

提交前按这份最小闭合清单逐项检查：

- 普通敌人不强制为空能力或空状态。简单遭遇可以只使用行动表；当剧情中的身份、形态、环境或已经发生的交互需要时，可加入少量彼此联动的自定义状态、一个或多个独立特色被动、临时牌、牌库干扰、增援或形态变化。复杂度只服务于敌人特色和可玩决策，不要求每只敌人复杂，也不要堆砌互不相关的机制。
- 每项能力必须补齐不同的合法英文 `id`、中文 `name/source/description` 与结构化 `trigger`；多个被动分别登记，不能合并成不可读的大对象。状态必须先注册完整定义，再由 `apply_status/remove_status` 浅层操作引用。程序没有内置状态，不能只写看似常见的状态 ID。机制必须有可读预告或合理应对窗口，不能制造无解循环。
- 行动模式按剧情表现和机制需要从下方四种模式中选择；没有明确顺序或权重需求时使用 `random`。禁止 `pattern/rotation/cycle/attack` 等近义词。
- 时间和地点只允许更新 `status.time/status.location`，禁止写不存在的顶层 `time/location`。

- 对象中的所有可执行内容都使用浅层 `effects`，不得生成旧 `effect` 字符串。
- `actions`、`abilities`、`lust_effect` 的 `description` 可省略，但通常写一句简短中文动作或表现说明；不要复述无条件的简单数值。只要存在条件、触发器、分支或多阶段规则，描述必须明确写出触发时机、条件和结果，不得用模糊叙事代替规则。敌人对象本身必须保留中文剧情 `description`。
- `actions` 至少一个，名称各自唯一；`weight` 为大于 0 的有限数。
- `abilities` 可选且允许多个，结构与玩家能力相同并在独立的敌方被动区逐项显示；`status_effects` 的每个 ID 必须已在 `battle.statuses` 注册。`defeated` 会在实体移除前执行，需要退场结算、增援或形态变化时按完整战斗规范使用通用 `spawn_enemy`，不得把未来实体提前写进初始敌人集合。
- 多敌对象可用整数 `action_priority/speed` 明确行动次序，省略都按 0；每轮先按 `action_priority` 从高到低，再按 `speed` 从高到低，最后按 `battle.enemies` 中的稳定顺序。死亡实体在轮到行动前跳过，玩家进入终态后停止余下队列。
- 敌人只有在行动或能力确实使用自定义资源时才写 `resources`，并必须在首次引用前按完整战斗规范注册；不同敌人的资源彼此独立，不能借用玩家或其他敌人的当前值。
- `lust_effect` 表示敌人使玩家欲望满溢后的终极效果；敌人自己欲望满溢触发玩家的 `battle.player_lust_effect`。两者都因触发困难而必须足以逆转或决定胜负，不能只给少量普通数值；可按剧情使用高额终结伤害、强力状态、强力召唤、额外行动、处决或明确叙事终局等可执行后果。只有叙事说明而没有实际终局操作不算有效。
- `lust_effect` 必须有非空中文 `name`，所有操作统一放入浅层 `effects`；不得把伤害、欲望或状态操作直接写在对象顶层。
- 当前生命/欲望在 `0..max` 内，最大值大于 0；AI 直接填写的战斗数值最多一位小数。
- 入战当前值必须承接本轮已经写完的剧情，而不是机械设为满值。若正文中玩家或任一敌人已受伤、被治疗、欲望变化、获得格挡或被施加可执行状态，应把结果分别反映到 `battle.core.hp/lust`、对应敌人的 `hp/lust` 以及双方活动状态中；只有剧情确实处于完整状态时当前值才等于最大值。正文明确写出一次攻击已经命中或擦伤时，本轮至少有一个对应的当前值或活动状态必须相对更新前真实值发生变化，不能拿上一场遗留的非满值冒充本次先手结果；使用三参数 `_.set` 时旧值必须逐字取自本轮注入的当前变量。正文明确写出完全闪避、无伤格挡或攻击尚未命中时则不要虚构变化。活动状态使用带 `id/stacks` 的对象，并确保对应定义已经注册。
- 敌人 `actions/abilities/lust_effect` 的 `self` 均指当前效果来源的敌人，`opponent` 均指玩家；它们不是“玩家/敌人”的固定别名。省略目标时按“战斗内容生成要求”的操作默认目标执行；只要效果目标不是通常方向，就显式写 `to`，并在该对象的中文 `description` 中明确实际承受者，不能依赖动作主语或叙述视角猜测。
- 多敌不改变相对视角：敌人来源攻击玩家仍写 `opponent` 且不写 `targets`；敌人治疗、格挡、强化或清除同阵营敌人的状态时写 `to:"self"` 并按完整战斗规范使用 `targets`。玩家效果默认作用当前活动目标；需要指定、随机、随机多个、最低或最高生命、全体敌人时严格使用 `targets`，不得通过复制效果或重复写行动伪装群体目标。

## 行动模式

- `random`：从行动表随机选择，无需配置。
- `probability`：`action_config.probability` 用行动名称映射正权重。
- `sequence`：`action_config.sequence` 是非空行动名称数组。
- `sequence_then_probability`：配置中同时提供 `sequence` 和 `probability`，先走完顺序再按权重选择。

配置中的名称必须精确匹配 `actions[].name`；写错会在启动前按路径报错，不会静默退化。

## 难度与可玩性

- 若 `battle.design_context` 提供程序评分、回合曲线、目标预算、实战校准或敌人谱系摘要，按其语义控制本场有效耐久、逐回合压力、目标回合和反制窗口；这些值是软预算，不是需要复制、解释或写回的字段。当前剧情已经发生的伤势、身份、场景和玩家自定义方向仍然优先。
- 生成普通敌人、重要强敌或阶段性首领时，根据剧情地位调整机制密度、容错和压迫感；不依赖固定生命区间，不用只堆高生命或伤害代替机制差异。
- 结合玩家等级、当前生命、卡组伤害/防御/恢复、遗物与状态设计，不只按等级机械放大生命。
- 敌人至少有一种对玩家形成压力的行动；也必须留出可应对窗口，禁止永久眩晕、无限治疗或玩家无法突破的锁死循环。
- 敌人的机制组合必须以主模型已经写出的剧情身份、形态、行为和场景为依据，不要因为出现欲望、诱惑或精神影响主题就把敌人固定成纯欲望流，且不预先规定欲望与生命伤害的比例。可按剧情组合生命伤害、欲望、格挡、控制、自定义减益、能力和牌库干扰；有明确特色时优先让少量机制形成联动，而不是只提高数值。无论主题为何，都必须存在至少一条可执行终局路径，使敌人反复行动能够通过生命伤害、已完整注册的持续伤害，或运行时支持的明确失败推进结束战斗；`lust_effect` 必须是与其高触发门槛匹配的决定性效果，不能只是增加欲望、修改敌人自身少量数值或重复普通行动。叙事后果可以写进中文说明，但不能代替实际可执行的终局机制。
- 程序没有内置状态。先汇总敌人行动、能力、双方欲望效果、状态层数公式与 `status_effects` 引用的全部状态 ID；已有 `battle.statuses` 定义可复用，当前不存在的 ID 必须在同一更新中先完整注册且只注册一次。不能因 ID 名称常见而省略定义。
- 当前战斗不得改写永久 `battle.cards/artifacts/items/player_lust_effect` 或成长数据；只生成敌人、新状态定义和确有必要的本场临时玩家能力/状态。永久成长只通过奖励、商店或营火事务进入。
- 若当前回复同时含 `<CHARACTER_INIT_PENDING>`，或当前变量中的 `battle.cards` 为空，必须先按“首条消息初始化”完整建立 `battle.cards/artifacts/items/player_lust_effect` 等初始内容，再注册敌人；不能因为已经进入战斗而跳过玩家初始化。
- 敌人的实体形态、主题和机制完全服从当前剧情，不预设固定类型。

## 最终输出门禁

这是普通剧情遭遇时最后执行的检查，优先于草稿习惯：单敌入口与多敌入口必须恰好一个非空；每个敌人的 `actions` 必须是对象数组，每项都有 `name/weight/effects` 且没有 `type`；`abilities/status_effects` 必须是合法数组，不需要时写空数组，需要时只保留由剧情支撑且完整注册的少量内容，每个被动拥有独立 ID、显示信息、触发器和效果；`lust_effect` 必须同时有非空中文 `name` 和非空 `effects`；`action_mode/action_config` 必须符合上方四种模式之一且名称精确匹配。每个敌人必须有可执行终局路径和合理应对窗口。若草稿出现重复敌人或被动 ID、字符串行动、空欲望效果、未知状态、未注册状态、`pattern` 或自造字段，必须在输出前删掉并按本门禁重写。

只有玩家已经初始化、当前 `battle.cards` 是非空数组且本轮没有 `<CHARACTER_INIT_PENDING>` 时，才执行“除完整敌人集合外不改永久玩家内容”的普通遇敌限制。普通遇敌只承接剧情已发生的生命、欲望和临时状态变化，禁止修改程序管理的 `battle.level` 与 `battle.exp`。若初始化标记与战斗标记同轮出现，这是一次合并事务：先按“首条消息初始化”补齐核心、卡组、遗物、道具、玩家欲望效果、等级与经验，再设置完整敌人入口；卡牌、遗物和道具逐项使用各自数组根路径的 `_.assign`，绝不能用 `_.set` 把数组替换成单个对象。关闭输出前必须同时通过初始化门禁和敌人门禁。
