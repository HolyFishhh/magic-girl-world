# 战斗机制契约与长期回归清单

- 效果 DSL 与公式常量允许最多两位小数，使 `0.75` 这类正常倍率与战斗运行时精度一致；超过两位仍拒绝。生命、欲望等 MVU 存档字段不随之放宽。

更新时间：2026-09-18
适用分支：`codex/tower-mode`

本文是近期新增战斗机制的长期事实源。任何一次机制、世界书、第二轮请求、结构化输出、战斗运行时或界面说明发生变化，都必须回到本文逐项复核；不得以旧测试记录或聊天上下文代替当前证据。

玩家可选择的组合方向维护在 [爬塔二级流派目录](design/tower-archetype-presets.md)。新增机制时同步检查 `src/game-core/towerArchetypeCatalog.ts`，补充能实际衔接的二级玩法或记录非玩家适用范围；运行 `npm run test:tower-archetypes` 检查覆盖，UI 变更另跑 `npm run test:tower-archetype-picker`。目录仅提供 Prompt 引导，不加入玩家内容的执行验收门槛。

## 一、不可改变的产品边界

1. 卡组评分、敌人评分、模拟胜率、流派契合度、卡牌质量和创意诊断只用于向 AI 提供设计建议和事后审计。
2. 程序不得因为“缺少防御/治疗”“牌组数量不理想”“欲望效果不够强”“敌人不够平衡”“卡牌不符合流派”等设计判断修改、拒绝或阻止内容。
3. 只有会让程序无法确定执行含义的结构错误才允许硬拦截，例如未知操作、无法解析的字段类型、未登记引用、冲突目标或非法递归。
4. 对可以唯一、安全补默认值的内容直接规范化，不再请求 AI。例如缺少展示 emoji、缺省空数组和可推导的初始资源当前值。
5. 以最新公开协议为准，不为历史版本或任意错误字段增加兼容语义。仅保留最新协议所需、信息等价且无歧义的规范化，并有对应回归。下一版本清理旧协议、迁移与兜底时，同步移除仅验证已淘汰行为的测试，保留最新生成、执行、显示和保存恢复检查。
6. 剧情模式继续走原有链路；爬塔专用后台生成、评分、预生成和修复只影响本角色卡、已经锁定 tower 模式的后台结构化请求。
7. 用户已长期授权后续更新使用 Git 保存：完成并验证的任务或独立阶段及时提交本任务改动，收尾报告提交号与验证结果。推送、安装、正式发布和卡图仓库更新按对应任务已有授权执行；普通提交不触发发布，玩家更新记录只在交付对应版本时更新。
8. 性能优化只允许精简重复剧情背景、重复状态快照、程序私有字段与重复措辞。凡是会影响内容是否能正确生成和执行的玩法机制、生成方法、公开 DSL、字段形状、目标视角、公式边界、流派设计、敌人设计与奖励要求，都必须完整进入对应的首次生成请求；不得缩成关键词目录、只交给 JSON Schema，或因 token/耗时压力省略。修复请求可以省略无关剧情，但仍必须携带完整公开 DSL，局部错误提示只能作为额外重点，不能替代完整契约。
9. 禁止对玩家填写的要求、语义化 MVU 中的卡牌/状态/资源/能力、构筑评分、知识图谱查询结果、敌人谱系或待修复候选做字符串截断。需要减小上下文时，只能先按字段职责移除重复日志、显示镜像、空节点缓存和程序私有数据，且保留下来的 JSON 必须完整闭合；不能用 `slice(0,n)` 把玩法事实或 JSON 从中间切断。
10. 普通 MVU 第二阶段必须同时看到本轮剧情片段与请求开始时的语义化 MVU 存档；可选的算分与流派建议只是在这两类事实之后追加。关闭设计辅助只能关闭算分，不能移除 MVU 存档。无需重发无限聊天历史，但角色、地点、持有物、卡组、状态、敌人和爬塔进度不能因剧情片段未重复提及而丢失。
11. 普通 MVU 第二阶段沿用玩家当前模型、接口和预设原本的思考能力，允许慢一些，不强制关闭 reasoning。格式修复、结构修复和已经完成程序算分后的辅助请求只在自然语言中要求快速直接输出；任何路径都不得注入 `thinking`、`include_reasoning`、`reasoning_effort` 等厂商专属参数，也不得假设所有模型支持思考链。

## 二、统一检查链路

每项机制都必须同时通过下列七层，缺少任意一层都不能标记为稳定：

`世界书公开写法 → 后台实际请求 → JSON Schema → 解析/编译 → 战斗执行 → 存档恢复 → UI 权威说明`

检查规则：

- 世界书与后台请求只能公开一套写法，不得让模型在两套同义 DSL 中猜测。
- 后台请求不继承世界书时，必须直接携带当前任务所需的完整玩法与生成契约；JSON Schema 负责约束结构，不能代替自然语言解释机制的用途、组合方式与语义边界。
- JSON Schema 必须约束关键嵌套结构，不能只写“任意对象/任意数组”后再依赖末端报错。
- 解析器只接受运行时确实能执行的字段；每个公开字段必须能追踪到执行代码和测试。
- 战斗执行测试必须验证真实数值、目标、次数、牌区、触发顺序和事务回滚，不只验证“解析成功”。
- 存档恢复测试必须在效果已部分运行后保存并重载，验证顺序、计数和实例身份不漂移。
- UI 说明从可执行结构生成，不依赖 description 猜测，且不得漏掉条件、目标、持续范围和次数。

## 三、近期机制回归矩阵

### 新机制的同任务完成要求（2026-09-11）

任何新增机制必须同时完成渲染、中文命名、权威规则说明和相关交互，不能只实现执行程序。以下事项属于该机制的完成条件：

- 公开字段同步 Prompt、Schema、投影、有限修复白名单和解析/执行，防止正常支持的字段在自动修复时失效。
- `contentDescription.ts` 和 `effectDisplay.ts` 同步覆盖新操作、枚举、公式与选择器；共享中文名称作用域不能漏传。不得显示内部英文 ID，也不得省略名称/ID 筛选、条件、目标、次数、期限、永久成长或未来副本范围。
- 核查受影响的奖励/开局/事件/商店/营火预览、牌组/牌库、战斗卡面/详情、状态与召唤物面板；使用结构化胶囊，独立特性单独显示，关联功能完整归组。完整预览必须可换行且不裁剪。
- 涉及手选目标或卡牌时，确认选择界面、取消、空候选与实际应用；涉及持续或永久机制时，确认结算与恢复。

## 四、2026-09-03 已确认的根因

1. 爬塔初始化 JSON Schema 只约束了 `player` 外壳，`core/cards/statuses/player_abilities` 等内部几乎是任意对象，结构化输出无法阻止错误 DSL。
2. `generateRaw` 不继承世界书；后台精简提示只说 `spawn_summon/channel_orb/stance` 使用“完整定义”，却没有提供完整定义。
3. 真实模型输出把资源初始值写成 `start`，而运行时只接受 `current`，导致内容生成成功后在战斗加载阶段崩溃。
4. 真实召唤输出只有 `id/name/emoji/max_hp/description`，没有行动或能力。它虽然能解析为单位外壳，但无法兑现卡牌描述中的召唤玩法。
5. 初始化门禁混入至少一件遗物、至少一个道具、欲望终极、至少十张牌、基础能量可打出牌和稳定胜利手段等设计要求，导致自由设计被误判并触发昂贵修复。
6. 初始化修复最多重复三次完整大请求，重复携带全部上下文和旧候选，造成数分钟延迟、截断和再次偏离。
7. 节点平衡流程会直接改敌人数值，并在模拟不满足程序目标时拒绝节点；这与“评分只辅助 AI”冲突。
8. 旧测试主要证明运行时手写夹具可执行，没有证明模型在真实后台请求中能稳定生成同一语法，因此不能继续用“单元测试通过”代表 AI 生成稳定。
9. 初始化内容包曾丢弃 `core.stance/orb_slots/orbs`，导致错误当前姿态或姿态槽内容能绕过第二轮校验，直到战斗载入才失败；这些容器必须随玩家内容一起进入共享契约。
10. 卡牌升级的后台紧凑说明曾错误写成 `upgrade_card:{levels,changes}`，真实语法却要求 `upgrade_card` 为数量或 `"all"`，并让 `levels/scope/changes` 与它同级；这是提示词直接制造非法输出的确定根因。
11. 召唤行动与能力虽然公开了各自 `creates`，编译器却曾只读取外层卡牌模板；行动的 `when` 也被接受后静默丢弃。局部临时牌和行动条件必须进入实际效果程序，不能只通过字段检查。
12. 召唤 `action` 与 `actions` 同时存在时运行时只选择 `actions`，旧契约却没有声明冲突；现统一为二选一，避免模型以为两者都会结算。
13. 召唤 `modifiers` 曾允许任意数值键，但运行时只消费六个明确修饰项；未识别键会被静默忽略。Schema、编译器、快照校验和世界书必须使用同一有限集合。
14. 召唤能力的 `passive` 不进入普通能力的持续修饰收集链，旧 Schema 却允许生成。当前公开契约不允许召唤能力使用 `passive`，持续效果必须落在召唤 `modifiers` 或召唤持有状态中。
15. 同一聊天中重新开始一局时，控制器虽然按本局种子隔离了自己的 Promise，生成宿主队列却只用 `chatId/nodeId/requestId` 去重；新局可能直接复用上一局已经完成或失败的旧请求，表现为模型完全没有被调用。队列键、生成 ID、请求元数据、取消与重试现统一携带 `runScope`，并兼容释放旧版无范围记录。
16. 新增机制目前存在两套说明链：战斗标签说明器已覆盖当前姿态、姿态槽、召唤、增援、延迟、回合控制和高级牌区操作，卡牌/状态自然语言说明器却只覆盖到附魔。结果是同一份可执行效果在部分页面显示完整、在另一些页面为空或退化为不准确描述；必须统一到可执行 AST 的权威说明，不能继续分别手工维护两套不等价分支。
17. 卡牌选择器的 Schema 与编译器支持 `name` 和 `root_only`，但效果投影元字段表漏掉了它们，部分自然语言说明会丢失筛选条件。这类字段漂移必须用自动字段矩阵发现，不能只依赖逐个机制夹具。
18. 召唤资源公开写法曾有冗余身份歧义：资源由对象键定位，值内又可重复提供 `id`。现统一以对象键为唯一权威身份；省略内部 `id`，若仍提供则必须与键一致，矛盾内容会在生成边界被拒绝。
19. 内部 `mwg.effect/v1` Schema 曾漏掉 `apply_status/remove_status/draw_cards/discard_cards/exhaust_cards/reduce_card_cost/copy_cards/double_card_effect` 八个运行时合法操作，导致编译成功的内容无法通过持久化边界。现已补齐，并用 61 项操作矩阵防回归。
20. 动态增援的资源在公开 DSL 与运行时中是数组，内部类型和 Schema 却曾声明为对象；同一合法内容会在不同层得出相反结论。现统一为资源数组，并让缺省 `start/current` 安全归零。
21. 召唤能力若只写触发时机、不写实际效果，编译器曾静默丢弃该能力并继续成功。现改为明确结构错误，禁止“描述里有能力、战斗里没有效果”的空壳。
22. 动态增援生成后，初始姿态虽然保存成功，进入效果却曾沿用已死亡母体的敌人解析栈。现按每个新敌人实例 ID 分别执行姿态进入、`battle_start` 与 `ability_gain`，多只同时生成也不会串目标。
23. 内部 AST 的 `spawn_enemy` 曾把行动、能力、当前状态、欲望效果和行动配置声明为任意对象，运行时验证器却会拒绝其中的坏结构，错误因此延迟到保存或执行阶段。现这些嵌套对象都有严格 Schema，并通过删除、置空、未知字段差分变异确认 Schema 与验证器一致。
24. 战斗结算修复会复核整套保留内容；旧存档状态若仅缺少展示 emoji，会错误阻断完全无关的奖励或惩罚写回。现只在 MVU 适配边界为缺失状态图标补通用符号，规则、类型、触发和引用仍按原契约严格校验。
25. 开局馈赠曾把完整玩家状态表重新塞进每一个奖励候选的独立校验包；一个全局状态错误会被每张卡、遗物和道具重复报告，修复模型因噪音无法看清真实候选错误。现在候选只完整校验自己携带的新状态，已有状态只提供稳定 ID 用于引用解析，全局定义由玩家内容包统一报告一次。
26. 真实模型会自然使用 `%` 表达“每第 N 张牌”，并使用 `has_debuff` 表达通用减益存在条件；旧公开说明没有等价写法，运行时也会拒绝。现在公式正式支持安全取余，并提供双方增益、减益、中性状态和全部状态的存在判断及数量统计，避免为了一个通用条件伪造特定状态。
25. DeepSeek Flash 的真实批量节点请求曾在 20,000 token 上限内把全部额度用于 reasoning，最终 `content` 为空；这不是 DSL 候选被拒绝。但不能据此强制开关任何模型的 thinking/reasoning、改写 reasoning effort、温度或其他供应商私有参数，因为玩家使用的模型和渠道并不固定。后台请求只通过删除重复剧情/状态/程序字段、直接输出 JSON 的指令和局部修复来提速；完整玩法契约和玩家生成要求不得缩短，并原样继承玩家当前连接与模型设置。generation marker 只用于请求识别和可观察性。
26. `recover` 的完整提示曾明确允许 `card_type/rarity/...` 筛选，通用牌区筛选器也能执行，但操作元字段表、公开 Schema 与内部 AST 漏掉筛选，导致模型按正确提示生成后在领取馈赠时才失败。现把筛选贯穿“提示→Schema→编译→运行→显示”，并在开场选项进入 UI 前使用与正式领奖相同的候选校验，禁止把错误延迟到玩家点击。
27. 结构化输出使用的完整 Schema 虽然把 `passive.effects` 限定为 `modify/card_rule`，发送给提供商前的有限化适配却曾把所有 trigger 合并成 `effects:{}`，模型因此被 Schema 明确允许把 `apply_status` 放进 passive；失败后又收到 `card.program.steps` 内部路径，无法定位到 `creates` 模板。现有限 Schema 保留 passive 与非 passive 分支，并在共享内容边界逐个校验 `creates` 模板，把错误还原为公开的 `cards[i].creates[j].trigger.effects[k]` 路径。有限化只消除递归引用，不得消除玩法关键分支。
28. 节点奖励池校验曾在第一张非法候选处立即退出；真实模型给多张普通卡统一输出 `status:null` 时，唯一一次修复只看见并修正第一张，其余候选到第二次校验才暴露。现必须先收集同一奖励池全部候选的独立结构错误再发起一次修复。新输出用候选同级 `statuses:[...]` 携带其真实引用且依赖闭合的新状态定义；旧单个 `status` 继续读取。没有新状态时必须省略，不能用 `null`、空对象、空数组或临时编造的状态占位。
29. 真实初始化曾把“从手牌选择一张技能牌打出”误写成只有一个 `option` 的 `choose/options`，修复提示只收到通用 `.options` 路径后仍原样返回。现明确区分两种选择：`choose/options` 是 2..8 个预设效果分支；牌区选牌由具体操作的 `pick:"choose"`、`from` 和筛选字段完成。修复必须保留原动作语义并移除错误外壳，不能靠编造第二个分支通过结构检查。
30. 同一 Power 同时含即时 `effects` 与 `trigger.effects` 时，内容契约曾在第一条来源编译失败后提前返回，导致触发器里的独立错误直到修复后才出现。现每个可独立检查的效果来源都必须在同一轮收集问题。`card_rule` 不支持 `when/on`；条件持续规则应归属状态 `triggers.hold`，由状态的施加、移除和寿命控制，不得删除条件后扩大为无条件规则。
31. 真实结构化批量修复曾在每个节点对象后多输出一个 `}`；内容本身完整，但标准 JSON 解析与通用 `jsonrepair` 都失败，整批可达节点因此丢失。现解析层只删除“按当前容器栈绝不可能合法闭合”的多余右括号；不会补字段、补值、跨容器猜测缺失括号，也不会改动字符串中的括号。修复后的结果仍必须通过完整节点、作用域和玩法契约。
32. 真实敌人欲望效果会自然把新妨碍牌直接放入弃牌堆，旧 `add_card` 却只支持手牌和抽牌堆，模型的合理牌库污染设计因此被结构校验拒绝。现 `add_card.to` 通用支持 `discard`，并贯穿公开 Schema、编译器、内部 AST、运行时牌区、说明和图谱特征；直接生成到弃牌堆只表示放置结果，不冒充从手牌弃掉，也不会触发 `discard_effects`。
33. 真实临时牌曾出现“Skill 只有 `discard_effects`、没有根 `effects`”以及“Curse 写 `cost:null`”。前者并不是可打出的完整 Skill，后者也不是省略字段。当前主提示、输出前自检和快速修复统一要求：非 Curse 可打出牌必须保留真实非空根效果；若原语义就是不可打出、只靠被弃掉等后果生效，则改用 Curse，并彻底删除整个 `cost` 字段。
34. 全机制字段矩阵发现 `copy` 的公开 Schema 与编译器都接受固定目的地 `to:"hand"`，但说明投影元数据漏掉该字段。现已统一元数据；它仍只有手牌一个合法目的地，不扩展复制玩法，也不改变既有内容语义。
35. 真实开局馈赠会自然生成“一个遗物在三种新状态中随机赋予一种”的完整设计；旧奖励外壳却只能登记一个 `status`，另外两个状态必然被判定为未注册，快速修复也没有合法位置补齐。现奖励候选通用支持 `statuses:[...]`：从候选直接引用沿状态依赖链验证闭合、合并同定义重复项、拒绝同 ID 冲突或未使用定义，并在领取或卡牌变形时一次原子登记全部新状态。旧单个 `status` 保持兼容，最终持有内容不会保留任一外壳。
36. 真实初始化会偶发把玩家自定义资源数组写成 `core.resource`。修复模型虽然能改回 `core.resources`，但“只合并已报错分支”的保护器会把没有被点名的旧 `player.core` 覆盖回来，使正确修复失效。现把“单数键且值明确为资源定义数组”作为无歧义信封别名，在保存、分支保护和资源引用闭包校验之前统一为复数；两种键同时出现等有冲突的情况仍交给校验和 AI 修复。
37. 真实节点奖励会把卡牌自身的 `exhaust:true` 放进 `effects` 数组；布尔值不可能表示“从牌区消耗若干张”的数量操作，唯一可执行含义是卡牌根部生命周期。现只把卡牌 effects 中键集合恰好为 `{exhaust:true}` 的项提升到卡牌根部；`{exhaust:1,from,pick}` 等真实牌区操作、公式值和冲突根标记完全不改，并由通用规范化覆盖初始牌库与所有奖励候选。

## 七、生成与修复验收

### 首次生成

- 一次请求同时返回引导剧情、玩家资料、初始牌库与启程馈赠。
- JSON Schema 与提示共同约束公开 DSL；不得先放任任意对象，再把数十个错误交给修复模型。
- 可安全推导的默认值由程序补齐，设计质量只记为建议。
- 首次候选若结构不可执行，只允许一次短路径修复。

### 快速修复

- 把失败路径、该路径的精确修法和必要候选片段放在最前面，同时继续携带完整公开玩法/DSL/生成契约与同一 JSON Schema；局部修法只能加强重点，不能代替完整规则。
- 可以省略无关剧情预设、重复世界状态、程序私有字段与设计评分，但不得省略机制用途、字段形状、目标视角、公式/触发边界、流派与敌人设计方法、奖励规则或玩家生成要求。
- 修复监视器必须展示实际请求、模型实际响应、解析结果和最终写入；不得声称能展示提供商未返回的隐藏思考链。
- 公式中的生命、欲望、能量、格挡、牌区、状态、资源与状态统计必须带 `self.` 或 `opponent.`。玩家持有或待领取内容读取玩家自己的四个牌区时可由路径无歧义修为 `self.<牌区字段>`；敌人路径不得在脱离原描述时静默猜测阵营。`card_rule` 的值必须是公开规则字符串，`limit/extra/筛选` 与其同级；缺少明确 `rule` 的对象不得由程序猜成某条规则。
- `card_rule.limit` 已经是每回合匹配前 N 张牌的窗口，不再携带 trigger 专用的 `ordinal/n/scope/event` 等字段。奖励卡、遗物、道具、能力或行动中的 `add_card/ensure_card/transform_card` 只能解析该内容对象自身的 `creates`；所有奖励验证入口必须把本对象模板表传给编译器，不能出现“模板明明同级存在却报未知”的宿主差异。

### 真实模型门槛

- 使用真实 SillyTavern、真实 Tavern Helper、线上插件与 DeepSeek Flash。
- 连续覆盖“初始化 → 第一批可达节点 → 进入第一节点后第二批可达节点 → 第三批可达节点”。
- 记录每次首次请求是否直接通过、是否进入修复、错误路径、耗时和最终是否可玩。
- 用户当前接受约 75% 的首次生成直接成功率作为迁移前门槛；修复后的成功不能计入首次成功率。每轮仍要分别报告真实比例，不能把“约 75%”写成测试脚本里的放宽或吞错逻辑。
- 至少包含两套不同流派，其中一套必须使用近期复杂机制；不得只用基础攻防夹具刷通过率。

显示与识别补充（v454）：详细页和剧场的实际HP填充立即更新，损失段以半透明独立层在320ms内缩短；护盾归零播放破碎，按单位稳定身份绑定，非选中敌人的受击不得改变详细页。隔离实际组件已验证两处14.7059%新血量、残影收缩及护盾破碎类；完整Tavern玩家页面仍须实玩确认。纯普通攻击或格挡且数值严格小于7的牌不计流派证据，普通能量费用和运行展示元数据不应影响过滤；低值特殊机制保留，战斗能力评估不排除基础牌。见test-tower-foundation-recognition、test-tower-foundation-guidance、test-archetype-graph。


### 敌人队列、响应行为与行动台词
- 敌人定义可以写 `quantity`（省略为1；整数1..100），每份展开为独立稳定身份、生命、状态和行动。内容设计优先同种不超过两只，例如四人队设计成两个变种各两只；这是 Prompt 设计指导，不以数量/数值质量为由重写合法内容。
- 战斗固定五个前排槽位；四人初始槽位为空、1、2、3、4。死亡不压缩其他位置。超额进入候补，不生成意图、不接受伤害/状态/选择、不触发生命周期与回合事件；补空位上场时才初始化意图并参与战斗。设计时控制候补和增援规模，避免巨量敌人使群攻收益与处理成本失衡。
- 敌人可写 `victory_on_defeat:true`：此实体最终被击倒即胜利，即使仍有其他前排/候补；成功复活或逃跑不算击倒。界面提示胜利目标；战斗恢复保留目标与候补。
- 敌方召唤物默认无容量上限，我方默认3；`spawn_summon`/`copy_summon` 可显式设置正整数 `capacity`，按原有 overflow 策略处理。敌人增援 `spawn_enemy.capacity` 可选，计算存活前排加候补，不再隐含上限12。
- 通用效果 `{"wait":true}` 表示空过（仍消耗这次行动）；`{"say":"台词"}` 只记录行动台词，不产生数值效果；`{"enemy_intent":"guard"}` 将当前结算敌人的下一次行动改为本敌人 actions 中已有的稳定 ID（例 guard），不影响其他敌人。可以放在现有结构化事件触发器、条件分支中，响应玩家出牌，不需要另建专用反应系统；禁止引用不存在或其他敌人的行动 ID。
- 卡牌、敌人 actions 条目与召唤物 actions 条目可选 `dialogue` 非空文本。执行对应行动时展示台词；台词仅用于叙事，规则仍由 effects 决定。

### 保护伤害（2026-09-17）

- `protection` 是能力或状态定义的持续字段；仅 `intercept` 与 `share_damage`，仅处理攻击伤害。`specific` 必须使用运行时敌人实例 `target_id`，目标失效时不回退到活动敌人别名、站位或名称；`all_allies` 覆盖全部存活同队成员。
- `intercept` 按 `priority`、再稳定 ID 排序，由存活保护持有者依次承受；每名持有者先经同一伤害执行器结算自己的减伤、格挡、事件和死亡，只有其结算后的余伤才转给下一名，最后才落到原目标。`share_damage` 的 `specific` 只在原目标及每名匹配且存活的持有者间分配该次伤害；`all_allies` 则在该队所有存活成员间分配。小数份额保持两位并把舍入余量留给原目标，绝不重设当前生命值为平均值。
- 敌方召唤拦截继续走既有 `interceptDamageWithSummons`，但现在以 `targetEnemyId` 匹配 `summonerId`；未知/旧存档敌方归属不参与拦截，避免活动 enemy 别名移位。

- 保护转交只计算一次原攻击者出伤修正，每个实际承受者独立计算入伤修正与格挡；穿透格挡标志随攻击保留。全额拦截后的零余伤不会因原目标易伤而重新产生伤害。吸血累计原目标和保护持有者的实际失血（不扩大既有召唤拦截吸血边界）。
- 纯保护被动可使用空 `effects:{}`，但仍拒绝非法触发过滤器/未知字段；无保护的空被动不因此合法。状态与能力保存恢复后须重新执行攻击证明生效。作者输入、生成/有限修复投影、spawn_enemy两次编译校验、两条中文说明与保护详情UI共同回归。
- 展示阵型按敌人数组首次出现的先后从右向左排列（右侧后排、左侧前排），AI不输出序号或stageSlot；运行时槽位身份不改写，死亡不将存活者压缩移位。
