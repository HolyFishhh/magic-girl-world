# 爬塔模式实施与验收计划

更新时间：2026-08-30
开发分支：`codex/tower-mode`

本文是爬塔模式的唯一完整需求基线与逐项验收清单。实现过程中如果方案调整，必须先更新本文并说明调整原因；不得只依赖聊天记录记忆需求。未通过真实 SillyTavern 游玩验证的条目不能标记为完成，也不能写进玩家更新日志。

## 2026-08-30 生成链路边界修正

- 剧情正文始终使用玩家当前正在使用的原预设。程序不得硬性规定正文长度、段落数、节奏、文风或剧情推进速度。
- 爬塔节点、敌人、奖励和 MVU 等后台结构化内容不经过当前剧情预设；它们使用隔离的 `generateRaw` 请求、独立 system must 与 JSON Schema，只以“结果可执行”为硬约束。
- 若后台模型仍受预设或越狱文本干扰，允许沿用 MVU 默认破限的隔离思路修复结构，但不得把这套 system 或输出限制注入剧情请求。
- 单页连续体验由程序地图、节点状态机、预生成队列和结算事务驱动，不依赖对剧情正文进行字数或节奏控制。
- 当前节点 JSON 中的 `narrative` 只保存结构化节点的情境摘要与故障回退文本，不得被当作剧情正文的长度模板。

## 固定执行顺序与发布边界

以下顺序不得跳过，也不得因为后续代码已经提前完成，就把尚未实机验收的阶段视为完成：

1. 修复同步列出的常驻卡牌、战报和多敌人展示问题，并回归剧情模式。
2. 确认强度控制系统已正确合并；先验证扩展的作用域、真实请求链和首次初始化，再依赖它开发爬塔内容。
3. 完成程序地图、节点状态机、提前生成、奖励预生成、难度校准和单页连续游玩。
4. 整理世界书，使剧情模式与爬塔模式拥有清晰且互不污染的权威入口。
5. 在真实 SillyTavern、真实模型请求中完成桌面与手机端端到端验收；API 测试和脚本测试只能作为前置门禁，不能替代实机游玩。
6. 全部验收通过后，才更新玩家发布文档、打包必需扩展、提交和推送本分支。未经用户许可不得更新卡图仓库。

若扩展安装、发布或外部下载环节必须由用户操作，只能在其余实现和本地验收全部完成后集中列出，不以此为由提前发布半成品。

## 不可变目标

- 剧情模式必须继续完整可用，爬塔开发不能改变其既有对话、MVU、战斗、奖励和存档体验。
- 游戏模式只能在首次开始时选择。一旦完成初始化，剧情模式与爬塔模式都不能在当前存档中互相切换。
- 爬塔模式必须依赖项目扩展；扩展安装、版本检查、下载与故障提示都要在发布前完成。
- 爬塔一局固定三幕。每幕具有程序生成的分支地图、连续节点和幕末 Boss。
- 叙事服务玩法：战斗与事件只给简短、具情境感的文字，不要求玩家依靠酒馆原生输入逐层推动。
- 玩家在一个持续存在的大页面内完成整局，AI 请求和酒馆消息楼层在后台运作，不因创建消息而重载当前界面。

## 玩家流程

### 首次初始化

1. 开始页选择剧情模式或爬塔模式。
2. 爬塔初始化表单允许填写角色主体、世界/剧情方向、初始牌组要求、额外偏好；所有自定义内容都从页面内部输入。
3. 难度由项目扩展控制并在悬浮设置页可见。
4. 完成提交后锁定模式并初始化玩家状态与牌组。
5. AI 生成一个与当前世界观相符的开局馈赠者事件：可以无条件馈赠，也可以以代价换取更好的收益；不固定角色、文案或奖励内容。
6. 程序生成第一幕地图并显示可到达路线。

### 单幕循环

- 地图节点至少包含：普通敌人、精英、事件、篝火、宝箱、商店、Boss。
- 玩家只能选择当前节点直接连接且可到达的下一节点。
- 普通敌人、精英和 Boss 使用现有完整战斗系统；事件、营火、宝箱和商店由同一大页面承载。
- 战斗前就要准备好该战斗的奖励候选，避免结算时再等待。
- 玩家正在处理当前节点时，后台只生成当前路线接下来可到达的 1–3 个节点内容；不可到达分支不得浪费请求生成。
- 每个节点由原预设生成剧情并自动衔接；无自定义要求时不需要玩家额外输入。
- 每幕 Boss 完成后进入下一幕，基础难度在上一幕基础上提高 5%–10%，最终范围由平衡回归确定。

### 终局

1. 第三幕 Boss 结算后计算两类成绩：
   - 击败敌人的强度分总和；
   - 每场 `敌人强度分 / 当时玩家牌组强度分` 的平均百分比。
2. 进入作者结局：显示正在改代码的 `🐟`，从多段预设的敷衍/吐槽式台词中抽取；玩家角色也会简短回应。
3. 玩家对鱼造成等于总分的伤害，显示结算动画，然后结束本局。
4. 预留导出与分享接口和稳定数据结构；当前版本不实现实际分享。

## 地图与内容生成

- 地图结构、楼层长度、节点比例、强制宝箱/休息/Boss位置、精英与事件分布需要先调研《杀戮尖塔》原版规则，再结合本项目三幕结构确定可测试参数。
- 地图必须由确定性程序生成，可保存随机种子；AI不负责连接拓扑。
- AI只生成节点内容，不决定玩家实际可走路线。
- 地图快照必须能随酒馆存档/分支回退，刷新页面后恢复同一路线和已生成内容。
- 节点内容要按 `未请求 / 生成中 / 已准备 / 失败可重试 / 已消费` 管理，防止重复请求与重复领奖。
- 预生成任务以节点 ID 和状态版本作为幂等键；玩家改道后取消或忽略已不可达的旧结果。

### 已确认的首版地图参数

调研基线采用“保留原作路线节奏、程序自行生成拓扑、AI 只填节点内容”的方式：

- 每幕使用 `7` 列、`15` 行候选网格，程序尝试生成 `6` 条不交叉路径，并在第 `16` 层连接单独的 Boss。
- 第 `1` 层固定普通敌人，第 `9` 层固定宝箱，第 `15` 层固定篝火，第 `16` 层固定 Boss。
- 随机节点配额以普通敌人约 `53%`、事件 `22%`、篝火 `12%`、精英 `8%`、商店 `5%` 为基线；宝箱不参加随机配额。
- 前 `5` 层禁止精英与随机篝火；第 `14` 层禁止随机篝火；精英、篝火、商店、宝箱不能沿同一路径连续出现。
- 同一分叉点的后继节点类型不能完全相同；所有活跃节点都必须从起点可达且能继续抵达 Boss，不允许死路与孤岛。
- 第一、二、三幕的额外难度倍率暂定为 `1.00 / 1.07 / 1.14`，地图类型比例不随难度联动。
- 拓扑、房间类型、节点内容、奖励分别使用独立随机流；节点内容失败只能重试该节点，不能改变地图或已准备奖励。
- 地图生成后还要检查：至少两个起点；存在精英不超过 `1` 的安全路线和精英不少于 `2` 的高风险路线；两者精英数至少相差 `1`；至少一个商店可达。

## 伪同层与后台 AI 链路

采用 Discord 教程验证过的伪同层方案，不使用会强制刷新楼层的普通 `/send` 或 `/trigger`：

1. 页面内部构造玩家/系统请求文本。
2. 剧情正文由扩展调用使用当前原预设的剧情生成接口，不附加长度、段落、节奏或文风限制；后台节点/MVU 则调用隔离的 `generateRaw + system must + JSON Schema`。两类请求不得共用提示配置。正在战斗时只在内存中保留请求与结果，不得立即追加楼层，否则当前战斗 iframe 会变成历史楼层并失去写入权限。
3. 后台结构化结果需要做标签提取、变量解析和内容契约校验；在最新 MVU 的深拷贝上执行节点事务。解析或事务失败时不得修改原 MVU，也不得发送完成事件。剧情正文不套用后台 JSON 契约。
4. 事务成功后由扩展用 `message_id: latest` 原子替换权威 MVU，再派发项目内部完成事件，让持续存在的爬塔前端刷新自身数据。角色卡 iframe 不作为权威变量提交者。
5. 请求、响应和提交前后快照先进入扩展的待归档队列。一整局尚未结束时不追加任何楼层，因为地图、事件、奖励和战斗仍要在持续页面写最新消息。
6. 第三幕结束、整局失败或玩家明确退出后，才通过 Tavern Helper 的 `createChatMessages` 批量追加隐藏的 user/assistant 对；任何活动战斗存在时仍必须拒绝归档。
7. 历史消息仍使用酒馆原生楼层保存；可用 `/hide` 控制进入上下文的历史量，并为后续读档、回顾、分支保留接口。

实现边界：

- 扩展负责后台任务队列、取消/幂等、难度评分注入、生成状态与跨 iframe 桥接。
- 扩展始终以 `message_id: latest` 读写权威 MVU；持续页面只消费扩展推送的快照并把操作代理回扩展，不直接向已经成为历史的消息楼层写入。
- “节点结束”不是安全归档点：玩家仍需在同一页面选择路线、领奖或进入下一战。首版只有整局终止或明确退出才允许追加楼层。
- 刷新恢复依赖已经提交到最新楼层的完整 MVU；未完成的内存 Promise 不进存档，遗留 `generating` 状态恢复为失败并允许重试。
- 角色卡运行时负责 MVU 数据、节点事务、核心规则与当前页面呈现。
- `src/game-core` 负责地图、状态机、评分与纯数据校验，不访问 DOM 或酒馆 API。
- 剧情模式继续走原有链路，不得被爬塔后台调度器接管。

## 难度与评分

- 每次遇敌前记录玩家当时的牌组强度快照，不使用当前 HP 参与牌组强度评分。
- 扩展将玩家强度、目标难度比例、建议敌人生命/输出/生存/机制预算及当前剧情摘要注入第二轮生成。
- 敌人生成完成后，再由程序按实际敌人定义反向评分；超出预算时进行最小调整或发起有界修复，不提前假设敌人内容。
- 节点模型先完成具有剧情特色的实际敌人；程序随后复用统一卡组评分、敌人评分与战斗模拟器，对照玩家分数、目标预算和当前资源做至多五轮纯数值最小校准。若仍未达到可通关置信线，只允许一次限定在 `payload.battle` 内的机制修复；修复后仍不可通关则拒绝提交该节点，不能让必败敌人进入地图。
- 后台节点请求使用单一的最新完整 MVU 区段，不再重复拼接 battle/status/run 摘要；上下文安全上限为 20000 字符，替代旧 1800 字符截断。
- 强度模型必须识别低质量牌、不合流派牌、难以打出的牌与牌库污染带来的降分。
- 三幕的额外提升在目标难度比例之上叠加；任何默认难度都必须保持理论可通关，不能靠生成必败敌人制造难度。
- 总成绩同时保留绝对总分与相对难度百分比，避免初始构筑强弱不同导致比较失真。

## UI 要求

- 前端设计与交互实现不得为赶流程而简化成占位面板；地图、节点、预生成、战斗、奖励、结算与故障恢复都按正式可发布体验制作，不能以“功能能点”为完成标准。
- 整体氛围参考《杀戮尖塔》的路线地图和奇幻手绘感，但沿用本项目自身字体、颜色与已有素材，不复制受版权保护的具体美术资产。
- 一张展开的大页面承载地图、节点、事件、战斗、奖励与终局；切换视图不能造成酒馆楼层闪烁或空白。
- 地图清楚显示当前节点、可达连线、已访问路线、锁定节点与 1–3 步预生成状态。
- 当前节点请求时要有非阻塞进度反馈；后台预生成不能打断出牌与界面交互。
- 桌面与手机均可用；全屏体验优先，同时保留退出与故障恢复入口。
