# MVU 原楼层修复验收（0.5.143）

## 故障结论

用户提供的失败楼层含两个 `<UpdateVariable>`。第一块是原始生成，第二块是修复模型生成；旧实现会主动保留第一块。修复请求还与初始化和战斗锚点共存，因此第二模型重新规划了玩家卡组和敌人，而不是只修正问题路径。

附件中的公开格式错误包括：

- `discard` 被写成含 `count/pick` 的对象；正确契约要求数量或公式写在 `discard`，`from/pick` 与它同级。
- 通用“数量为 1 时可以省略”的说明误伤了牌区操作。弃 1 张牌仍必须显式写 `discard:1`，否则模型容易退回对象写法。
- `discard`、`draw`、`damage` 等被写进同一个效果对象。弃牌、抽牌、消耗、回收等牌区操作必须各自独占一个 `effects` 数组项，并按执行顺序排列。
- 公式调用函数；当前安全公式只接受运算符、比较、布尔和三元表达式。
- 状态的 `apply` 子触发器为空对象；没有效果的子触发器必须删除。
- 第二次输出仍有多处对象型 `discard`，因此不能视为有效修复。

## 已实现门禁

1. 修复期间隐藏所有非修复生成锚点，只激活相应修复世界书。
2. 额外模型必须返回一个新的 `<UpdateVariable>`，不能仅依赖楼层已有旧块。
3. 最终只保留最新修复块，旧块全部删除；原正文与运行标记保留。
4. 变量差异合并后执行生产 `preflightBattleContent`；仍非法时完整回滚。
5. 每类一次提供最多 8 个紧凑路径，修复模型不需要长分析，也不会遗漏常见的多项错误。
