# 流派与评分系统审查及后续方案（2026-09-22）

本轮范围是审查、资料对照、合法构筑复现和改进规划。未修改运行时算法、生成规则或角色卡，没有操作玩家存档、刷新页面或调用真实模型。审查基线为源码提交 `16c11fc`，此前安装记录为 `2b9c4e3`。

结论：现有系统可以提示简单构筑方向，但存在可复现的错分、漏识别和缓存错误，不能把流派百分比理解为识别置信度，也不能把各处的评分当成同一种强度。优先修正语义和统计口径，再扩充流派。当前统计为 **67 个流派节点、138 个基础预设**；数量本身不是主要短板。

## 1. 当前实际调用链

| 层级 | 入口及用途 | 目前含义 / 边界 |
| --- | --- | --- |
| 流派证据 | `archetypeEvidence.ts` → `archetypeGraph.ts:profileDeckArchetypes` | 从结构提取机制，卡牌按数量、遗物按 1.5、能力按 1.25、持有状态按 0.75 加权；占比反映证据分配，不是胜率或实际输出占比 |
| 静态强度 | `deckPowerScore.ts:scoreDeckPower` | 预算与特征公式；奖励候选增量、删去一张牌的贡献估计使用它，不能用界面正式实测的改进替代这里的修正 |
| 影子模拟画像 | `deckPowerProfile.ts:profileDeckPower` | 单独的模拟模型，含静态维度；`sillytavern-extension/designEngine.ts` 和角色摘要使用，服务设计提示与预算 |
| 正式引擎实测 | `runtime/towerRuntimeBalance.ts:measureTowerBuild` → `buildAssessment.ts:assessMeasuredBuild` | 主界面测试表现达成度；8 类固定对手，每类默认 2 个种子 × 3 种策略，共 48 次试打 |
| 敌人静态强度 | `enemyPowerScore.ts:scoreEnemyPower` | 行动加权与机制计数，行动周期、条件和被动强度覆盖不足 |
| 具体遭遇试打 | `runtime/isolatedEncounterEvaluator.ts` | 正式引擎隔离执行，有策略/搜索/出牌上限，覆盖与构筑画像不能混为一谈 |

已有值得保留的设计：流派分析剔除名称和文案；追踪实际引用的状态与生成牌；召唤物输出与玩家输出区分；跨卡配合按资源/状态/召唤物身份连接；正式实测明确不是胜率；不确定结果不直接算零分。这些比关键词猜流派可靠，应在共同语义层上继续完善。

## 2. 合法输入复现

运行 `node scripts/audit-archetype-scoring.mjs --measured`。脚本使用合成内容，先通过 `validateContentPackContract(..., {requireExecutable:true})`，检查输入未被改写，禁止访问宿主存储。结果写入忽略目录 `tmp/archetype-scoring-audit.json`，正式引擎原始试打保留在其中。

脚本记录观察结果，**不把当前错误分数写成必须保持不变的回归断言**；后续修复后应更新观察并加入符合新语义的回归。

| 优先级 / 编号 | 对照案例与当前结果 | 判断与影响 |
| --- | --- | --- |
| P1 / A1 缓存身份 | 同样卡组与状态库，持有的状态从伤害 +1 改为 +20：先算前者再算后者都是 **78.8**；清缓存后后者为 **177.7** | `contentFingerprint.ts` 递归删除所有 `id`，把状态引用身份也删掉；两种实际构筑的指纹相同。这是确定的缓存错误，可能影响奖励增量与显示更新 |
| P1 / A2 词条漏识别 | 灵巧攻击牌 + 主动弃牌，只识别直接压制 50%、弃牌引擎 50%，且提示缺收益；换成遗弃、遗忘得到相同静态分 **41.8** 与相同流派 | 灵巧没有转为“主动弃牌 → 免费执行”的证据；投影跳过 `lifecycle`，遗弃/遗忘代价未区分。不能把三者都当成普通弃牌收益 |
| P1 / A3 零费漏识别 | 原生 `cost:0` 的伤害+抽牌循环，识别直接压制 40%、抽牌 30%、节奏循环 30%，没有零费连锁 | 节点要求 `free` / `reduce_cost`，没有覆盖卡牌本来的零费用 |

| P1 / A5 入门牌阈值跳变 | 5 张格挡 6 + 2 张伤害抽牌：直接压制 40%、抽牌 30%、节奏 30%；仅把格挡 6 改 7：格挡循环突然占 **71.4%** | `isPlainLowValueStarterDefinition` 在数值 7 处从完全排除切为完整计权；普通数值升级改变主流派，与实际机制变化不符 |
| P1 / A6 无效定义加分 | 相同 10 张牌，只在库中添加无法获得的状态，预算完全相同，静态总分从 **70 → 71.5** | 静态特征遍历全部 `pack.statuses`，未和流派分析一样限制实际可达定义；“机制更多”带来不应有的收益 |
| P1 / A7 资源稳定性 | 5 张费用为法力 2 的牌，完全无法获得法力与初始拥有 5 法力，两者稳定性均为 **65** | 该维度按费用数字 ≤2 判可用，没有检查真实资源供给。两者总分 **19.7 / 228.1**、伤害预算 **0 / 100** 已有区别，不能误报为整个系统完全忽略资源 |
| P1 / A8 敌人静态分 | 随机二选一攻击/等待与“攻击一次、等待四次”的敌人都为 **119 分、期望伤害 15**；反伤 1 与反伤 100 都为 **127 分** | 周期敌人完整 5 回合平均主动伤害实际为 6；被动量级不影响静态分。这些情况下 `coverage=1` 仍出现，覆盖标志不能当作语义准确性保证 |

另外两项代码级缺口需要配套正式回归，而非仅调参数：

- `profileDeckArchetypes` 的根定义不纳入玩家欲望满溢效果、当前姿态、已有球体及持续卡牌改造等状态；“双轴压制”一张牌中同时有伤害和欲望，就能得到欲望转化证据，无需证明后者产生前者。合法满溢效果必须存在，因此本轮对照并不声称“完全没有满溢效果也能过契约”；错在把并列效果当作转化、缺少实际满溢收益分析。
- 静态/影子画像指纹也遗漏姿态、球体、持续卡牌改造和召唤成长等输入。应逐项对照各评分器实际支持范围：支持的纳入依赖；不支持的明确标为未知，不仅添加缓存键后就宣称已支持。

## 3. 正式引擎评分的审查重点

当前未获胜样本：`100 × (0.65 × max(累计伤害 / 对手总生命, 累计欲望 / (100 × 对手数)) + 0.35 × 剩余生命比例)`，进度夹到 0–1；战败封顶 25，胜利为 100。每类对手按种子整体选择一个最好策略，再取 8 类结果中位数。

这比直接累加卡牌文本更接近实际战斗，但需要修正以下口径：

1. **欲望数值不天然等于清敌进度。** 必须看满溢后实际执行的效果。回满、清空、反复累积欲望可能不造成击杀；治疗、护盾、资源类满溢收益应进入对应表现维度，不直接折成终结进度。脚本用没有伤害的护盾满溢对照验证这点。
2. **总中位数会掩盖短板。** 8 类中可以有 3 类非常差而总分不下降；胜利都为 100，也无法区分险胜与低损耗胜利。应保留胜负、回合、战损和最差场景，并把短板放到主结果旁。
3. **两种子仅适合快评。** 不应据此给精确胜率/稳定性判断。建议快评维持轻量，按需后台提高样本数，展示样本数与波动；新增样本复用旧样本。
4. **三个策略仍是受限选牌器。** 当前构筑测量使用 `search:'rollout'`，每步只看有限候选的即时结果，并非完整连招求解。延迟回报的启动牌、需要先亏后赚的两牌组合可能被低估；无限/超长循环触及每回合 24 次出牌上限时，应报告“截断”，不能下低强度结论。
5. **八场测试尚缺针对性敌人。** 目前主要变化是血量、数量、伤害、欲望、虚弱，缺护盾阻碍吸血、驱散负面、逐次减伤/受击成长、出牌/花费响应、费用压力等。应补成可配置的对局矩阵，不让总分代替克制分析。

正式试打的具体结果及验证记录见本文末尾验收段。

**正式引擎复现 A9（P1）**：两套牌都为 5 张费用 1 的技能，每张获得 40 格挡，玩家最大生命 80；玩家满溢效果仅获得 1 格挡。对照组没有欲望输出；实验组每张还对所有敌人增加 100 欲望。数值是用于隔离评分口径的合法合成案例，不代表推荐卡牌平衡。

| 构筑 | 48 次试打结果 | 实际伤害 | 选择策略后的 8 场景表现 | 最终总分 |
| --- | --- | --- | --- | --- |
| 仅防护 | 48 次到达测试回合上限，0 胜 | 全部为 0 | 全部 35%，剩余生命均为 80 | **35%** |
| 防护 + 非致命欲望 | 48 次到达测试回合上限，0 胜 | 全部为 0 | 全部 100%，剩余生命均为 80 | **100%** |

这证明当前“清敌进度”会被没有任何清敌结果的累计欲望填满。问题位于评分归一化，而不是战斗执行把欲望误判成胜利；试打记录正确保留了未胜利结果。主界面说明为“表现达成度”也不足以消除这个语义错误。

## 5. 流派系统建议

保留现有目录，补充三层信息，避免继续堆叠相互重叠的百分比：

- **主要获胜方式**：生命压制、实际满溢收益链、持续消耗、召唤物输出等。以可执行结果判断，不凭卡名猜。
- **运转方式**：抽牌/弃牌/消耗、能量与自定义资源、状态、保留/复制/重放、召唤、形态等；同一副牌允许多个标签。
- **当前成熟度和风险**：已有组件、配合闭合、试打已触发；缺抽牌/资源/目标/收益、展开慢、被净化/反伤等限制。静态推断和实测事实分开标明。

优先补强下列组合与诊断，不把已有玩法重复注册成新流派：

| 方向 | 需要补充的判断 |
| --- | --- |
| 灵巧弃牌 | 主动弃牌来源 × 可触发灵巧的牌 × 免费执行收益；回合末自动弃牌不算灵巧启动 |
| 遗弃 / 遗忘 | 所有弃牌都会触发；前者本场移除，后者永久删除。既可能减薄牌库，也可能破坏关键组件，不能无条件加分 |
| 吸血续航与自损交换 | 实际穿过防御的伤害能否转为恢复、是否过量治疗、启动需不需要先承受失血；不要和“治疗触发输出”混用 |
| 负面叠层 / 引爆 / 反哺 | 施加目标、可叠层对象、消耗层数与收益是否引用同一状态；主动净化和清除自己的收益状态可能相反 |
| 多段 / 单次大伤害 | 逐击收益与每次固定减伤、反伤、受击成长之间的关系；单纯累计伤害不能代表相同对局能力 |
| 零费 / 花费 / X 费用 | 原生零费、临时免费、降费分别识别；按出牌次数和按实际花费触发分别计算，不能把免费打出当成已支付原费用 |
| 召唤与形态 | 在场单位、承伤位置、支援范围、指令、死亡再利用；现有形态和球体状态进入分析作用域 |
| 诅咒交换 / 长期成长 | 即时负担与战后/长期收益分别报告；只看一场战斗的试打不足以给永久删除或诅咒遗物定全局价值 |

UI 示例：`灵巧弃牌：有配合，尚缺稳定弃牌来源；吸血续航：已在试打生效，对高格挡敌人表现下降。` 展开后列实际卡牌、状态和触发证据。剧情名称继续显示“黑暗仪式”等原创命名，内部分类不把它替换成“力量”。

## 6. 推荐实施顺序与验收

### 阶段一：先消除确定错误

1. 将“精确执行状态缓存”和“找换皮/近似结构”指纹分开；语义引用 ID 必须保留或做一致的引用规范化。覆盖全部实际依赖，升级缓存版本。
2. 统一可达定义和受益方语义，补灵巧/生命周期/原生零费；转化、倍率等节点必须有可追踪的因果证据。
3. 去除入门牌 6/7 的数值断崖，保留“基础打击/防御不压过特色组件”的产品意图；使用身份/机制角色或平滑权重，具体依据需和初始卡组协议对齐。
4. 正式分数按实际终结进度与战斗结果计分；敌人静态周期/被动未支持时降覆盖，不伪装为完整估分。

验收不是“旧分数不变”：改名不改变机制分、无关库定义不加分、引用身份改变立即重算、自动弃牌不触发灵巧、普通 +1 数值不改变主流派、无法造成终结的欲望循环不获得满额清敌进度。资源不存在时允许识别为尚未启动的构筑意图，但必须提示缺口。

### 阶段二：统一结果解释与奖励比较

- 每处数值都注明用途：固定对局表现、资源预算、奖励边际收益。主界面显示样本数、战损、薄弱对手，保持快评可取消、后台不阻塞操作。
- 奖励当前已计算加入后的静态增量，但仍有固定新颖度奖励和重复结构扣 12。应将“新颖性”和“实用性”分开；同一张启动牌的第二张可能比全新花样更能改善构筑稳定性。
- 使用同种子前后对照评估候选，先静态筛选、缓存复用，再按需要实测；不要每次渲染都重跑全套模拟。低置信度只提示，不硬拦合法生成。

### 阶段三：扩充对局与准确性数据

- 固定基础对局加机制挑战对局，构筑得分和克制暴露分别报告。软克制仍保持小怪 20%、精英 50%、Boss 50% 的程序抽签；增强分析不提高触发概率，不按标签生成全面免疫。
- 建立人工确认的正例/反例矩阵，统计每个节点的误报、漏报、混淆和未覆盖机制。先覆盖本次缺陷、主要流派和混合构筑；样本数量随覆盖扩展，不在缺少标注时承诺总体准确率。
- 用同构改名、数量变化、弱数值升级、资源断供、敌我目标互换、存档往返等变换测试语义稳定性。对复杂组合记录“自动策略未发挥”与“机制未支持”的不同原因。

以上均为分析、显示和 Prompt 建议；不会新增卡组质量硬门槛、自动改写合法卡牌、强制套用预设 buff，或为了凑数值删除玩法。

## 7. 本轮验证与交付边界
