# 通用卡牌核心与《杀戮尖塔 2》Mod 可行性

日期：2026-09-22。状态：架构规划与资料调研，未创建 Mod、安装工具或修改运行时。主路线见 [Steam 实现路线](standalone-steam-roadmap.md)，引擎与智能体方案见 [独立智能体与表现层设计](standalone-engine-ai-assets.md)。

## 1. 决策与范围

独立 Steam 游戏是当前产品主线。卡牌核心需要能够被不同宿主消费，方便机制更新；Bilibili Toy 与《杀戮尖塔 2》Mod 暂时只影响模块边界，不进入首发排期。用户已明确优先考虑尖塔二代，不沿用一代 Java／ModTheSpire 的接入路线。

采用“内容协议、规则核心、智能体、宿主适配、表现层”分离的方案。同一套规则只维护一份权威实现，但不承诺所有宿主都能完整执行它。独立游戏可以使用完整引擎；接入已有规则的游戏时，可以仅复用内容生产能力及已验证的机制子集。

这里的通用是脱离酒馆、引擎、模型供应商与具体世界观，并为实际宿主留接口。首期不开发万能卡牌编辑器、任意脚本插件系统或覆盖所有卡牌游戏的抽象框架。当前 emoji＋卡牌战斗美术、AI 必需的剧情模式、一个基础离线爬塔预设、低价买断与去色情/欲望体系的要求不变。

## 2. 当前源码基础与缺口

已有基础经过只读核对：

| 入口 | 已有职责 | 后续需确认或补齐 |
| --- | --- | --- |
| `src/portable/cardBackend.ts` | 卡牌规则、效果执行、选择、奖励、内容编译/校验与部分说明的公开出口 | 公开 API 收敛、结构版本、外部消费者契约 |
| `src/portable/battleBackend.ts` | 战斗状态、回合、触发、终态及适配器出口 | 完整会话边界、跨进程选择与恢复 |
| `src/portable/api.ts` | 已有 `mwg.portable/v1` 标识 | 它不是存档、规则和所有桥接版本已统一的证据 |
| `src/adapters/referenceBattleRuntimeHost.ts` | 基于共享状态的事务、回滚及卡牌/战斗运行时接入 | 真实独立客户端及外部游戏的宿主验收 |
| `src/game-core` 与当前 controller | 已有整局、路线和节点相关逻辑 | 整局/爬塔门面、完整双说明链、移除聊天/MVU 投影耦合 |

核心职责以 [后端边界](../backend-boundaries.md) 为准。参考宿主的注释包含 Mods，但尚未证明已兼容尖塔二代。公共导出存在也不代表纯逻辑依赖闭包、存档兼容与实际分发已经完成。

## 3. 目标模块边界

下列是逻辑模块建议，先在同一仓库按边界演进，不立即拆成多个仓库或远程微服务。

| 模块 | 负责 | 边界 |
| --- | --- | --- |
| 内容协议与编译 | 卡牌/状态/资源/召唤物定义、Schema、引用检查、编译、诊断、有限修复及结构化说明 | 不绑定 HTML、Godot 场景、酒馆变量或某个模型 |
| 卡牌/战斗规则核心 | 牌区、费用、目标、效果、触发、回合、状态、实例身份、事务及确定性随机 | 不进行模型请求、画面播放、文件读写或平台调用 |
| 整局与模式流程 | 节点、奖励、商店、营火、胜败、剧情/爬塔的衔接 | 与单场战斗分层；尖塔 Mod 不必消费我们自己的地图与整局规则 |
| AI 智能体运行时 | 查询、草稿、工具反馈、修复、上下文、预算与取消 | 通过目标宿主的工具端口工作，不自行成为战斗状态所有者 |
| 宿主适配 | 状态提交、存档介质、模型网络、凭据、生命周期、平台能力 | Steam 客户端、Toy、尖塔分别实现各自边界 |
| 表现层与内容包 | 输入、卡面、emoji、动画、中文排版；世界设定和预设内容 | 表现层不重算规则；主题字段不固化进通用卡牌内核 |

现有 TS 核心先保留为唯一实现来源。Godot 桌面候选方案通过随包提供的本地运行时消费它，Web 宿主能否直接导入由实际环境决定。未来 C# Mod 可以复用数据协议或对接受控服务，但“JSON 通用”不等于“TS 执行器可以直接放进 C#”。在没有实测瓶颈前，不为潜在 Mod 同时维护 TS 和 C# 两套完整内核。

动作接口按“玩家动作 → 规则处理 → 状态版本/事件/待处理选择”设计。使用稳定内容 ID 与实例 ID，显式输入随机状态；取消选择、回滚及恢复都走规则事务。对外传递可序列化的结构，不暴露内部可变对象或回调函数。跨进程通信按动作批次进行，动画帧留在客户端。

战斗核心不依赖画面时钟。等待模型、动画加速或跳过演出不能改变随机序列和结算次数。存档保留已提交的 AI 内容、规则版本及随机状态，不在恢复时重新向模型生成原卡牌。

## 4. 便于持续更新的约束

1. **单一机制来源**：新增效果须同步 Prompt/Schema/字段表、编译、校验与有限修复、执行、保存恢复及双说明链。宿主消费经过验证的版本，不复制源码再各自修改。
2. **数据与机制分开**：现有机制内的新卡牌和新预设优先作为内容包更新；新增操作、时机或选择语义属于核心升级。内容包不能夹带任意代码。
3. **明确版本职责**：分别记录内容结构、规则集、存档格式与消息协议版本。首次独立版支持明确的版本组合；遇到不支持的数据保留原文件并提示，不默默转换。不由通用化要求扩展旧协议兼容承诺。
4. **按宿主声明能力**：宿主报告可执行操作、选择类型、保存能力等。AI 获得目标能力范围，生成后仍由程序验证；不支持的机制给出明确错误，不悄悄删掉效果。这是实际执行边界，不是构筑强度或创意硬门槛。
5. **维护有意义的契约样本**：用卡牌、状态、选择/取消、随机和奖励等小型场景验证执行、显示、存档恢复。使用我们完整规则的宿主应得到相同结果；使用尖塔规则的后端单独验证原生映射，不能假装两种规则数值天然一致。
6. **发布时锁定组合**：客户端、核心和内容包携带可追踪版本/哈希；先以本地一致安装包交付。远程热更新、插件市场和跨产品存档互通不属于当前要求。

以下为查询日的公开资料，不是本机运行验证；社区库与游戏版本可能继续变化。

| 已核实事项 | 对本项目的影响 | 来源 |
| --- | --- | --- |
| 官方确认二代使用 Godot；社区模板面向 C# | 可积累相近的表现层经验，但游戏内部模型与我们的 TS 核心仍然不同 | [Mega Crit FAQ](https://www.megacrit.com/faq/)、[模板维护者说明](https://github.com/Alchyr/ModTemplate-StS2/wiki) |

| 社区 BaseLib 提供自定义模型、UI 扩展及存储属性注册等支持 | 卡牌/遗物/状态/UI 有可用基础，但 AI 动态定义是否完整恢复仍要验证 | [BaseLib 功能](https://alchyr.github.io/BaseLib-Wiki/docs/Features.html) |
| 卡牌等内容采用模型及生命周期，通过命令调用实际行为 | Mod 应交给原生规则执行受支持效果，不绕过钩子直接覆盖生命或牌组 | [Modding Basics](https://github.com/Alchyr/ModTemplate-StS2/wiki/Modding-Basics) |
| Mod 包包含清单、代码 DLL，以及需要时的资源 PCK | 内容协议还需 C# 宿主、打包与版本管理，不能只导出 JSON 就交付 | [Modding Basics](https://github.com/Alchyr/ModTemplate-StS2/wiki/Modding-Basics) |
| Mega Crit 已公开尖塔二代创意工坊上传工具 | 未来存在发布路径；本次不安装、不上传 | [官方上传器](https://github.com/megacrit/sts2-mod-uploader) |

BaseLib 是社区项目，不等同于 Mega Crit 保证稳定的完整 Mod API。现有卡牌教程以预先定义的卡牌类和卡池为起点；这证明常规扩展有现成路径，但不能据此宣称运行时任意生成卡牌、重载、升级和长局恢复已经受支持。[添加卡牌教程](https://github.com/Alchyr/ModTemplate-StS2/wiki/Adding-Cards)

## 6. 哪种 Mod 值得考虑

以下是结合本项目机制范围作出的工程判断，不是实测工期比较。

| 路线 | 复用内容 | 主要新增工作 | 建议 |
| --- | --- | --- | --- |
| 少量固定卡牌/遗物或角色 | 内容设计、部分素材与机制思路 | C# 模型、原生命令、资源和测试 | 通常范围小于完整新游戏，但不能承载我们的主要 AI 特色 |
| AI 内容扩展 Mod | 智能体、受支持内容协议、编译诊断/修复思路及素材映射 | 动态内容实例、原生效果映射、描述、存档、API 配置与异步请求 | 未来优先验证的路线，首个原型仅单人 |
| 整套玩法移植/大规模改造 | 希望复用全部规则、状态、整局和剧情 | 规则接管、时机/选择/随机协调、复杂 UI、存档、跨语言运行时及 Mod 冲突 | 成本可能接近或超过独立游戏，不作为当前前置工作 |

完整移植困难的关键是状态权威。若我们的内核和尖塔都处理同一场战斗，会同时遇到伤害修正顺序、遗物触发、牌区变化、选择挂起、随机消耗与恢复语义的问题。再加入 AI 动态卡牌，必须保存每个实例对应的定义、修改与引用关系，不能只保存一张通用卡的类名。

建议未来的 AI Mod 使用“尖塔原生规则为权威”的方案：AI 提交受限的结构化内容，C# 适配器先验证，再通过原生命令执行；我们的内核可用于已有内容分析，但不能拿它的模拟结果当作尖塔战斗的准确预言。服务端或伴随进程若有必要，优先用于内容生成与校验，避免跨进程接管每次战斗触发。

例如 AI 提出“造成 8 点伤害并抽 1 张牌”：结构可进入共享协议，但最终伤害修正、抽牌触发和原生遗物反应交给尖塔。我们独有的召唤物、触发时机或选择器，只有在适配器证实支持后才能进入生成范围。模型不生成并执行任意 C# 代码。

尖塔二代的多人玩法另有同步要求。未来原型仅验证单人，不能因单人能玩就声称多人可用；当前独立游戏本身也仍按单人规划。

## 7. 三个方向的消费方式

| 目标 | 规则权威 | 计划复用 | 当前工作 |
| --- | --- | --- | --- |
| Steam 独立游戏 | 我们的卡牌/战斗/整局核心 | 完整协议、执行、说明、智能体与内容包 | 当前主线，先验证 Godot＋本地 TS 候选方案 |
| Bilibili Toy | 若宿主允许，使用我们的核心 | 目标为共享核心和内容，呈现/存储/网络各自适配 | 只保留接口；Toy 的运行环境、网络与密钥存储能力尚未在本任务核验 |
| 尖塔二代 AI Mod | 尖塔原生规则 | 智能体、内容协议与可映射机制子集 | 调研记录；C# 接入及动态内容原型待将来立项 |

不能为了 Toy 预先假定浏览器、后台服务或伴随进程可用，也不为 Mod 裁掉独立游戏已经需要的合法机制。能力差异由宿主适配与内容目标声明处理。

## 8. 实施顺序与后续验证

执行前自审将起步拆为基线与桌面通信 E0/E1、清理后的规则与战斗 E2，之后再接智能体、剧情、爬塔和一个离线预设，详见 [执行方案](standalone-execution-plan.md)。通用化在这些真实消费路径中收敛，不先为三个平台分别做一套成品。

当前下一步的核心工作包是：补齐整局/完整说明出口，明确动作、快照、事件和待处理选择契约，注入随机源，完成独立存档边界，再用一个外部消费者证明不依赖酒馆运行。参考现有 `test:portable-boundary`、`test:reference-battle-session-host` 及匹配源码构建后的 `test:portable-package`，按实际改动补有意义的恢复与显示回归。

未来若启动尖塔二代验证，先限定一个小切片：一张运行时定义的卡牌、一种状态、一次选择、存档/退出/恢复，以及与一种原生遗物的交互。先用固定 JSON 证明原生执行与持久化，再接 AI；分别记录生成、打出、升级/复制、保存重载后的语义。只有动态内容和状态权威成立，再决定是否扩展为独立 Mod 项目。

本次证据仅包括源码入口核对与官方/工具维护者文档。未验证尖塔二代游戏安装、Mod 构建、跨进程桥接、动态模型保存、多人兼容、Toy 接入或完整独立版实玩。文档更新不触发酒馆角色卡构建与安装。
