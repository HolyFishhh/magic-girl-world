## 1. 执行建议

| --- | --- | --- | --- |

| B：Phaser + Electron + TS 核心 | 语言和既有核心更容易衔接 | 仍需重新组织战斗界面和桌面分发 | A 出现已证实、无法合理解决的分发/交互问题时再评估，不同时建设 |
| C：将规则整体改写为 C#/GDScript | 可以统一客户端语言/运行时 | 重做效果、状态、选择、说明和回归，增加语义偏差风险 | 当前不采用；潜在尖塔 Mod 不足以成为重写理由 |

低价 Steam、玩家自填 API、AI 必需的剧情模式、AI 爬塔、一个简单离线爬塔预设、移除色情与整个欲望体系、沿用 emoji＋卡牌美术均保持。Toy、尖塔二代 Mod、公开素材库暂不执行。通用核心为它们保留边界，不把三端同时完成作为独立游戏前置条件。

## 4. 最小运行架构

Godot 接收玩家输入并显示结果；TS 应用层持有唯一权威状态，通过现有内核执行规则。AI 工具只能读状态、检索规则/历史、修改草稿、编译试算和提交候选，实际提交由应用层检查并完成。

首选桥接原型使用 Godot `OS.execute_with_pipe(..., false)` 启动随包 Node，以带协议版本的 UTF-8 JSON 消息通信。stdout 专用于协议，stderr 用于诊断；处理半条消息、多条消息、背压和进程退出，不逐帧发送规则请求。官方明确此方法可创建非阻塞管道，而且子进程不会随 Godot 自动终止，所以正常关闭、管道 EOF、异常失联和必要时终止进程都必须实测。[Godot OS 文档](https://docs.godotengine.org/en/stable/classes/class_os.html#class-os-method-execute-with-pipe)

消息最少区分命令、响应、状态/呈现事件和选择请求，携带请求 ID、运行 ID、状态版本及明确的选择 ID。使用稳定字符串 ID，不序列化可变对象引用、函数或 Promise。超时后先查询原请求结果，不能把“没有收到响应”直接当作“未执行”再打一遍牌。

存档以完整动作事务为提交单位，同时保存已提交 AI 内容、随机状态、规则/内容版本和请求去重信息。存盘成功后再确认需要持久化的动作；动画不参与规则提交。先实现普通稳定边界的原子保存/恢复，再验证选择中的策略：可序列化继续状态，或保持上一个完整动作快照并明确恢复位置。初版如暂不支持中途继续，不得自动替玩家选择，也不能把等待中的 Promise 当成存档。

发布小样先用 Godot 导出 EXE/PCK + 独立运行时目录 + 编译后的 JS/资源，用户只启动游戏 EXE，不需全局 Node、编辑器或开发服务器。Godot 官方已有 Windows 导出流程；Node 的单可执行文件方案仍有额外打包约束，不把制作“只有一个 EXE”列为早期目标。[Godot Windows 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)、[Node SEA 文档](https://nodejs.org/api/single-executable-applications.html)

Node 采用执行时核实的受支持 LTS，锁定精确版本并验证包内依赖，而不因为开发机已有 Node 就略过分发。当前官方发布表将 24.x 列为 LTS。[Node 发布周期](https://nodejs.org/en/about/previous-releases)

E0/E1 先解决工程与分发风险，E2 才清理并冻结独立游戏规则格式。E2 的固定战斗是开发测试内容，不增加无 AI 剧情模式，也不算离线爬塔已经完成。首个面向玩家的 AI 小样以 E3 完成为准。

简单离线包仅定义实际引用的内容，不强制展示全部通用机制。建议规模为一名角色、一个固定初始牌组、小型奖励池、少量普通敌人与一个 Boss、必要事件/商店/营火和短路线。具体数量在 E4 按可玩性调整；这是官方内容制作范围，不限制 AI 合法构筑的卡数、强度或创意。

Steam 商店材料和 AI 接入说明可以早准备；平台申请与审核不会由本地开发验证替代。Steam SDK、成就和云存档接入不作为 E1/E2 启动的前置条件。实现和验收了哪些平台能力，再决定商店承诺哪些；早期本地存档不含 API key。

## 7. 首批实际执行清单

下一批先做 E0/E1，再进入 E2，按照以下顺序提交独立阶段：

1. 核对当前工作树状态及目标目录，冻结拟用源码清单，创建独立工作树与分支，留下起步记录。
2. 确认 Godot 可执行文件与匹配导出模板；缺少时使用官方来源在独立工具目录准备。锁定 Node 与依赖版本，避免改动当前酒馆的构建环境。
3. 建立最小 `client/godot` 工程和 `src/standalone` 入口，使用进程管道做握手、状态查询、错误响应与正常/异常退出；这一阶段不接模型。
4. 导出 Windows 小样，在移除开发工具 PATH 依赖的环境验证启动；记录窗口/输入法/emoji、消息交互和进程回收结果。这只是初步隔离验证，E6 还要干净机器验收。
5. 若上述通过，进入 E2：在独立分支完成色情/欲望依赖清理，补齐核心门面与受影响契约，再接一场固定战斗和稳定点存档。

第一批起步成果是“可启动和关闭的独立桌面工程及可复现构建”；第一个可玩成果是“无酒馆、无需 API、使用真实内核的测试战斗”；随后才是“自填 API 的剧情与战斗闭环”。三者分别报告，不把壳工程当作游戏完成。

## 8. 验证与执行边界

每阶段只运行与改动有关的检查；现有核心边界/参考宿主/类型检查作为起点，发布门面构建后再用对应源码的 `test:portable-package` 验证。机制清理必须继续覆盖 Prompt、Schema、编译、有限修复、执行、保存和双说明链，不能靠删除现行合法行为回归得到通过。

桌面切片验证长中文卡面、固定标题/类型/词条布局、引用详情、目标与实例身份、选择取消、动画跳过、状态/资源来源图标。至少检查常用桌面窗口尺寸及系统缩放；仅离线程序断言不等于 Godot 视觉实玩。

存档验证中断前后均能找到完整恢复点、随机消耗一致、已提交内容不重新生成，以及重复响应不重复发牌/领奖。API key 独立存储；AI 提案用状态版本和请求身份检查，取消后迟到结果不提交。导出资源检查独立入口确实不带入旧色情内容/欲望定义，也不依赖在线字体或图片。

真实模型测试在 E3 使用专门配置的测试连接、样本和调用预算；不自动沿用酒馆私人凭据，也不在本轮产生费用。当前缺少引擎实测与模型样本不妨碍 E0/E1，进入对应阶段时再解决具体依赖。

按每个完成且验证的阶段做本地 Git 提交，报告改动、检查、产物与未验证项。正式上传 Steam、支付入驻费用、对外发布或联系平台分别按届时明确范围处理；本执行前方案没有执行这些动作。
