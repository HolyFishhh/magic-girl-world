# SillyTavern 角色卡研发手册

## 目的

本手册记录“魔法少女世界”开发中反复遇到的酒馆、酒馆助手、MVU、角色卡打包与本地调试问题，供后续酒馆项目复用。目标是缩短定位路径，减少反复导卡和全量构建。

## 1. 先判断问题属于哪一层

按以下顺序排查：

1. **源代码层**：TypeScript、SCSS、HTML、世界书源文件是否正确。
2. **构建层**：`dist` 是否来自当前源文件，资源是否被正确内联或导出。
3. **角色卡层**：PNG 中的角色、世界书、正则、脚本和版本是否与 `dist` 一致。
4. **导入层**：酒馆当前角色是否真的是刚导入的文件，聊天是否仍引用旧角色或旧正则。
5. **楼层层**：当前消息变量、正文、额外模型输出和脚本是否来自同一个最新楼层。
6. **运行时层**：酒馆助手事件、MVU 应用、iframe、战斗会话存储和浏览器缓存是否一致。
7. **模型层**：第一阶段剧情、第二阶段变量模型、预设、世界书角色和上下文边界是否正确。

不要在模型提示里修复程序层错误，也不要用前端容错掩盖非法变量。

## 2. 本地端口与浏览器边界

- SillyTavern 当前监听 `127.0.0.1:8012`。
- Codex 内置浏览器的 URL 安全策略会阻止自动化访问 `localhost`、`127.0.0.1` 和其他回环地址。若命令行 HTTP 返回 200、端口处于 Listen，但内置浏览器显示“无法访问此站点”，这是工具策略，不是酒馆关闭、端口冲突或其他任务占用。
- 禁止尝试通过替代浏览器自动化、原始 CDP 或代理绕过该策略。
- 可用的安全替代方案：酒馆 HTTP/API、Socket.IO、变量快照、聊天 JSONL、构建夹具和用户手动浏览器验证。

快速检查：

```powershell
Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8012/ -TimeoutSec 5
Get-NetTCPConnection -LocalPort 8012 -State Listen
```

## 3. 实时监听开发

项目的 Webpack watch 默认监听 6621。开发时优先保持一个稳定的 watch 进程，再让酒馆助手加载开发资源；不要每次修改都重新打包角色卡。

建议流程：

1. 启动 `npm run watch` 或项目的 `npm run dev:tavern`。
2. 确认日志出现首次成功构建，并记录实际资源 URL；不要沿用旧模板中的 5500。
3. 在酒馆助手脚本中只替换开发资源入口，不改生产角色卡结构。
4. 修改代码后等待增量构建完成。
5. 对不支持热替换的 iframe，手动刷新当前酒馆页面或重新渲染楼层。
6. 用变量快照和控制台日志确认加载的是新哈希或新时间戳。

若监听日志始终没有酒馆连接记录，先检查资源 URL、端口、CSP 与浏览器缓存；不要假设热更新已经接通。

## 4. MVU 两阶段模型边界

- 第一阶段负责剧情正文，可以读取紧凑构筑简报，但不生成变量命令。
- 第二阶段负责 `<UpdateVariable>`，必须读取完整长期变量和程序设计上下文。
- 模式锚点和远征开关属于程序路由信息，不必污染剧情模型；第二阶段可读取完整状态以执行正确事务。
- 第二阶段分析保持短格式，禁止要求长思考链。非流式请求在 UI 中显示加载状态，结束后展示自然语言更新摘要。
- 修复必须重用当前楼层的额外模型事务，不能新建剧情对话。
- `battle.design_context`、运行时计数器和会话字段由程序维护，AI 只读。

诊断第二阶段失败时依次保存：原始模型文本、提取到的更新块、解析错误、应用前变量、应用后变量、契约校验问题和当前消息 ID。只看最终 UI 无法区分“没生成”“没提取”“没应用”“应用后回滚”。

## 5. 变量和楼层一致性

- 所有写操作先确认当前消息仍是最新楼层；历史楼层只读。
- 异步评分、校准和修复在写回前再次比较内容指纹与消息范围。
- 一次性变量只保留到事务消费；玩家卡组、遗物、道具、能力、状态、NPC、谱系和设计上下文长期可见。
- 避免在每轮对话重新初始化整副卡组。首轮负责初始化，后续只做增量获得、升级、删除、变形或修复。
- 卡牌奖励领取、经验结算和敌人清理由程序原子执行；第二阶段不能重复结算。

## 6. 性能排查

越玩越卡时先测量，不要先删动画：

1. 是否重复绑定事件监听器或定时器；
2. 是否在每次渲染重新解析整个聊天历史；
3. 是否把完整大型变量重复序列化多次；
4. 是否在 MVU 写事务内运行影子模拟；
5. 是否无界增长战斗日志、敌人历史、缓存或 DOM；
6. 是否因内容指纹不稳定反复重建会话；
7. 是否把一次性奖励、敌人或修复结果误存为长期重复项。

当前约定：评分在渲染后延迟执行；缓存有上限；同一楼层不重复写相同上下文；战斗日志内部保留完整事件，发送剧情模型时按回合压缩。

## 7. 角色卡构建与验证

推荐顺序：

```text
typecheck
-> 目标模块测试
-> 世界书/接口契约测试
-> production build
-> export tavern runtime/interface
-> patch character card
-> verify tavern contract
-> import verification
```

不要在源测试未通过时用角色卡现场测试替代。生成测试卡时保留版本、来源 commit、世界书清单、脚本清单和构建时间，便于确认导入内容。

## 8. 共享工作树协作

多个任务共享同一目录时：

- 每次编辑前读取最新文件和 `git status`；
- 补丁失败通常意味着文件刚被别人修改，重新读取后合并；
- 不使用 `git reset --hard`、`git checkout --` 或整文件覆盖；
- 发现同功能重复实现时保留更完整的一份，删除重复代码和样式；
- 测试失败先判断是自己修改还是并发修改造成；
- 分支只隔离 Git 指针，不隔离未提交的共享文件。

## 9. 最小现场验收脚本

现场测试至少覆盖：

1. 新对话首轮生成有效起始牌组；
2. 普通剧情多轮只做增量变量更新；
3. 剧情自然触发首战并保留先手伤势；
4. 第一战获胜、查看并领取奖励；
5. 卡组、流派占比和删卡次数立即更新；
6. 第二次遇敌继承谱系或明确形成不同机制；
7. 第二战失败并允许一项或多项合理惩罚；
8. 返回剧情后战斗按回合完整叙事化；
9. 重载聊天后进度、设置和会话不丢失、不重复校准；
10. 历史楼层只读，最新楼层可继续。

自动化夹具应覆盖同一事务；人工现场测试用于确认酒馆、预设、模型和视觉交互的组合结果。

## 10. 顶层扩展调试

需要为某一张角色卡服务的顶层扩展，必须使用角色卡元数据中的稳定协议标记做作用域判断；不要依赖角色名、头像文件名或变量路径。请求阶段还要叠加框架自身的阶段信号，例如 `Mvu.isDuringExtraAnalysis()`，形成“角色卡身份 + 请求阶段”双重门禁。

角色 iframe 的 6621 热更新与 SillyTavern 顶层扩展是两条加载链。开发顶层扩展时：

1. 构建 `dist/sillytavern-extension/<extension-id>`；
2. 复制或链接到 `public/scripts/extensions/third-party/<extension-id>`；
3. 刷新 SillyTavern 顶层页面，不能只重渲染消息 iframe；
4. 在扩展面板确认状态点和知识图谱统计；
5. 普通生成与 MVU 额外生成各抓一次最终请求，确认只对后者注入；
6. 用敌人定义指纹区分“新敌人”与“同一敌人战斗中掉血”，禁止每轮重复校准；
7. 监听 `GENERATE_AFTER_DATA` 时保留 `CHAT_COMPLETION_SETTINGS_READY` 兼容回退，并用提示标记防重复；
8. 注入放在 `</past_observe>` 后、MVU 任务前，避免历史信息稀释或末尾 system 兼容问题；
9. 扩展 `activate` 只注册监听和 UI，深模拟放空闲预热与有界缓存；
10. 禁用扩展后必须移除监听，角色卡降级链仍能单独运行。

MVU quiet/background 请求不能依赖 SillyTavern 原生 Function Calling。需要程序数据时，优先在请求发送前完成确定性查询并注入结果；不要为第二轮额外搭建会增加多次模型往返的工具智能体。
