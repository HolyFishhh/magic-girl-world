# MVU 世界书边界

本项目使用 MagVarUpdate 的额外模型解析模式时，世界书条目 comment 中的标签是传输边界，不是普通提示词标题：

| 分类 | comment 标记 | 剧情模型 | 变量模型 | 条目 |
| --- | --- | --- | --- | --- |
| 变量模型专用 | `[mvu_update]` | 否 | 是 | `额外模型变量更新格式`、`变量更新规则`、`首条消息变量更新` |
| 剧情模型专用 | `[mvu_plot]` | 是 | 否 | `等级表现形式`、`世界信息`、`地点与NPC线路`、`入侵与遭遇类型` |
| 两边共用 | `[mvu_plot][mvu_update]` | 是 | 是 | `输出格式要求`、`变量说明`、`战斗内容生成要求`、`战斗场景生成`、`远征节点协议`、`初始战斗内容修复`、`战斗场景修复` |
| 配置，不是提示词 | `[config_override]` | 不发送 | 不发送 | `mvu-config-override.json` |
| 禁用旧配置 | `[mvu_plot] [initvar]` 且条目关闭 | 不发送 | 不发送 | `变量初始化.json` |

## 为什么存在混合条目

- `输出格式要求` 同时规定剧情正文/选项顺序和变量块边界。
- `战斗内容生成要求`、`战斗场景生成` 同时规定叙事入口和可执行战斗 JSON；变量模型必须知道对象契约，剧情模型也必须知道何时进入战斗。
- `远征节点协议` 同时规定事件/商店/营火的叙事行为和 `run_result`、`run_upgrade` 的变量命令。
- 两个修复条目同时描述程序给出的错误上下文和最终变量修复格式。
- `变量说明` 是共享的路径地图，保证剧情模型在单模型模式下也能输出正确路径；额外模型模式下它对变量模型尤其重要。

这些混合条目是有意保留的协议型共享内容，不代表两个模型会收到完整的对方职责。真正的职责分工由标签过滤完成。

## 单模型模式的区别

当 MVU 设置为“随 AI 输出”时，MagVarUpdate 不执行上述额外模型过滤，世界书按酒馆正常规则发送给主模型。因此 `[mvu_update]` 在该模式下不是访问控制标签；它只在“额外模型解析”模式下产生分流效果。

## 本次 502 的边界

`502 Bad Gateway` 出现在远程酒馆自己的：

```text
http://38.147.172.105:7676/api/backends/chat-completions/generate
```

这发生在世界书过滤完成之后、变量文本返回之前。它表示当前 MVU 选中的 API 方案/模型后端没有成功响应，不是 `[mvu_update]` 语法或世界书解析错误。重试只会重复请求同一个故障后端。

排查顺序：

1. 在 MVU 面板确认“更新方式”和当前 API 方案；“与插头相同”使用酒馆主模型，“自定义”使用 MVU 自己保存的 URL、密钥和模型名。
2. 直接确认远程酒馆的后端地址、模型名和密钥可用，再把请求策略从“失败后重试”改为一次请求验证。
3. 后端恢复前可临时选择“随 AI 输出”避免第二次 `/generate` 请求；这会让主模型承担变量命令，仍使用同一套 `_.set/_.assign/_.remove/_.add` 协议。

角色卡不保存 API Key，也不会把远程 502 转换成可用的变量更新；卡内配置只能决定是否启用额外模型及其自动请求开关。
